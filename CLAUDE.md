# CLAUDE.md

## Design Tenets

Principles that guide every decision in dux. If a change conflicts with a tenet, the tenet wins.

### Configuration

- **All settings are configurable.** Every single one. If a user can't change it, it shouldn't be hardcoded.
- **The config file is the documentation.** It must clearly explain what each setting does through inline comments. A user should never need to leave the config file to understand an option.
- **Project config is portable desired state, not runtime cache.** `[[projects]]` may store portable user intent (id, path, name, default provider, auto-reopen, startup command). Do not write runtime-derived git or agent state into config.
- **Keep derived project state in SQLite.** Branch status, worktree paths, agent branch names, and provider process/session state belong in SQLite/runtime memory only. Saved config must omit derived values like the leading branch so autodetection is not pinned into portable config.
- **Startup command execution shell is global config, not project state.** Project config owns the command text; the global `[startup_command_terminal]` section owns the shell used to run it.
- **Config wins for explicit project preferences.** When a project exists in both config and SQLite, explicit config values for safe preference fields update SQLite on startup/reload. SQLite may fill missing config fields but never overrides a value the user wrote. Reserve hard sync conflicts for genuine identity ambiguity (duplicate ids or paths that disagree).

### UI and Navigation

- **New UI must use the theme engine.** Every screen, pane, dialog, and visual state derives colors and styles from `Theme`/`theme.rs`, never hardcoded values. Reuse an existing semantic field when it matches the meaning; add a new one only when none does, and wire it through every supported theme in the same change.
- **Tab and Shift-Tab navigate between panes.** This is the primary spatial navigation model.
- **Panes have local key combinations.** A key combo bound in one pane does not necessarily work in another.
- **Panes have interactive and non-interactive modes.** In interactive mode all key combos (including global ones) are suppressed and input is forwarded to the PTY. In non-interactive mode both local and global combos are active.
- **Key combinations are documented in the help page.** The in-app `?` overlay is the authoritative reference. External docs describe how to configure bindings, not enumerate them.
- **Line-scroll keys are gated by context.** In interactive (PTY) mode, arrow keys and Space only scroll when already scrolled back; otherwise they pass through to the child. Non-interactive views scroll unconditionally. Page-scroll keys always initiate scrolling.
- **Movement keys move focus; Space and Enter act on what has focus.** Movement keys never change a value. Space activates the focused button or checkbox in every dialog (a universal accessibility convention, not a configurable binding), and types a space when a text field has focus. Any modal with more than one focusable control needs an explicit focus concept, and the focused control must visibly render as focused. Bindings are user-configurable, so never name specific keys for these roles in code, copy, or docs; resolve them through the bindings.
- **Every modal declares its family in the registry.** `crates/dux-tui/src/app/modal.rs` holds an exhaustive registry with no wildcard arm: a new modal does not compile until it is assigned one of four families, derived from what a keystroke means, not how the modal looks. Report (read-only, scrollable, no focus), Confirm (prose plus buttons, movement moves focus), Picker (rows with a selection cursor; picking confirms, so no button pair unless the buttons are genuinely distinct actions), Form (fields plus buttons; horizontal keys belong to the caret). A modal's family may depend on its state, not just its variant.
- **A modal with a full-text (multiline) field must have a confirm button; a modal with only single-line fields must not need one.** In a multiline field Enter is content, so the form needs a button to say "done"; in a single-line form Enter submits unambiguously. The registry enforces this and the known-violations list is empty and must stay that way. This is house style for modals, not a logical necessity.
- **A shared component probably already exists; ask before you invent one.** The modal chrome, focus ring, key ladder, click routing, hint bar, and text input are all extracted in `crates/dux-tui/src/app/components/` and `modal.rs`. A second copy of any of them is the drift this rule exists to prevent.
- **All text entry goes through the one shared `TextInput`.** It owns caret motion, word motions, and multiline scrolling. Never hand-roll a buffer; a new typing surface gets a `TextInput` field, not a `String` you push characters onto.
- **Two kinds of text field, told apart by a real flag.** Single-line fields have no mode: typing is immediate and the arrow keys must reach the caret, so the binding lookup is suppressed while one has focus (otherwise an arrow key silently triggers whatever it is bound to; that bug shipped). Multiline fields have an explicit engage step tracked as a mode: unengaged, the modal owns every key; engaged, every key goes to the text and the exit-edit binding leaves the modal open. Engaging is always an explicit act, never a side effect of typing. The reason for the mode is Enter, which is content in a multiline field and the confirm key everywhere else; it is not Tab.
- **An unengaged field must look unengaged and say how to start.** Focus and engagement render differently: focused-but-unengaged gets the focus border and no caret, and the footer names the engage key. Both surfaces go through the shared field-frame renderer.
- **Filters, search rows, and the command palette are deliberately type-immediately.** Keystrokes go straight into their `TextInput` with no engage step. Adding a mode to a search box is friction, not consistency.
- **Escape never saves.** It abandons, or it exits edit mode.
- **A field the user cannot click into is a gap.** Every caret-bearing field publishes its rect into the overlay mouse layout so a click can land the caret. Caret positions are display columns, never byte offsets or char counts; use the shared column/byte conversion helpers, and render single-line fields through the shared renderer, which is char-safe and takes a focused flag.
- **The PR banner is a click target on both surfaces wherever it is painted, and it opens the pull request through the same command the palette runs.** The web banner is one link across the whole strip, so the TUI band is clickable end to end too: it is dux's own chrome in a lane of its own, outside the pane, so any left click on it opens the pull request whatever modifiers are held, and nothing is forwarded to the child. The web banner is an anchor, so parity is the RELEASE, not the press: the press arms the gesture and a slide off the band cancels it, riding the link click's retirement triggers rather than a lifecycle of its own. The rect is published only where the band is actually painted, which is what keeps a maximized surface, or a pane that is taking input, from leaving a live click target nobody can see.
- **Clickable controls need misclick-safe spacing.** Separate adjacent click targets enough that an imprecise click cannot activate a different item.
- **Animations and periodic refreshes use wall-clock time, not tick counts.** Use elapsed real time so animations stay smooth regardless of tick cadence.
- **Chords belong to dux; typing belongs to the agent.** Tab is the one typing-looking key dux keeps by default, because it has moved panes since the first version; `tab_reaches_agent` hands Tab and Shift-Tab to a live agent in the typeable pane, and the pane chords always work.
- **The embedded-PTY caret is the host hardware cursor, never a painted block.** The OS anchors CJK IME composition popups to the hardware cursor, and pre-painting the cell breaks hosts that draw their cursor by inverting it. The caret look is the host terminal's cursor and is not theme-colored; that tradeoff is intentional.
- **The TUI does not disambiguate Shift-Enter; Ctrl-j is the supported soft-newline key.** Interactive input is a verbatim passthrough, and pushing Kitty keyboard-enhancement flags would re-encode every key for the child, breaking providers that don't speak the protocol. Users who want Shift-Enter can run dux inside a terminal or multiplexer that already speaks the Kitty protocol. Only the web UI rewrites Shift-Enter, because there the key event is available before encoding.

### Web UI (server mode)

The web UI (`crates/dux-web/web/`, React + Vite + Tailwind) has its own conventions, distinct from the TUI's theme engine. It is currently dark-only. Style through the shadcn/base-ui token CSS variables, never hardcoded colors.

- **Components: shadcn/base-ui first.** Reuse an existing `components/ui/*` primitive before hand-rolling one. Hover hints go through the shared tooltip component, never a native `title=`.
- **Actions collapse into one `⋯` menu, on a row and on any pane- or bar-scoped surface.** A list row needing more than one action gets a single dropdown menu behind an ellipsis trigger that reveals on hover, consumes no layout space when idle, stays revealed while its menu is open, and always shows on touch. The same idiom carries the secondary controls of a surface that is not a row: the editor header's phone fold, every phone pane screen's action flap (an agent's and a terminal's alike), the desktop pane header's own `⋯`, and the input `⋯` anchored to the virtual input. A surface-scoped `⋯` is present for as long as its surface is, never conditional on some state within it (a control that appears only once you are stuck is a way back, not a way there), it never renders empty (compute the items, then decide whether the trigger exists), and exactly one instance of it is on screen whatever the surrounding state. A control that must be reachable when a surface is GONE therefore cannot live in that surface's `⋯`: it belongs in the menu of a surface that outlives it. Every menu item carries a leading icon; a trailing `…` marks any item that opens a dialog or needs confirmation. Destructive menu items default to neutral color: the ellipsis and the confirmation dialog are the danger signal. (The agent menu's Delete entry is the one deliberate red exception; do not propagate it without a deliberate decision.)
- **On a phone the pane's actions hang off the band as a flap, and theater flies that flap into the pill rather than swapping one for the other. Every pane screen has one, an agent's and a terminal's alike.** The screen's header keeps navigation, identity and (for an agent) the pull-request chip only: on a narrow screen the identity is what tells you which of half a dozen near-identical terminals you are looking at, and it lost that argument to every button placed beside it. A project or standalone terminal has no changed-file summary and no pull request, so its cluster is one control shorter and its band is always the plain one, which is exactly why the silhouette is measured rather than drawn; nothing else about it differs, because it is the same component running the same flight. The flap is dux's own chrome painted over the terminal, so a press on it never reaches the PTY; it costs no layout space, so theater (a request for more room) does not take it away but flies it; and it sits outside the pane's overlay slot, because that slot is withheld under a full-pane cover and the flap is the only way to the session's actions. Its silhouette is ONE generated SVG measured from the cluster it wraps, never CSS borders and gradients, which cannot hold a seam against the band at fractional device pixel ratios. Entering theater collapses the TOP chrome only: on a coarse pointer the compose bar and the key row are the typing surface, and a mode about looking at the terminal must not take away the way to answer it. The cluster then travels as one object, which is only possible because the flap and the pill are the same component at the same offsets; anything that differs between them tears at the handoff, and the pill's extra width is the grip slot, animated in flight rather than reserved as a blank space the flap would have to leave. The return is deliberately travel THEN snap, and it parks on the pixel grid before the real flap swaps in. Every stage collapses to an instant swap under reduced motion, and a page that opens in theater runs no flight at all, because there was never a dock on screen to leave.
- **Theater mode is the ONE way to hide the phone's top bar, and there is no preference beside it.** It takes the header and the tab strip together and hands back the way out in the same gesture (the pill, and Leave theater mode in the top menu the pill opens). The exit is deliberately NOT in the input `⋯`, which lives inside the virtual input and leaves with it. A `ui.mobile_top_bar` preference did the same job with no way back of its own, and two flows for hiding one header are two things that can disagree about what is on screen; it is gone from the menus, the Preferences dialog, the store and the config, and a config file still carrying the key loads unchanged with the key ignored. The touch terminal-keys bar keeps its preference, because it hides a typing surface rather than navigation. A non-owner therefore gets no input row of its own: the top-bar toggle was the only item a viewer could act on.
- **Every surface has ONE top menu, and it owns the input's permanent controls in a labelled INPUT group at its head.** That menu is the flap's `⋯` on a phone, the pane header's `⋯` on a computer, and the floating pill's in theater, and it is always reachable whatever the pane is doing, which is exactly what the virtual input is not. It is deliberately NOT the header's cog: the cog's menu is the app's, and none of these rows is about the app, so the group goes where every other per-entity action already lives. THE MENU IS ONE BODY PER KIND OF PANE, and the sidebar row is a fourth anchor on that same body rather than a smaller menu of its own: what an anchor may change is where the menu opens and how its trigger is drawn, never what is in it. Which body a surface opens is the question its own identity already answers (an agent's when an agent is behind the pane, a session-owned terminal included, whose own Close and editor entries then ride along as a labelled group for the pane in front of you; the terminal's own when there is no agent), and the one-home rule for the input rows is unaffected, because what the group holds is the pane's published answer rather than an anchor's decision. WHICH pane's answer is the one thing an anchor must hand over, because only it knows what is on screen underneath it: a companion terminal's pane publishes under the TERMINAL's id while the menu over it is the agent's, so a scan derived from the subject finds nothing and leaves that pane with no attach item and no way back from typing straight into the terminal. The desktop cluster around that `⋯` is theater and Macros, one outline family at one height token, rendered together or not at all so half a cluster never paints; the reopen control is deliberately not one of them, since it has to outlive the pane it brings back and therefore sits out in the Changes-pane spacer beside the cog. The theater button says the word "Theater" beside its glyph: it is a mode with no other way in, and a lone glyph among glyphs is the control nobody finds. So the group carries "Attach a file…" and, once the virtual input is down, the way back to it; the group's label stays even with one item in it, because these rows are about the typing surface rather than about the agent whose actions sit below them. WHAT IS IN IT IS THE PANE'S ANSWER, published under its pty id: only the pane knows whether it owns the input and whether a bottom bar of its own is already carrying a row, and that is what keeps a control in exactly one of the two menus at a time. The attach act is borrowed from the same pane's own capability rather than published twice, and a group with nothing in it renders no label and no separator. The count and the state a surface reports stay out: this is the same menu, under the same rule, that refuses to grow a second copy of the tab strip or the changed-file count.
- **The floating pill carries controls that ACT, and nothing that merely reports, and its `⋯` is the pane's whole menu on both surfaces.** Theater unmounts the sidebar and the header together, so a pill carrying only the app menu leaves that surface with no route to the agent's or terminal's own actions at all; the app menu rides inside the merged body as the Settings drill instead. Its tab-status expander is gone on both surfaces: the agents list and the tab strip are where tab status lives, and a second, smaller copy of it floating over the terminal was a place for the two to disagree. The cost is stated rather than papered over: in theater on a phone, where both of those are off screen, a hidden tab needing attention has no on-screen signal until you leave the mode. That is accepted, and it is not "a toast will tell you", because nothing raises one for attention.
- **Destructive actions always confirm.** A destructive item opens a dedicated dialog (Cancel autofocused, destructive-styled confirm, misclick-safe spacing), following the existing per-action dialog pattern. Target-keyed dialogs close themselves when their entity vanishes from the live view model. A monitoring surface confirms its stops too: being a screen about destructive actions is not a licence to act on one click. Keep confirms cheap to dismiss so the hung-agent escape hatch stays fast.
- **Shift-Enter inserts a soft newline, not a submit.** The terminal pane intercepts it at the key-event layer (the data layer cannot distinguish it), the decision lives in pure, unit-tested helpers in `lib/termkeys.ts`, and it never rewrites a keystroke mid-IME-composition. Only the input owner writes the newline. The mobile accessory bar carries a dedicated soft-newline key; both entry points share one write helper so their behavior cannot drift.
- **Width decides the layout; the pointer decides the DEFAULT typing surface, and the user's explicit per-device choice wins after that. Two separate rules.** The mobile breakpoint picks which shell you get. Pointer coarseness picks whether typing STARTS in the buffered compose bar (where autocorrect, swipe, and IMEs have something to work with) or directly in xterm. They are orthogonal: a tablet in landscape gets the desktop layout and still gets the compose bar. The detection is a guess and it loses to the person: one resolved value, an explicit choice over the pointer's default, flips in both directions on every device, and turning the compose bar on where the browser says it is not needed is allowed. Detection changing (a rotation, a mouse unplugged) moves the default only; the choice persists until the user changes it. A hard `always`/`never` from Preferences still wins over both, so the per-device choice is the live override within `auto` alone, and the switch is offered only there, where a press can take effect. Wherever the compose bar is up, it is THE typing surface, for the input owner alone: xterm stops holding the keyboard for that pane, a click into the terminal and a right-click paste both land in the box, and xterm's helper textarea leaves the tab order so backward keyboard navigation still leaves the pane (a focus rule cannot answer that one, because a Shift-Tab out of the box and a click into the terminal are the same event). The focus redirect is deferred by a microtask so xterm can finish publishing a selection to the X11 primary selection first. The switch lives in the input `⋯` for as long as any row under the terminal does, and moves up into the TOP menu (the flap's `⋯` on a phone, the pane header's `⋯` on a computer, the floating pill's in theater) once nothing is left to carry it. The one-time hint that says where it went names the control of the shell it fires on, never the other one's.
- **The compose bar is the typing surface wherever a finger types; xterm is never typed into directly while it is on.** Send delivers the body as macro-style keystrokes with the submitting Enter travelling separately and delayed (deliberately not bracketed paste: the wire keeps "line break" and "Enter" distinct); an empty Send is a single bare Enter for confirming TUI menus. Draft state outlives the bar, so rotation or a preference flip never destroys a draft, and a refused send keeps the buffer and toasts why. Non-owners get no typing surfaces. The gating preference's `auto` mode alone consults a transient, locally-stored per-device choice, because the browser cannot tell a tablet with a keyboard case from one without; that choice writes nothing to config. The virtual input is the textarea and the terminal-key rows, which follow the pointer rather than the layout and switch independently of each other (see the next tenet). `never` is the operator saying "no message box" rather than a person choosing to type directly, so it offers no surface switch anywhere, and a coarse pointer keeps its keys there because a finger still cannot produce a Ctrl chord. THE WAY BACK LIVES IN WHICHEVER MENU THE PANE PUBLISHES IT IN, every surface that flips the choice writes through one helper so they cannot drift, and the first switch that leaves nothing at all under the terminal raises a one-time per-device hint naming where the way back went. A physical keyboard over a focused compose box forwards exactly Escape and F1-F12 to the PTY, decided by a pure rule in `lib/termkeys.ts` and delivered through the accessory keys' own write helper: those keys have no textarea meaning, and a hardware Esc is the physical twin of tapping the accessory Esc, so it rides the same path (ownership gate included). Every modified press stays browser-side, Ctrl chords above all, because Ctrl-C is copy in the browser and SIGINT in the PTY and hijacking copy is worse; nothing forwards mid-IME-composition, where Escape means cancel the composition; Direct mode is the full-fidelity escape for everything else.
- **The message box and the terminal key row are INDEPENDENT surfaces with independent switches, and all four combinations of them are legal.** They answer different questions: the box is where the text is composed, in a buffer autocorrect, swipe and IMEs have something to work with; the row is keys a soft keyboard cannot produce at all (Esc, Tab, a Ctrl chord, a soft newline). Keys with no box therefore exists on purpose and is not a degraded state: a finger holds the virtual Ctrl while a physical keyboard types the letter. "Type directly in the terminal" takes the BOX and never the keys, which keep their own Hide-terminal-keys preference; a fine pointer's keys still arrive and leave with the box, because a laptop already has those keys. ONE HOME AT A TIME FOR THE WAY BACK, and the pane decides which: the bottom input `⋯` exists while ANY bottom row is up and carries the surface switch in BOTH directions plus the keys toggle, while the top menus' Input group carries the way back only when nothing is left under the terminal at all, and the one-time hint fires only in that last case, because otherwise the way back is visibly in the bottom `⋯`. The key row carries terminal keys ONLY: no mode-changing or behavior-changing control rides on it, because a control that changes what the surface IS, one cell wide among keys that merely type, is not something a thumb reaching for Tab should be able to hit; that action belongs in the bottom `⋯`, which is a menu and says what it does.
- **`lib/notify.ts` is the one place that raises a notification, and a boundary test keeps it that way.** No other module imports the toast library directly. The library stays the countdown mechanism; dux owns the policy. A toast id means replacement, not de-duplication, so repeat-raising on a fixed id pins a toast open. The configured display window lives inside the raiser, not at call sites, so it can never be captured stale. The standalone editor tab shows only what it raised itself or what the wire addressed to its own connection, and it carries no attention count: workspace-wide messages live in the workspace tab.
- **Every toast dismisses itself on a severity-graded window derived from the one configurable base, except the few marked sticky.** Sticky is a boolean orthogonal to tone, reserved for when the user must act outside the toast to recover or something may be lost or left half-done; keep the sticky population in single digits, and when in doubt record at the site that it was weighed. A busy toast is the exception, and it is never retired by a clock: it leaves only when its own final replaces it, or when something says in words what happened to it. It needs its own guard because the library refuses to retire a loading toast, and that guard REPLACES the spinner with a warning rather than dismissing it, because a spinner that simply vanishes is read as "the operation finished" and the guard knows no such thing. It is timed clear of the engine's busy timeout, which is the cadence a live server answers on: at the timeout the engine either upgrades a genuinely stranded busy to a warning or, when the operation behind it is still registered as running, re-sends the busy on the same key. A running operation therefore keeps its spinner however long it runs, and the guard firing means the server went quiet. The guard's own wording is chosen per origin: a spinner waiting on the wire points at the log, a spinner waiting on a fetch this tab made says the request is still in flight. Severity reads at a glance through icon color and shape (never color alone), and swipe dismisses because the close button is not a touch target.
- **One marker for git status.** Every changed-file status marker renders through the shared `FileStatusIcon`, backed by the one pure status-interpretation helper. Never re-implement it inline. In the changes pane the leading slot belongs to the marker, which becomes the selection checkbox on hover, on focus anywhere in the row, or while the row is checked (on a coarse pointer there is no hover, so the slot is the 40px tap target and tapping it ticks the row); the checkbox is always in the DOM and the swap is opacity, never `display`, so a keyboard can always reach it. A checked selection is acted on by one bulk bar of plain verbs carrying their counts, plus a Select all / Select none toggle over the rows the filter shows, never by a second surface-scoped `⋯`, and the header's stays the pane's only one.
- **Touch targets have a 40px floor, and any exemption is per axis and justified at the call site.** The floor exists so an imprecise tap cannot hit a different control. A control may shrink along an axis only when every neighbour on that axis is non-interactive, absorbs a stray tap harmlessly, or is separated by measured clear spacing, and it keeps the floor on the other axis. A bare smaller class with no comment naming the neighbours is a bug, not an exemption.
- **A control's height is set explicitly, never inherited from padding or content.** Controls that sit together share one height token and vary only in width. On phones prefer icon-only, except where the text is data (a count, a size). Verify group heights are identical rather than asserting it.
- **An action cluster shares one variant (outline); navigation stays quieter.** A control that navigates rather than acts may match the cluster on geometry and differ on weight, but decide and write the reason at the site.
- **The working-agent icon bob is required and must settle back to rest.** It animates only while the agent works, and when work stops it eases back to the rest position rather than freezing mid-cycle (keep the transition class paired with the conditional animation class). The bob and the name shimmer fire on the same flag so they stay in lockstep.
- **Terminal clipboard is wired explicitly and follows the classic-terminal model: selecting copies, right-click pastes, no context menu.** xterm's defaults would leak the paste chord to the remote machine's clipboard, so the pane owns clipboard. Classify clipboard chords by physical key, never by `ev.key`, or non-Latin layouts reopen the leak. When the app in the PTY has mouse reporting on, a drag is forwarded instead of selecting locally; a force-local-selection modifier is the escape hatch and a one-time hint toast points at it. The suppressed native context menu requires wiping the selection xterm stuffs into its hidden input, for every pointer type. Keep all of this when touching `TerminalPane.tsx`.
- **A finger selects text with a long press, and dux drives xterm's selection model itself.** The browser can neither select inside the terminal nor synthesize mouse events for a touch drag, so the pane selects via xterm's public API, drags re-select, and the lift copies through the same copy-on-select preference while cancelling the browser's synthetic events. The arithmetic and word rules are pure in `lib/termselect.ts` and reuse xterm's own word-boundary behavior, because a long press and a desktop double-click are the same intent. A long press always selects locally, even under mouse tracking.
- **A click that dispatches a hyperlink belongs to dux, and never reaches the app.** dux is remote-first, so a mouse-tracking CLI answers a forwarded click by opening the URL on the SERVER's machine, where the clicker cannot see it; the browser-side open is the only one that lands. So while the app is tracking the mouse, a press on an OSC 8 link is withheld from the PTY along with its release, decided at press time (a lone press is what a TUI button acts on) and keyed on the link dispatch alone, so every other click still forwards. The hatch chord (Cmd on a Mac, Ctrl elsewhere) forwards the click and refuses dux's open, and the force-local-selection modifier is left alone entirely (it is a selection, so the press passes through, xterm forwards nothing under it, and dux opens nothing either): a link must not be the one place the selection hatch fails. This deliberately diverges from iTerm2, Ghostty and kitty, which give the click to the app and reserve links for a modifier. The TUI follows the same rule and the same split: the PRESS decides (withheld from a tracking child, keyed on the link alone) and the RELEASE opens, only where it landed on the same link or never left the cell, so a drag across a URL still selects it rather than opening it. Ctrl is the hatch, and like the web it refuses the open only while a child is tracking the mouse, because with nothing to hand the click to the chord has nothing else to mean. One pure helper decides press and release for both the windowed mouse path and the fullscreen raw-input path, one pending record carries the gesture (retired on a new press, on focus loss, on a resize and on a surface change), the hatch rebuilds the whole gesture modifier-free rather than passing raw bytes through, and the hit test refuses a snapshot that does not belong to the pane on screen. Shift stays out of it on this surface, deliberately unlike the web: it is dux's own selection modifier and the host terminal's link gesture while dux holds the mouse, and a selection must not end in a browser tab.
- **A forwarded touch gesture is a replayed DOM event, never a mouse report dux encodes itself.** Mouse protocol and encoding are negotiated by the app and xterm publishes no read of them, so `lib/termmouse.ts` plans DOM events and lets xterm resolve the cell and encode with whatever was negotiated; tapped hyperlinks are resolved the same way in `lib/termlink.ts`. Subscribe to both data and binary output streams or some protocols' reports are dropped. A forwarded touch-scroll sends at most one wheel notch per touch-move, reproducing desktop wheel cadence; magnitude bursts corrupt real TUIs' repaints. Local scrolling of xterm's own scrollback keeps the full magnitude.
- **Attaching never steals, and take-over is a fresh attach.** A plain resize claims only an UNOWNED pty; against one somebody else drives it is refused whole (resize included) and silently, so the `connected` handshake must carry the pty's current owner or a foregrounded arrival wedges itself as a phantom owner with no card and no keystrokes. Only a resize explicitly flagged as a take-over transfers ownership, the claim decision and the resize enqueue share one critical section (or the recorded owner ends up paired with the loser's geometry), and the owner's disconnect is broadcast (or the card becomes a permanent lie about a browser tab that closed). LOSING OWNERSHIP IS STICKY: that broadcast only re-titles the card, and nothing passive ever re-claims, because the server reaps a dead connection tens of seconds after a blipped owner is already back and an idle watcher would win a race the returning driver did not know it was in. The re-claim gestures are the button, a reload, navigating away and back, and the returning owner's own handshake, which recognises the pane's previous, dead connection id as its own ghost and SELF-SUCCEEDS with a flagged claim (foregrounded pages only, so the backgrounded-owner contract stands). Take-over itself sends nothing down the live socket: it arms an intent and bounces the socket, so the claim rides the reconnect's first resize frame and the replay clears the viewer-era scrollback that a live claim would have kept. The cost, accepted: ownership no longer follows focus, so switching devices costs one tap. **An automatic reconnect is a plain attach and never a take-over: no retry, resume or heal bounce carries the flag, and only a press on the button does.** The intent never outlives the socket it was armed for, so any close of that socket drops it and the button works again; self-succession survives as the one press-less re-claim, and it is safe only because the flagged frame names the exact ghost connection it expects to succeed and the server refuses the transfer inside the claim's own critical section when anybody else holds the pty by then. THE COVER STAYS UNTIL THE REPLAY IS APPLIED, never merely until the socket opens, and every open mints an attach epoch that its held bytes, its drain state and its own write callbacks are keyed to, so a superseded open can neither clear the cover the new one put up nor flush a byte stream the server has already replaced. A wait that has no answer is bounded rather than blank: past the replay wait the cover becomes a Reconnect box, and no unbounded blank pane remains. Reconnecting is indefinite while the page is visible and parked while it is hidden (PTY sockets only, because attention indicators ride the events socket), it resumes idempotently on every return signal rather than tearing down a live socket, and it is gated on the server-run identity check having actually RESOLVED, never merely on the events socket being open. One periodic client frame carries both the viewed semantics and an application-level beat, because the server's ping is send-only and the half-open socket a radio handoff produces answers nothing; there is never a second pinger. Every one of these clocks counts accumulated visible time, not wall time, because a throttled or suspended page resumes believing hours passed.
- **A watcher renders at the PTY's true grid, shrunk to fit, and there is no other mode.** One PTY has one authoritative grid, the owner's, so the pty socket carries it (on the `connected` handshake and as a `size` event on every APPLIED resize, never on a refused one) and a non-owner adopts it rather than fitting its own container: the emulator is re-gridded to the child's geometry and the FONT shrinks until it fits, never a CSS transform (which would break xterm's pixel-to-cell math for selection, links and touch), floored at a readable minimum below which the terminal overflows into a pannable host. That removes the divergence class instead of managing it, so the live view is faithful and local scrollback cannot record wrapped garbage. The mode is derived live from the ownership verdict, never latched, and the coordinator stays the one owner of every fit, send and re-grid. There is deliberately no preference for the old fit-my-window behavior and no "sized for another device" badge: the full-pane take-over card covers a watcher's terminal in every ordinary state, so the only difference the two modes ever produced was hidden behind it, and faithful adoption keeps the grids equal whenever a remote grid is known at all. A diverged viewer still heals its already-polluted scrollback by bouncing its socket through the ordinary reconnect path (debounced, and never when it is the owner, mid take-over, mid bounce, or on the handshake's own grid), adopting the new grid BEFORE the bounce so the replay is parsed at the child's geometry. The take-over surface is the full-pane card, deliberately: it tells the watcher that a device with a different viewport size is driving this PTY and that taking over retargets the PTY's size to this device, not that the picture underneath is bad (the faithful buffer keeps it clean regardless, and take-over stays a fresh attach).
- **A local refit and the child's resize notification are one atomic pair, and the viewer never volunteers focus state during a replay.** A gesture that holds one half holds both: a measured xterm resize resets the scrolling region to full screen on both buffers, so refitting mid-gesture corrupts a region-relative pager that is still painting for the old geometry, and every direct-send resize path routes through the same hold (coalesced, last geometry wins) rather than around it. Applying a replay is likewise bounded by a suppression window, closed by the write callback and never a timer, because the replay's mode-restore tail makes xterm report its own focus state back at the child; real focus transitions outside the window still flow.
- **The soft keyboard is handled by the browser, not JS, and the web UI has no fullscreen mode.** Every directive on the viewport meta in `index.html` is deliberate and measured (keyboard-resize behavior, safe-area insets, suppressing the input-focus auto-zoom without harming accessibility zoom). Do not reintroduce the browser Fullscreen API, Keyboard Lock, or a fullscreen toggle: on Android the Fullscreen API hard-clips against the keyboard-shrunk viewport, and the shortcuts it captured have in-app equivalents. The TUI's fullscreen pane is separate and unaffected.
- **The URL is the source of truth for position, and nothing navigates relatively.** The hash names the whole position; state-to-URL is the normal direction. Moves within a screen replace, screen changes push, so Back always visibly moves. In-app chevrons are Up controls that push a named destination, never `history.back()`: a relative step has no floor and can walk out of the app. A URL naming a missing agent renders a truthful not-found screen (never a silent fallback to home), retired automatically when the agent reappears; vanished ephemeral targets fall back out loud, rewriting the URL.
- **A reconnect onto a different run of the server hard reloads the page, and that is the only reload in the app.** The server publishes a version and a once-per-run process id; either moving on reconnect reloads with no prompt, because a stale page is wrong exactly where nobody looks. An unknown answer is not a change, so a flaky network never reloads. Keep it narrow: this identifies the server run, and must not grow into a schema version.
- **Settings live in exactly one place: the Preferences dialog.** A preference is a row in the settings descriptors, not a menu item; the app menu carries actions and dialogs. A preference needing a write side effect gets a bespoke write target routed to the existing dedicated endpoint, never a fork of the generic settings patch.
- **The launcher corner is one filled verb plus one grouped `⋯`, and the starter-.gitignore list is deliberately not a setting.** One component renders the corner wherever it appears (the sidebar footer and the mobile hub's bottom bar; neither hand-rolls a copy), and the collapsed rail carries the same two controls as bare icons. The verb is the workspace's one primary creation click: New agent, flipping to Add project only on a CONFIRMED zero project count (an unloaded spine is not a zero) through a pure helper the empty state's hero button reads too, so the two buttons on screen can never name different next steps. The `⋯` never flips: it is the constant home of every other way to create something, one shared menu body that groups the shared creation lists under Agents / Terminals / Projects, and it is the standalone terminal's home on every surface, cog submenu included. The verb is the corner's ONE filled control; the `⋯` stays outline, because a control that only reveals a menu is quieter than the act beside it (the same rule that keeps the Agents header's sort trigger quieter than its `+`), and the pair that used to break one-variant-per-cluster is gone with the split buttons. The collapsed rail mirrors the corner as bare icons and its verb icon never flips (a rail is too narrow to say what it flipped to). Sections carry their own creation buttons instead: the Agents header a new-agent `+` beside the sort control at one shared height token, the Terminals divider a standalone-terminal `+` as a SIBLING of its collapse toggle (never nested inside it), and the Inactive divider none, because there is no such thing as creating a dormant agent. The seed list for newly initialized repos is a compile-time constant extended via PR, a deliberate, documented exception to "all settings are configurable" (a config surface would invite unreviewable divergence in what dux writes into users' repos).
- **One menu definition drives both presentations.** `lib/appMenu.ts` is pure data; the desktop flyout and the mobile bottom sheet both render it and neither hand-authors items.
- **Dropping a file saves it and pastes its path; it never sends the file's bytes, and the upload route never writes to a terminal.** No agent CLI reads a file from its input stream, and injecting text server-side would bypass the input-ownership gate on the socket, so the browser pastes the returned path over its own already-gated connection. File names are validated, never rewritten; creation is symlink-refusing relative to a pinned directory handle; collisions get suffixed, never overwritten.
- **The drop destination follows the intent of the pane, and a picker invoked from a surface inherits that surface's intent.** A drop on an agent means "look at this": it lands in a hidden, self-gitignoring upload directory inside the worktree (so CLIs can read it and deletion is free; directory name and gitignore seeding are configurable). A drop on a terminal lands in the shell's live working directory, discovered from the process at drop time. A drop on the editor's file tree means "add this to my project": an ordinary visible file in the directory pointed at, never the upload directory, never a paste into a terminal. All three share the one upload route; the tree destination is stricter (it creates nothing and refuses symlinked components).
- **How the pasted path is quoted is a per-provider config setting with measured defaults, and the paste length limit is keyed by the command being run.** Receiving CLIs genuinely disagree about how they read a pasted path, so the form is config, not code; the length cap is a measurement of a third-party CLI, so it stays a compile-time table keyed by the command's file name, never the provider's free-text block name. A plain terminal always gets a quoted path, because a shell is the reason it must be quoted. What a running process launched with wins over config while it runs; each half reaches the browser on the event that can change it.
- **One toast per drop, with an explicit sticky decision per rung.** The outcome ladder is nothing-saved / saved-but-not-sent / refused / success; only the rungs where something may be lost are sticky (a saved file whose path exists nowhere else on screen, a cancelled paste whose text is now only on the clipboard).
- **Pasting an image, pasting text past the configurable size threshold into an agent pane, and picking a file from "Attach a file…" are the same journey entered by different gestures.** All three reuse the route, the form, the limit, the naming, and the one toast; the pure decision lives in `lib/clipboardPaste.ts`, reading the paste event (never the async clipboard API, which is blocked on the plain-HTTP origins dux routinely serves on). An image wins over text in the same event; a force-text chord bypasses both behaviors; long text pasted into a terminal stays verbatim at any length, because it may be a command or heredoc. The threshold counts code points and is conservative on purpose. The picker is the third gesture and adds no pipeline of its own: one shared helper owns the hidden input and guards re-picks and user activation, and the row-menu entry points borrow a mounted OWNER pane's capability rather than opening a side channel. Ownership and socket state are rechecked immediately before each paste, and the toast must say where the path actually landed (sent to the agent versus joined a compose draft). Web-only: a real terminal emulator already types a dropped path for you.
- **In-browser file editing is web-only, and the TUI gets no counterpart.** The editor exists for editing on the go; anyone at a terminal already has vim. The TUI's answer is open-worktree.
- **The editor is rooted at a tagged root, not at a session id, and a terminal's root is PINNED to where it was spawned.** An agent's root is its worktree; a project or standalone terminal's is the directory that terminal started in. Pinned rather than live, deliberately parting company with the file-drop tenet: a drop on a terminal pane follows the shell because that is where the user is typing, while an editor root backs a tree, a set of buffers, their drafts and a bookmarkable URL, and a `cd` would invalidate all four at once. A session-owned terminal has no root of its own and resolves to its AGENT's, decided in one place, so one worktree never sprouts a second, git-blind editor and the existing agent-terminal editor address keeps its meaning. Roots are namespaced keys (agent ids and terminal ids come from different counters), and the same tag drives the API namespace the server serves each root from and refuses every other id at.
- **An editor never outlives its target, and a terminal-rooted one has no diff mode and no changes broadcast.** A closed terminal takes its editor with it, out loud: the in-page overlay closes through the spine prune, and the standalone tab says what happened before landing somewhere real, holding open and asking first only when a buffer is dirty (the root that could have saved it is precisely what vanished, so that confirm is a sibling of the per-tab close confirm and never a variant of the reload one, which is disk-truth-shaped). Diff mode and the changed-files broadcast are ABSENT for a terminal root rather than disabled, because there is no HEAD behind the directory and no agent to name in a broadcast; freshness there rides the remaining two triggers, window focus and tab activation, and git decorations degrade through the answers `entry_info` already gives. Editing outside a worktree, home directories included, is a deliberate yes under the single-tenant trusted-access model: the browse and upload surfaces already reach the filesystem, so this extends degree, not kind.
- **A move is a modal, it is a rename on the wire, and an occupied destination is refused, atomically.** There is no separate move route (a second endpoint would let the containment guards drift) and no overwrite-with-confirmation, because there is no trash behind it; the refusal uses a no-replace rename, not a racy stat-then-rename. Moving a symlink moves the link (the entry, never the target); a destination reached through a symlinked directory is still refused. Destination browsing reuses the same lazy tree endpoint as the explorer.
- **The editor's info panel and the reload confirm are the two dialogs with a live truth to close themselves on.** The panel distinguishes "gone" (dismiss) from "refused" (stay and say why), stats the link itself rather than the target, and refreshes on exactly two events: opening, and the window regaining focus. There is no poll; a file deleted while the tab stays focused is not noticed, and that gap is accepted and stated. Git status has a variant per genuinely different answer, including ignored paths and nested repositories, because `git status` is silent rather than reassuring about both. The reload confirm's truth is "still worth asking": still dirty and still stale.
- **An open buffer is questioned by events, never by a poll, and a save carries proof of what it read.** dux has no file watcher and is not getting one: freshness rides the changed-files broadcast, the window's focus event, and tab activation (mount included, because a buffer can come back from the draft cache). Every trigger buys ONE metadata check and never a reload, because the user's own save and ordinary slice churn move the signal too. A clean buffer then reloads IN PLACE, keeping the component mounted so the model, its undo history and its cursor survive; a dirty one gets an in-pane banner, and only the destructive confirm behind it may discard what the user typed. The save sends the token the read handed out and the server refuses a mismatch; a refusal is a choice offered, not an error reported. Absent token means the old unconditional write, so every other writer is unaffected. The token is mtime plus size (one tick can hold two writes), and every mtime string in every payload comes from one shared formatter, or nothing ever matches.

### Serving Modes and Concurrent Serving

- **There are exactly three ways to serve, one process behind all of them.** `dux server` serves with no TUI in front of it and honors `[server] host` and `--bind`. The `start-web-server` flip hands a running TUI's terminal to the server and is UNCHANGED by any of this. `[server] serve_while_tui` keeps the TUI and serves in its background. The two in-app ways bind LOCAL MODE addresses only (loopback plus the Tailscale leg) and never read `host`, so neither can open a public listener. The flip and the background mode are alternatives rather than companions: starting the flip while the background server serves is refused out loud, with both ways forward named.
- **The TUI's run loop IS the web layer's engine servicer while serving, and a panic in either takes both down.** The engine is `!Send` and the TUI owns it, so the seam is a turn, not a share: a `dux-core` companion trait the TUI lends the engine to once per reaction (pre-consume, because `apply_reaction` takes it by value) and once per iteration. The TUI is the only `worker_rx` drainer, so every shared maintenance sweep has exactly one runner and its OUTCOMES cross the seam rather than being swept twice. A drained reaction's follow-up is routed by ORIGIN through one exhaustive core method, or a browser's action runs its arm on both surfaces. The accepted cost is written down in `background_serve.rs`; the poll interval caps while serving, because that interval is a browser's request latency.
- **The TUI is an ordinary participant in PTY ownership, never a privileged one.** While serving it holds a real connection id from the same process-global counter every browser socket draws from, and a fixed device label (`TUI_DEVICE_LABEL`) because it has no `User-Agent`. Only the card's button claims: a terminal the TUI does not drive, owned by another device OR by nobody, is covered by the web's card word for word (Active on X / Active on another device / Running in the background), and a press is the one act that claims it; typing under the card reaches nothing. The card is built from the modal primitives without being a modal (so pane and tab navigation keep working under it); the focus-agent binding and Space press its button on the focused pane, and the palette has no command for it. The other claiming act is a launch this surface started, so an agent created here is the TUI's with no card over it, while the startup auto-reopen sweep claims nothing and those agents wear Running in the background until pressed. Take-over works in both directions, sticky both ways: losing a pty never passively gives it back. Release is deliberate ends only, so stopping, flipping and quitting release, and merely deselecting an agent does not. A granted TUI resize joins the one apply order every web resize goes through. Toggle the mode off and none of this machinery exists: no seat, no registry, no gate, and the TUI types exactly as it did before any of it was written.
- **`[server] tailscale` is a tri-state and it applies to all three modes.** `auto` (the default) watches the interface and brings the leg up and down as a laptop roams, `yes` binds it and then stops looking, `no` never looks. A best-effort leg's death is isolated from its siblings; a required leg's is fatal to the serve. The watcher runs on its own thread with a bounded probe, because the wedged-daemon case is exactly the one it exists for. `serve_while_tui` and `tailscale` are the live switches; host, port and the caps still need a restart.
- **One seam changes the Tailscale mode while dux serves, and only the serve loop may act on it.** A mode change is an act (stop a watcher, drop a listener, run a bounded detection), so every surface asks the same `TailscaleModeControl` and the loop answers EVERY request, a superseded one included. The steps are a pure planner, the detection is its own select arm (never awaited inside a mode arm, or a teardown waits out a probe), each watcher carries a generation so one parked mid-probe cannot re-bind a leg the change just let go, and the Host guard's tailnet-literal rule moves with the mode instead of being fixed at bind time. `auto` probes immediately rather than after the first watch period, because the gesture needs a visible outcome. `--no-tailscale` refuses a live change for its whole run and the config value still saves. There is exactly ONE reload owner per serving mode: the engine actor's reload arm for `dux server` and the flip, the terminal UI's `apply_reloaded_config` for the background mode.
- **Serving is visible on the terminal UI, and the indicators are honest about what they count.** The header carries a serving crumb whenever a listener is up, count or not, because being the standing "you are running a listener" signal is its first job; it lives outside the header's selection arms, since a listener is a fact about the process. The word is "connections", not "devices": the count is Events sockets, one per browser tab, so one laptop with two tabs is two and nothing on this side can honestly say otherwise. Each agent row's line two carries a quiet remote-viewer count in the MUTED tone (the standalone identity tone means something else), summed over every PTY the agent owns (its provider tabs AND its companion terminals, whose rows carry no count of their own) the way its liveness ORs over tabs, and the center pane's caption says the same for the tab it shows. It counts open sockets, the driver's included, so the honest word is "remote", never "watching". Every count is structurally zero when nothing is serving.
- **One driver at a time, and the model spans surfaces rather than living in one.** The ownership registry is in `dux-core` so both surfaces ask it the same questions; a watcher on either surface still gets live output, scrolling and copying. Every refusal names the device that is driving, or says plainly that nobody is, and every write goes through the gate, macros included: a refusal must never report that it sent something.

### Agents and Providers

- **A provider is supported if and only if it supports PTY mode.** dux embeds the CLI's interactive session in a pseudo-terminal; that is the only thing a provider has to support.
- **Any CLI tool can be a provider.** Configure `command` in `config.toml` and dux spawns it. No adapters, no protocol layer. Adding a new provider is a config-only change, not a code change.
- **Claude, Codex, OpenCode, and Copilot are the defaults.**
- **No protocol layer.** No JSON-RPC, no custom message format, no adapter binaries. The CLI runs exactly as it would in a normal terminal.

### Standalone Agents

- **An agent's home is one of exactly two things: a managed working copy, or the user's folder.** The record carries a single workspace value with all the git fields inside the managed one; faking them with empty strings for a folder is a lie some screen eventually believes. Every risky question (where does this run, may the branch features run here, what may deletion remove, which project owns it) is answered by a named method whose body is an EXHAUSTIVE match, never a `matches!` at the call site. This is the same discipline `TerminalOwner` already enforces, extended to agents, and the browser mirrors it with one matcher module whose switches end in `assertNever`.
- **dux never creates, moves or removes a standalone agent's folder.** Deleting the agent removes dux's own record and nothing else; the delete dialog loses the removal checkbox entirely, because the removal payload is workspace-typed and a folder cannot produce one. A worktree-removing delete on a standalone id is REFUSED out loud, never silently downgraded. Factory reset skips it, and the worktree manager sees it occupying its directory (canonical paths) so it cannot delete the ground out from under it. The hidden upload directory inside the folder outlives the agent by design, and the docs say that cost out loud.
- **A standalone agent is project-less structurally, not by convention.** The association lives inside the managed workspace, so a project-less agent cannot be bucketed under one: the sidebar mints no orphan group for it, per-agent logs cannot collapse into a shared directory, and a project removal cannot cascade into it (every statement of the SQLite cascade scopes on the kind column AS WELL AS the project id: a standalone row stores empty text there, so a project whose id is empty would otherwise sweep up every standalone agent the user has).
- **The branch-identity features never exist for it; the changes panel is folder-driven.** Push, pull, fork, pull requests, provenance and the worktree manager are about a branch dux manages; the startup-command and environment entries are PROJECT scoped, which it also has none of; and its name is a label rather than a refname, so neither creation nor rename applies the ref validator to it. All of them are ABSENT rather than disabled, because a disabled row promises a thing that will never arrive. The changes panel instead asks the FOLDER: it works when the folder is itself the repository's top level (canonical paths, so a symlink cannot fake it) and is quiet otherwise, with a sentence per genuinely different quiet. A folder inside somebody else's repository is the hazard this exactness exists for: git walks up, so it would stage and commit to the parent.
- **The capability is enforced on the server, not hidden in the client.** Every git action resolves the agent's workspace through one engine chokepoint that refuses with a purposeful sentence, because each of those actions is also an HTTP route and a palette command. An unclassified folder fails CLOSED for mutations: writing into the user's directory on a guess is the one direction dux cannot undo.
- **Nothing polls a plain folder.** Every background enumerator (branch sync, pull-request sync and its one-shot, the refs watcher, the changed-files watcher and the web's changes service) consults the workspace before enrolling. The old error path reported "the repository is busy" once per poll cycle about a folder that simply has no repository.
- **It gets the global environment with no project overlay, and no startup command.** Named and tested rather than inherited: every project-lookup path falls through to an EMPTY environment for a project-less agent, which is a different and much worse thing. A startup command is worktree provisioning, so there is none to run.
- **One standalone agent per folder, refused at creation on canonical paths.** Coding CLIs resume their conversation history per directory, so a second agent there would silently resume the first one's conversation. The refusal is a signpost, not a wall: it recommends adding the folder as a project, which is the multi-agent shape dux is built for and brings tabs along.
- **Its display name is never empty.** Every row label falls back through the branch name, which does not exist here, so creation resolves a name (a typed one, or the folder's own) and the model's one display rule is what both surfaces read. A typed name is used verbatim: no branch is created, so the ref-name validator deliberately does not apply.
- **What dux writes into the folder fails CLOSED on an unknown answer, and "not looked yet" is not an accusation.** The upload directory's self-gitignoring seed is written only where git can actually see the path, so an unclassified folder gets nothing rather than junk; every mutation is refused for the same reason. The unprobed state is its own verdict rather than a second meaning for "git could not be consulted": they gate identically, but a freshly created agent in a healthy repository passes through it, and telling that user to check whether git is installed is a lie about their machine. The probe is bounded to one in flight per agent, because every question about the folder asks for a refresh and the web's changes poller asks every couple of seconds.
- **A workspace kind this build has never heard of degrades once, at ingestion.** Both sides fail toward MANAGED: an unknown kind read as a folder would hand a directory dux may in fact own to the rules that say it is the user's. The browser's matcher keeps throwing on an unknown kind (that throw is what makes a missing case a compile error) but can no longer see one, because the one normalization point rewrites it first; leaving it to the matcher meant a newer server unmounted the React root.
- **It lives among ordinary agents on both surfaces, told apart by its folder.** No section of its own, no badge: the row's second line names the folder where a project would go, through the same tag idiom, distinguished by a glyph rather than a badge (both surfaces draw the literal `✷` star, the web as a text glyph on the `↳` arrow's own idiom with an aria-hidden glyph and an sr-only "standalone" word so a screen reader speaks the meaning rather than a Unicode name, because "this one lives in your folder, not a dux-managed working copy" is the same fact on both and neither surface's return arrow or folder icon said it: the glyph and the folder label wear a quiet identity tone, the TUI's dedicated standalone-location theme color and the web's dedicated `--dux-standalone` token minted on the typing-token precedent, identity and never state, so line one's animation-not-color rule stands untouched; the TUI star's one-cell width is pinned by a test against the row layout's own width machinery). The star is ONE indicator learned once: a standalone terminal's row wears the same star over its spawn directory, while session- and project-owned terminal rows keep the `↳` arrow, which there means "owned by". The header carries the folder chip, on the phone lane too a standalone terminal already has; the info panel and the vitals tooltip name the folder and drop the branch rows. The folder joins the search haystack, so typing part of a path finds the agent.

### Agent Tabs

- **A tab is a provider session inside the agent's one shared worktree, not a new worktree.** One agent session (one branch, one sidebar row) hosts N provider tabs; every tab edits the same files. The strip carries provider tabs only (companion terminals never fold into it), renders only when there are two or more tabs unless the user has asked to always see it, and tabs are never separate sidebar agents.
- **Every tab is a row with a stable id of its own, the agent's first tab included.** No tab is privileged, none is synthesized, and none is inferred: not from a position in the strip, not from a missing row, and never from a tab id that happens to look like a session id. A tab's id is the key its process, its address, its attention state and its connections all hang on, and it never changes for the life of the tab.
- **The session names its first tab through a pointer, and that pointer is the only slot oracle.** Every "is this the first tab" question, on either surface, resolves the session's pointer through the shared resolvers; no call site compares a tab id against a session id. Session ids and tab ids are distinct types at the slot-sensitive seams, so handing one where the other belongs is a compile error rather than a hunt, and the one place that reinterprets a session id as a tab id is the deliberate placeholder for "the first tab, whichever it is" in the layers that hold ids and no session record.
- **Closing the first tab hands the slot to the next tab in strip order; closing the last remaining tab is refused.** Promotion is one persisted step: the pointer moves, the provider mirror moves with it, and nothing else is re-keyed, so the promoted tab keeps its process, its connections, its address and its attention state and nothing remounts. An agent always has a first tab, so its only tab cannot be closed at all, in one refusal both surfaces say in the same words; stopping everything the agent runs is the distinct detach action.
- **Resume is decided dynamically by liveness, per provider, in exactly one place.** A launching tab resumes the provider's prior conversation only when it is the sole live-or-launching tab of that provider in the session, because a provider's conversation history is directory-scoped and per-provider. The decision lives in `Engine::tab_resume_decision` and every launch and reopen path routes through it; do not reintroduce a positional or first-tab notion of resume.
- **Closing a tab ends that tab; a clean exit ends it by itself.** Closing a tab deletes its row (destructive, so confirm it); a clean exit closes the tab with no confirm, because nothing is lost (conversation history lives in the worktree). A non-zero exit keeps the dormant tab as the crash-diagnosis surface. A tab exiting while siblings live shows a quiet tab-scoped message, never the workspace-wide agent-exited warning, which fires only when the last live tab exits.
- **Restart brings tabs back dormant, not running, and what launches one is decided by the tab, never by focus.** Each tab reopens as a pill with no process. An extra tab waits for an explicit action on both surfaces, and so does any tab whose LAST RUN ENDED BADLY (a launch that failed, an exit that was non-zero), because a tab that cannot come up would otherwise relaunch every time the user looks at it with no way out. In the TUI that is the whole rule: focus alone never launches. On the web, selecting an agent starts its healthy dormant FIRST tab, because selecting an agent is asking for the agent and that tab coming up is the same gesture rather than a second one; the web's dormant card must render without opening the PTY socket, because subscribing is what force-launches. The failure gate is enforced on the SERVER rather than trusted to a client, so no surface can forget it and no client can talk its way past it. The verdict is memory-only, so a restart, a deliberate stop and a successful run each clear it. The launch's resume eligibility follows the same dynamic rule as any other launch.
- **Tab state is derived runtime state: SQLite, never config.** Creating an agent writes the session, its first tab and the pointer in one transaction, so a rowless tab never exists even for an instant. A pointer that names no usable tab is healed loudly at startup rather than papered over, and a migration that cannot complete stops startup rather than opening a half-migrated workspace. `agent_sessions.provider` is a mirror of the slot tab's provider with a single write site, so a retarget or a promotion cannot leave the two disagreeing.
- **Runtime provider state is keyed by tab id, the first tab's included.** Sidebar liveness ORs across all of an agent's tabs, and so does its attention; session-level running state and auto-reopen intent stay agent-level and move only with the slot tab.
- **The strip renders extras in creation order and a promotion never reorders the survivors.** Promotion removes the head; everything behind it stays exactly where the user has been looking at it. Tabs never reorder for any other reason.
- **Tabs honor each surface's existing UI tenets.** TUI: themed through `theme.rs`, switch keys work in non-interactive mode only, the strip is not rendered in fullscreen, and the pill carries the same activity glyphs the agent list does (the spinner while working, the blinking attention dot when it needs you, obeying the same `attention_indicator` setting) while the active tab is its highlight alone. Web: deep-linkable pills reusing the shared menu, confirm, touch-target, and working-bob tenets. New tabs default to the project provider and start fresh; provider is per-tab, retargeted for the next launch; a configurable per-agent cap applies, counting every tab once.

### Terminals

- **A terminal is owned by exactly one owner: an agent session, a project, or nothing at all.** Session-owned terminals spawn in the agent's worktree, project terminals at the repo root, standalone terminals in the user's home directory. Ownership never changes after spawn. Standalone is a real variant, not an option or sentinel, and every ownership question is answered by an exhaustive method on the owner type (both in Rust and in the web's owner helpers), so a fourth kind is a compile error everywhere it must be answered for.
- **A standalone terminal opens in the home directory, falling back to `/`.** What is resolved is a usable directory, not merely a path, because the value goes straight to the spawn; an unusable or unresolvable home takes the fallback rather than refusing. Never retry a failed spawn at `/`: a missing shell is a configuration problem the user must see. It gets the global environment with no project overlay, is addressable at un-nested routes (which serve standalone terminals only), and is named a "standalone terminal" wherever it must be named; its row names its spawn directory (home-collapsed), which travels on the wire because the browser may not be on the server's machine.
- **Terminals are runtime-only.** No SQLite row, no config entry, no restore across restarts. Existence equals a running PTY.
- **Project and standalone terminals do not run the project's `startup_command`.** That command is a worktree provisioning step for new agents; a terminal is a plain shell.
- **Removing a project closes its project terminals; deleting an agent closes that agent's; nothing closes a standalone terminal automatically.** The last is a decision, not an oversight, and is documented beside both close paths so nobody later "fixes" the omission. Detaching an agent leaves its terminals running.
- **A terminal row is an agent row.** It renders through the same shared row component and idiom on both surfaces (the framed two-line row, the same selection painting), never through a lesser single-line item. The row contract is two lines of `[glyph] [left text that ellipsizes] … [right text that survives]`; when the agent row's framing changes, the terminal row moves with it because they share the code.
- **A terminal has three states only: idle, running, typing.** Never detached or needs-attention (a live PTY is alive or gone). Priority mirrors the agent row; the busy word is "Running" rather than "Working" on purpose. A terminal is busy when it is streaming output or a foreground app is running in it, even while quiet; the predicate lives once in the engine so both surfaces agree.
- **Typing is a real keystroke; a forwarded pointer report is neither typing nor evidence of work.** One classifier in core sorts every PTY write into typing, pointer, or ignored, and both surfaces route through it. A pointer report makes mouse-tracking children repaint, so while the pointer window is fresh the engine stops inferring "working" from output text and defers to the agent's own progress reports; the suppression window is per gesture (longer for wheel, short for click, none for motion). Only the streaming inference is suppressed, never the foreground-app fact.
- **State colors are theme-derived, and Idle is the only unstyled state word.** Busy is green, typing violet, detached amber, needs-you cyan, on both surfaces through semantic tokens. Line one (glyph plus name) carries no live-state color: the operating cue is animation (spinner plus name shimmer), not color, and the animation cadence is paid only while something animates.
- **Every sidebar element carries a position; both surfaces sort terminals by the active sort mode.** Terminals get a runtime-only sort order and their own reorder command; the sort comparators are duplicated per surface and must stay in lockstep. The web's Terminals section is a collapsible divider defaulting open (a live terminal is worth surfacing, unlike dormant agents).

### Git and Data Safety

- **Worktrees are user data.** Never removed or mutated casually. Deletion requires explicit user confirmation.
- **Git operations are conservative.** Source checkout refresh uses `--ff-only`. Destructive operations require confirmation.
- **Commit messages are plain sentences.** No conventional-commit prefixes, no structured trailers unless the user explicitly asks.
- **Prefer explicit failure over silent waiting.** If something fails, say so immediately with context.
- **A refname is a positional, so every git call that takes one needs `--`.** A dash-leading branch name in a positional slot is read as an option, git obeys it and exits 0, and dux reports success for the wrong operation. Such names really do reach dux (plumbing creates them, and non-leading components may lead with a dash). Two measured exceptions where `--` is not enough, because a porcelain command consumes the separator and forwards the positional to an inner command without one: `git worktree add` (resolve the start point to an object id first) and `git pull` (pass a fully qualified `refs/heads/` refspec, which cannot lead with a dash). When a separator does not visibly work, measure what the subcommand does rather than assuming; every case gets a test in the existing option-looking-name family in `git.rs`.
- **dux deletes only the branches dux created, unless a dialog asked and the user answered otherwise.** An agent records at creation whether its branch was minted by dux, attached to one that already existed, or adopted with an existing worktree. That provenance is the whole answer for every caller with no dialog in front of it (the project cascade, the create rollback, factory reset), which is what keeps a project removal from taking a user's `develop` with it. The agent-delete dialogs on both surfaces carry an explicit "also delete the branch" box whose answer travels with the request and wins in both directions: ticked by default for a branch dux created, unticked with a warning naming the risk (and its unpushed-commit count, computed in a background worker) for one that predates the agent. An absent answer is not "keep it", it is "nobody was asked", and the provenance decides. The box is offered only where the worktree is going, because git will not delete a branch that is still checked out; a standalone agent has no branch and gets no box. The worktree manager keeps its own checkbox for a worktree no agent holds.
- **Every file dux keeps for itself is owner-only, and the config root's own mode is what actually enforces it.** Per-file modes are defence in depth; the directory is the boundary, because SQLite creates its sidecars with modes dux cannot choose. The one place that decides any of this is `crates/dux-core/src/file_modes.rs`; never chmod at a call site. Tightening only clears group/other bits (idempotent, safe every startup), is best-effort (a mode dux cannot set is a warning, never a reason to stop logging or refuse to start, and best-effort error paths get tests), and never follows a symlink. dux does not tighten the user's own data (worktrees, the lock, user-created theme directories); a change that starts must be argued for. Note that "a read-only config stays read-only" is a claim about the tightening pass only: the atomic config write replaces the file and resets its mode, and both user-facing surfaces say so.

### Tone

- **Welcome tips are playful and sassy.** They should feel fun, not like a manual. Lead with surprise or delight, highlight non-obvious features that differentiate dux, and keep keybinding references secondary to the feature discovery. Avoid dry "press X to do Y" phrasing.

### Quality

- **Prove your work with tests.** Every change should include unit tests. When feasible and low-lift, add integration tests as well.
- When debugging a problem, before fixing it, **aim to prove your findings with a unit test**.

## Project Summary

`dux` is a Rust terminal UI for orchestrating AI coding sessions per git worktree.

The current app provides:

- A left pane for projects and agent sessions
- A center pane showing the agent's terminal output (embedded via PTY) or diff viewing
- A right pane for changed files and diffs
- Commented user config in the platform-specific dux config directory (`~/.dux/` on macOS, `~/.config/dux/` on Linux)
- Session persistence in `sessions.sqlite3` alongside the config
- Logging in `dux.log` alongside the config
- PTY-based agent startup: spawns CLI tools (`claude`, `codex`, `opencode`, `copilot`) directly in a pseudo-terminal

## Important Constraints

- The app spawns CLI tools directly via PTY (portable-pty) and renders their output using an embedded terminal emulator built on alacritty_terminal. There is no protocol layer (no ACP, no JSON-RPC).
- Long-running actions should not block the UI thread.
- All periodic or potentially-blocking work (git commands, file I/O, network) must run in background workers, never on the main UI thread. Even fast operations like `git symbolic-ref` should use workers to prevent UI freezes if the filesystem or git lock stalls.
- Async operations must keep the status line updated for the full operation lifecycle: set a Busy message when the worker starts, then replace it with a clear success or failure message when the worker completes. Do not start background work silently.
- User state lives under `~/.dux/` on macOS and `$XDG_CONFIG_HOME/dux/` (or `~/.config/dux/`) on Linux.
- **The web server (server mode) is single-tenant / trusted-access by design.** There is no login. The server binds loopback by default and optionally a Tailscale address; access control is delegated to loopback scope, Tailscale ACLs, or an upstream proxy. A Host-header allowlist and same-origin check guard against DNS rebinding and cross-site requests. Every client shares one workspace: it can drive any PTY, browse the server's filesystem, and see every session. This is intentional for a per-developer or trusted-team tool. Do not add features that assume mutually-distrusting web users without first designing a real per-user isolation model.
- Worktrees are user data and should not be removed or mutated casually.
- Git operations should be explicit and conservative, especially around the source checkout.
- **Target platforms are macOS and Linux only.** Windows users run dux through WSL2, which is Linux. Do not add `#[cfg(windows)]` branches, `cfg!(windows)` checks, or Windows-specific code paths. Assume Unix throughout.

## App Module Structure

The `crates/dux-tui/src/app/` directory splits the TUI into focused submodules. Each file contains an `impl App` block for a specific concern:

- **`mod.rs`**: `App` struct, types, enums, bootstrap, run loop, and state helpers. Read this first to understand the data model.
- **`input.rs`**: All keyboard/mouse event handling (`handle_key`, `handle_left_key`, etc.).
- **`render.rs`**: All rendering methods (`render`, `render_header`, `render_left`, etc.) and UI helper functions.
- **`sessions.rs`**: Project and session CRUD (create agent, delete, reconnect, refresh, project browser).
- **`workers.rs`**: Background thread management (`drain_events`, `spawn_*`, `run_create_agent_job`).

When making changes, edit only the relevant submodule. If you need to add a new method to `App`, place it in the submodule that matches its concern. If adding a new type or enum, add it to `mod.rs`.

## Recommendations For Future Changes

- Keep the status line centralized. New async operations should report progress through the shared status API, not ad hoc strings.
- The core keyed status controller (`dux_core::statusline`) is the single source of truth for engine status across the TUI and the web. The TUI renders it as a single most-recent-wins status line; the web renders it as toasts, one per open keyed status. Correlation is by per-operation key: a Busy and its eventual final carry the same key so the surfaces replace or dismiss the right entry. Every Busy must be followed by a final; a keyed Busy left open expires to a warning, but only once nothing is left running behind it. The timeout is a guess about silence, and the controller no longer has to guess: liveness is recorded rather than inferred, in ONE set of keys the engine and the controller share. Every path that emits a keyed busy registers its key, the controller retires it at the one place a final of any origin lands, and a registered key is re-sent as a busy instead of being called timed out. Do not answer liveness by enumerating op registries; several keyed busies have no registry at all. A slow clone therefore keeps its spinner for as long as it takes, a spinner never leaves a screen without something saying why, and a leak in the set is bounded by an absolute ceiling past which a busy is upgraded whatever liveness claims. Under Retain, Info clears after the window, a Warning after three windows, an Error only when replaced; the web's toast windows follow the same factor, and a warning that is still true after three windows is pinned rather than exempted by tone. Do not add a third surface, and do not emit an unkeyed Busy for a multi-step web operation.
- The controller has two retention policies, chosen at construction, because the surfaces ask different questions: the TUI retains statuses for its single line, while the web emits finals as events, retaining them only for a short fixed replay window so a reconnecting client still learns the outcome without every new page load replaying hours-old errors. The window is deliberately a constant, not the user's clear-seconds setting: how long a status stays replayable and how long a toast stays on screen are different questions. The doc comments on the controller carry the full reasoning.
- Status line messages must be verbose and actionable. Do not write terse messages like "Done." or "Pushed."; explain what happened and, when relevant, what the user can do next.
- Code must be production ready and modular to allow future Open Source contributors to integrate new features with ease. Do not take shortcuts.
- Route new modal UI through `PromptState` so `Esc` keeps working uniformly.
- Prefer command-palette actions over adding many more global hotkeys. This is per surface: in the TUI that means the `Ctrl-p` palette; the web has no palette, and its equivalent home is the cog app menu, which deliberately has no keybinding of its own. Do not add a global web hotkey to reach a menu action; add the action to the menu.
- Keybinding labels shown to the user should use proper casing (e.g. `Ctrl-g`, not `ctrl-g` or `CTRL-G`). The `^X` notation is acceptable in footer hint bars since its meaning is explained in the help overlay.
- Keybinding parsing from config is case-insensitive for modifiers and control keys; letter keys are lowercased during parsing, so binding uppercase requires an explicit `shift-` prefix.
- Never hardcode keybinding labels in user-facing strings. All keybindings are user-configurable; always look up the actual binding via `RuntimeBindings::label_for()` so labels stay accurate after rebinding. The only exceptions are pure text-input contexts and palette-only command names.
- Keep agent creation and other blocking git/provider work in background workers.
- The PTY approach is CLI-agnostic: any terminal command can be used as a provider. Keep it generic.

## Keeping Documentation In Sync

- When adding, removing, or changing keybindings, update `README.md` if it documents controls or shortcuts.
- **The TUI has a command palette; the web has an app menu. Never conflate them in docs or UI copy.** The TUI palette opens with a rebindable key; the web menu is a button, reachable by Tab, with no keyboard shortcut. When docs must name a key, scope the sentence explicitly to a surface. Never suggest `ctrl-k` as a TUI rebind example (terminals commonly treat it as readline's kill-line).
- **The two surfaces are independent, so keep them in step by hand.** `dux_core::palette` is the source of truth for the TUI palette only; the web app menu is defined client-side in `lib/appMenu.ts`. When you add a palette command, decide explicitly whether it warrants a web app-menu entry, and say so in the PR: a global, parameter-free command usually does; a per-entity one usually belongs in the web's row menu instead. Nothing fails if you skip this, which is exactly why it must be a deliberate step.
- When changing features, pane layouts, config paths, or provider behavior, verify that `README.md` still accurately describes the application.
- The README intentionally omits a full keybinding reference. The in-app `?` overlay is the authoritative reference; documenting how to configure keybindings is fine, enumerating them is not.
- The marketing/documentation site lives in `website/` and is published to `getdux.app`. When a change affects anything the site describes or shows, update `website/` in the same change. Match the site's playful tone, avoid counting features in headings, avoid enumerating keybindings, and make sure copy referencing real values reflects what the app actually does.
- No half-width prose unless something sits in the other half: a width-capped section intro with nothing beside it is a column of text and a hole. If a full line reads too long, shorten the copy or add a real second column.
- In `.astro` templates, write the space between a closing inline tag and adjacent text explicitly as `{" "}`; Astro eats the line break after a closing inline tag and welds the words together, the build succeeds, and nothing warns you. There is deliberately no automated check (the checkable half produced mostly false positives); catch it by writing it correctly and looking at the rendered page.
- **The docs are consumer docs, never coding internals.** A page describes what a user of dux sees, configures, and does. HTTP routes, sockets and wire frames, engine and worker mechanics, storage layout beyond "your state lives here", and design rationale are not consumer facts and stay out, however true; state the observable behavior instead (the API is not a supported surface today). Every setting, default, limit, command, refusal, platform caveat and data-loss warning is a consumer fact and stays. Box what a skimmer must not miss as an admonition (WARNING/CAUTION for security and loss, IMPORTANT for must-know behavior, TIP for a better way, NOTE for asides); a plain paragraph in a box is noise.
- The docs section at `getdux.app/docs` is generated from plain Markdown in `website/docs/`; add a `.md` file with `title`, `description`, `group`, and `order` frontmatter and everything else is derived. When a feature change touches anything a docs page explains, update the Markdown in the same change.

## Recommendations For Debugging

- First check the `dux.log` file in the dux config directory (`~/.dux/` on macOS, `~/.config/dux/` on Linux).
- Confirm whether the provider command in `config.toml` is installed and on PATH.
- If agent creation fails, determine whether it stopped in:
  - worktree creation
  - PTY spawn (command not found)
  - PTY process early exit
- If the UI appears frozen, verify the operation is on a worker path rather than the main event loop.

## Git Command Safety

When shelling out to git, **always ensure the command output is immune to user-specific git configuration**. User settings like `color.diff`, `diff.noprefix`, `status.branch`, `status.renames`, `core.quotePath`, and others can alter output in ways that break parsing.

- **Prefer plumbing commands** (`cat-file`, `rev-parse`, `for-each-ref`) over porcelain when you need machine-readable output. Plumbing commands are guaranteed stable.
- **Use `--porcelain`** for `git status`. Never use `--short`; it is affected by user config.
- **Prefer `--porcelain=v1 -z` when parsing status paths.** Parse NUL-delimited records so spaces, quotes, Unicode, and embedded newlines in paths are handled safely.
- **Use `--numstat`** for line-level diff statistics; prefer `--numstat -z` when parsing file paths from diff stats, especially rename and copy records.
- **Override config with `-c`** when a porcelain/plumbing alternative doesn't exist (e.g., `git -c color.diff=false diff`).
- **Imperative commands** that aren't parsed (`worktree add`, `branch -D`, `pull`) are fine as-is; rely on exit status rather than parsing their stdout.
- **Do not parse human-facing commands like `git branch --show-current` when a plumbing-style alternative exists.** Prefer `symbolic-ref --quiet --short HEAD` or `rev-parse`.
- **Avoid shelling out to `git diff` for display**; the project computes diffs in-process using the `similar` crate and applies syntax highlighting with `syntect`. Use `git::file_at_head()` for the base version and read the working copy from disk.

## Recommendations For Editing

- Follow the existing `crates/dux-tui/src/app/` submodule pattern when adding new concerns. If a new feature area grows beyond ~200 lines, extract it into its own submodule with `use super::*;` and an `impl App` block.
- Keep changes scoped to one submodule at a time; avoid cross-cutting edits across multiple app submodules in the same PR when possible.
- Use `theme.rs` constants for all colors and styles; never use raw `Color::*` values in rendering code. `theme.rs` is the single source of truth for visual styling.
- The canonical config renderer produces a fully commented config on first creation. Subsequent saves preserve user edits via `toml_edit`. Users can run `dux config diff` to see what changed or `dux config regenerate` to get the latest canonical template.
- **`dux config diff` is derived from the config structure; adding a setting requires nothing of you.** It compares the parsed file against the defaults structurally, so new keys are reported automatically; sensitive subtrees (env, projects) are summarized so tokens and local paths never reach the output, and there is deliberately no "ignore" policy. An exhaustiveness test mutates every leaf of the default config and asserts each is reported; do not weaken it. The `--raw` form prints the whole config, `[env]` values included: the plain summary is safe to paste into a bug report and `--raw` is not, and docs must say so.
- When a setting can have a sensible default at first boot, resolve and store the concrete value in `config.toml` right away; users should see a working value they can edit, not a placeholder.
- Preserve safe failure behavior around project refresh and failed agent startup.
- **Never use byte-based `.len()` or `[..n]` slicing to truncate user-visible strings.** Terminal output, paths, and UI text contain multi-byte UTF-8; byte slicing panics inside a multi-byte character. Use char-based counting and truncation.

## Verification

Use:

```bash
cargo fmt
cargo clippy --all-targets --all-features -- -D warnings
cargo test
```

`cargo clippy --all-targets --all-features -- -D warnings` is a CI gate; the same command runs on every pull request and fails it on any warning. Run it locally before committing. When a new stable Rust release enables lints that previously passed, fix the code rather than suppressing the lint unless there is a specific, documented reason.

For interactive smoke testing, ask the user to run `cargo run` as a final sanity check rather than running it automatically.

**Seeing the web UI: use the preview container at `tools/preview-env/`, never a directly-run dux.** It runs the host-built binary in an isolated Docker container with its own config, a loopback-only port, and a fake streaming provider, and screenshots via its scripts (see its README). Never run `dux server` or the TUI directly on the host to inspect UI work, and never kill dux processes on the host: a directly-run instance shares the developer's real config directory with their own live dux, so a stray instance corrupts shared state and a killed process can destroy the user's active session.

**The web UI is compiled into the binary, and a failed frontend build is a hard build failure.** The build script deliberately writes no placeholder and falls back to nothing, so a broken frontend cannot ship quietly. The escape hatch for Rust-only work is `DUX_DISABLE_UI_BUILD`, which skips the build rather than tolerating a failure; CI fails fast if it is set, and the release workflow smoke-tests the packaged archive. Contributor-facing detail lives in `CONTRIBUTING.md`.
