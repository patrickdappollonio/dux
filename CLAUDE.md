# CLAUDE.md

## Design Tenets

Principles that guide every decision in dux. If a change conflicts with a tenet, the tenet wins.

### Configuration

- **All settings are configurable.** Every single one. If a user can't change it, it shouldn't be hardcoded.
- **The config file is the documentation.** It must clearly explain what each setting does through inline comments. A user should never need to leave the config file to understand an option.
- **Project config is portable desired state, not runtime cache.** `[[projects]]` may store portable user intent such as `id`, env-expanded `path`, `name`, `default_provider`, `auto_reopen_agents`, and `startup_command`. Do not write runtime-derived git or agent state into config.
- **Keep derived project state in SQLite.** Values such as `leading_branch`, `current_branch`, branch status, agent worktree paths, agent branch names, and provider process/session state belong in SQLite/runtime memory only. In particular, `leading_branch` may be parsed from older config files to repair SQLite, but saved/generated config must omit it so autodetection is not pinned into portable config.
- **Startup command execution shell is global config, not project state.** Project config owns the command text; `[startup_command_terminal]` owns the system-wide shell and args used to run it. Keep this out of SQLite and UI-only state so shell behavior stays portable and reviewable in config.
- **Config wins for explicit project preferences.** When a project exists in both config and SQLite, explicit config values for safe preference fields should update SQLite on startup/reload. SQLite may fill missing config fields, but should not override a value the user wrote in config. Reserve hard sync conflicts for project identity ambiguity: duplicate ids/paths, same id with different expanded paths, or same expanded path with different ids.

### UI and Navigation

- **New UI must use the theme engine.** Any new screen, pane, dialog, status text, or visual state must derive colors and styles from `Theme`/`theme.rs` rather than hardcoding visual values. Prefer reusing an existing semantic theme field when it already matches the visual meaning. Only add a new semantic theme field when the existing theme surface truly lacks the needed meaning, and when you do, wire every supported theme/default mapping through it in the same change so themes cannot drift.
- **Tab and Shift-Tab navigate between panes.** This is the primary spatial navigation model.
- **Panes have local key combinations.** A key combo bound in one pane does not necessarily work in another.
- **Panes have interactive and non-interactive modes.** In interactive mode, all key combos (including global ones) are suppressed and input is forwarded to the PTY. In non-interactive mode, both local and global key combos are active.
- **Key combinations are documented in the help page.** The in-app `?` overlay is the authoritative reference. External docs describe how to configure bindings, not enumerate them.
- **Line-scroll keys are gated by context.** In interactive (PTY) mode, arrow keys and Space only scroll when already scrolled back (`scrollback_offset > 0`); otherwise they pass through to the child process. In non-interactive views (diff overlay, non-interactive agent pane, help overlay), there is no competing use for these keys, so they scroll unconditionally. Page-scroll keys (`PgUp`/`PgDn`) always initiate scrolling regardless of context.
- **Space activates the focused button in confirmation dialogs.** Every modal that presents buttons (confirm/cancel, delete/cancel, etc.) must treat Space as equivalent to Enter — it executes whichever button is currently highlighted. This is hardcoded, not a configurable keybinding, because it is a universal accessibility convention. New dialogs with buttons must include this behavior.
- **Movement keys move focus; Space acts on what has focus.** Movement keys (the horizontal navigation keys, the arrows, Tab/Shift-Tab) only ever MOVE FOCUS between a modal's controls. They never change a value. Space acts on whichever control currently has focus: it toggles a checkbox, activates a button, and types a space when a text field has focus. It follows that any modal with more than one focusable control needs an explicit focus concept (a `…Focus` enum on its `PromptState`), and that the focused control must render as focused: focus you cannot see is not focus. Wiring a movement key straight to a value is the bug this rule exists to prevent — `RenameSession` had no focus concept, so its movement action was bound directly to the rename-branch checkbox and Tab flipped the box instead of highlighting it. Bindings are user-configurable, so never name specific keys for these roles in code, copy, or docs; resolve them through the bindings.
- **Every modal belongs to one of four families, and the registry makes you say which.** `crates/dux-tui/src/app/modal.rs` holds `modal_spec`, an EXHAUSTIVE match with no `_` arm assigning every `PromptState` variant a family. A new modal does not compile until you have chosen one on purpose. The families are derived from what a keystroke MEANS, not from how the modal looks:
  - **Report**, read-only and scrollable. Up/Down scroll the body. No focus concept, because there is nothing to focus. (Agent Info, Add-Project-Failed, First Load, Help.)
  - **Confirm**, prose, two buttons, sometimes a checkbox. The horizontal keys move FOCUS between those controls and change nothing; Space and Enter act on whichever control has it.
  - **Picker**, rows with a selection cursor and maybe a filter. Up/Down move the SELECTION, which is a value and not focus; Enter picks it. A picker confirms by PICKING and so needs no buttons: the three provider pickers had a Cancel/Apply pair and lost it, because the close key already cancelled and the confirm key already picked, and the buttons bought nothing but a focus concept, a Tab stop and three near-identical handlers (which are now a single `App::handle_provider_picker_key` selected by `input::provider_picker_kind`). The kill-running dialog is the one picker that keeps footer buttons, and it keeps them because they are DISTINCT ACTIONS rather than a confirm-and-cancel pair, which is stated at its render site. If you remove a picker's Apply button, check what else that button was saying: the provider one greyed out to mean "this row is already the active provider", and that cue had to move onto the row as a text marker rather than a style, because `Theme::selection_style` sets a background and bold that ratatui patches over the row's own style, so a dimmed row would lose the cue exactly when it is highlighted and being read.
  - **Form**, fields plus buttons. The horizontal keys belong to the CARET and must never reach the binding lookup (that is what `keybindings::text_field_owns_key` is for).
  `EditMacros` is deliberately state-dependent: one variant that is a Picker while its list is showing, a Form once an edit is open, and a Confirm while its nested delete-confirm is up. `modal_spec` answers as a function of the value, not the discriminant. And the registry's coverage is `PromptState` and nothing else: the commit-message pane and the startup-log viewer are not variants, so it cannot see them, which is stated in the module docs and must stay stated.
- **A modal with a full-text field must have a confirm button; a modal with only simple fields must not need one.** Think of it as the difference between an `<input>` and a `<textarea>` on a web form. In an `<input>`, Enter submits, and that is unambiguous, so the form needs no button to be operable. In a `<textarea>`, Enter is a newline, it is content, so the form has to carry a button, or there is no way left to say "done". dux's modals are the same: a modal holding a `TextInput::with_multiline` field gets a confirm button, and with one Enter has three unambiguous meanings depending on where focus is, ENGAGE the field while it is unengaged, insert a NEWLINE while it is engaged, and ACTIVATE the control when focus is on a button. A modal whose fields are all single-line needs no button, because Enter submits and nothing competes for it. The rule is enforced by `ModalSpec::satisfies_dual_mode_rule` and by fixtures that BUILD every variant and RENDER it, because "has a multiline field" is a runtime flag and "publishes a confirm button" is only knowable from `OverlayMouseLayout`. `KNOWN_DUAL_MODE_VIOLATIONS` is now EMPTY, and must stay that way: the three modals that broke the rule (startup-command, project-environment, global-environment) got their Cancel/Save pair in the same change that redefined their Enter to ENGAGE, because the moment Enter stops meaning submit a buttonless modal is a state the user cannot commit from. The list is still asserted as an EXACT set, so a new violator cannot appear without someone writing its name there and defending it in review. Be honest about what kind of rule this is: it is a design choice, not a logical necessity. dux's own commit-message pane is a dual-mode field with no confirm button whose Enter is perfectly unambiguous, because submit there is bound to a different key entirely. The rule is the house style for MODALS, where Enter is otherwise overloaded; it is not a claim that no other design can work.
- **A shared component probably already exists, ask before you invent one.** Before writing a new modal helper, look in `crates/dux-tui/src/app/components/` and `crates/dux-tui/src/app/modal.rs`, and if what you need is close to something there, ASK rather than adding a parallel implementation. Already extracted, and not to be re-hand-rolled: the frame/dim/rect chrome trio (`App::open_modal_frame`), the focus ring with conditional stops (`components::focus_ring::next_focus`), the key ladder and its text-field gate (`modal::modal_key_step`, `modal::binding_lookup_is_suppressed`), click routing to a control (`modal::click_target`), the footer built from action/description pairs (`components::hint_bar::modal_hint_line`), and the one shared `TextInput`. A second copy of any of these is the drift this section exists to prevent.
- **All text entry goes through the one shared `TextInput`.** `crates/dux-tui/src/app/text_input.rs` already owns caret motion, word motions, and multiline scrolling, and every prompt, filter, and search row holds one. Never hand-roll a buffer: a new typing surface gets a `TextInput` field, not a `String` you push characters onto.
- **There are two kinds of text field, and a real flag tells them apart.** `TextInput::with_multiline(n)` sets the optional `multiline` state; that flag is what makes a field full-text, not its height, its label, or the modal it sits in. Check the constructor to know which kind you are touching. Only a handful of fields are multiline (the commit message, the startup command, project and global env, the macro body); every other field is simple.
- **Simple (single-line) fields need no mode.** They are one stop in the focus order, typing is immediate, and the arrow keys must reach the caret. `keybindings::text_field_owns_key` is what guarantees it: while a text field has focus, plain characters and the horizontal arrows belong to the field and the binding lookup is skipped for them. The bug this prevents is real and was shipped. The selection-toggle action's default key set includes the horizontal arrows, so in the rename-agent and new-agent-name modals pressing left silently flipped the "also rename the git branch" checkbox instead of moving the caret, arming a branch rename the user never saw.
- **Full-text (multiline) fields need the engage step, and engaging is always an explicit act.** Editing one is a mode, tracked by `App::input_target`. While NOT engaged the field owns no keys at all: the modal owns them, the movement keys move focus across its stops, and a plain character is dropped rather than typed. In a MODAL there are exactly three ways in, and every modal full-text field offers all three: the CONFIRM key while focus is on the field, the `EngageCommitInput` binding (whose default is the vim-style `i`, so resolving it through the bindings gives the vim key and still honours a rebind, never hardcode the letter), and a DOUBLE CLICK on the field. (The commit-message pane is not a modal and predates this: it engages through `EngageCommitInput`, through the files pane's own open action, and through a click on an already-selected commit section. Leave it alone unless you are deliberately unifying it.) Typing does not engage: the older auto-engage-on-first-printable-key behaviour was removed, because once a modal carries buttons a stray keystroke landing in the body is a surprise, not a convenience. While engaged every key goes to the text, and the exit-edit binding leaves edit mode and leaves the modal OPEN. Never let it close the modal, and never let it save.
- **An unengaged field must LOOK unengaged and must SAY how to start.** Focus and engagement are two different things, so they render as two different things: a focused-but-unengaged field gets the focus border and NO caret (a caret on a field that will not receive your keys is a lie), and its footer names the engage key. An engaged field additionally carries the `editing:` marker on its bottom border naming the key that stops. Both surfaces go through the one shared `App::render_modal_text_field_frame`, and a field that can overflow its pane carries the shared `components::scroll_marker`. Do not re-implement either.
- **The reason for that mode is Enter, not Tab.** Do not repeat the plausible-sounding Tab rationale: dux cannot insert a tab character anywhere, and `text_input::tests::handle_key_returns_false_for_tab` pins Tab as unconsumed by the component, so Tab is free to keep being a focus key. The actual collision is Enter: it is content in a multiline field and it is also the confirm key in every modal, and only a mode can tell those two apart. A reader who believes the Tab story will build the wrong thing.
- **Space is content in both kinds of field.** So Space-as-activate must key off focus actually sitting on a button or a checkbox, never off the modal merely containing one, and never off mouse hover (there is no hover state; nothing handles mouse-move). With a text field focused, Space is typed.
- **Filters, search rows, and the command palette are deliberately type-immediately, and must stay that way.** Every one of them (the palette, the agent-list filter, the files-pane search, the macro bar, the project browser and chooser filters, the kill-running filter, the startup-log filter and viewer search) puts keystrokes straight into its `TextInput` with no engage step. A key that merely opens a search row is a filter toggle, not an engage step. Adding a mode to a search box is friction, not consistency: do not "fix" the palette.
- **Escape never saves.** It abandons, or it exits edit mode. The macro editor was the one violation (Escape wrote the body to config, so a started edit could not be abandoned) and has been corrected.
- **A field the user cannot click into is a gap.** Publish the field's rect into `OverlayMouseLayout` every frame so a click can land the caret, and route the click to a setter that calls `cursor_from_single_line_position`. Every caret-bearing single-line field now does. `PullRequestInput` was fixed first and wrongly called the last holdout; two filters were still missing, the project chooser's `/`-search (a reachable, everyday surface) and the startup-log picker's, and both now publish an `input: Option<Rect>` that is `Some` exactly while the field is the thing being drawn. A new field publishes its rect in the same change that adds it.
- **A single-line field is rendered by `render_single_line_cursor_input`, never by hand.** It takes a `focused` flag and clamps the caret to a character boundary before slicing. Three modals used to hand-roll the same few lines with a BYTE split (`after.split_at(1)`), so any name holding an accent or an emoji crashed dux the moment the caret sat before it, and they drew the caret unconditionally, so the field looked focused while a checkbox had it. Two more hand-rolled copies survived that sweep and have since been converted, the macro editor's name field and the startup-log picker's filter; both were char-safe, so neither crashed, but each carried its own caret model. Pair the flag with `Theme::overlay_field_border_style(focused)` so the border agrees with the caret. What the shared renderer does NOT do is scroll horizontally: no single-line field in dux does, so a value wider than its field runs off the end. That is a known gap, not a property of the renderer, and converting a field to it does not close the gap.
- **A caret position is a DISPLAY column, never a byte offset and never a character count.** The two halves are `input::cursor_from_single_line_position` (a clicked column to a byte caret) and `render::single_line_caret_column` (a byte caret to a hardware-cursor column), and they are exact inverses; use them rather than counting anything by hand. A CJK glyph or an emoji is two cells wide, so a char count drifts one cell right per wide glyph and a byte offset drifts further still: clicking the `a` in a field holding `"日本語abc"` used to put the caret at the END of the string, and the startup-log filter's caret sat three cells past a three-glyph query. A click on the SECOND cell of a wide glyph resolves to the caret position BEFORE that glyph, because the renderer paints the caret over the whole character and that is the only offset that highlights the glyph the user clicked. The click handler must also pass `prefix_width: 1` when the renderer pads by one leading space; passing 0 puts the caret one character past where the user clicked.
- **Clickable controls need misclick-safe spacing.** Separate adjacent click targets enough that an imprecise click cannot accidentally activate a different item. When a checkbox sits above modal buttons, include a blank row or equivalent spacing between the checkbox and the buttons.
- **Animations and periodic refreshes use wall-clock time, not tick counts.** Tying visual updates to tick rate couples frame cadence to logic timing. Use `Instant::elapsed()` (or equivalent) so animations stay smooth and refreshes stay consistent regardless of how often ticks fire.
- **The embedded-PTY caret is the host hardware cursor, never a painted block.** Render the agent/terminal cursor by moving the real terminal cursor onto the PTY cursor cell (`set_cursor_position`) and never pre-paint that cell into a styled cursor block. We do this deliberately for **accessibility and UX with CJK IME**: the OS anchors composition popups (Korean/Japanese/Chinese input) to the hardware cursor, so without it composition renders at the terminal origin instead of the agent prompt. Pre-painting the cell as well also reintroduces an invisible-caret bug under hosts like Alacritty that draw their block cursor by inverting the cell (inverting an already-styled cursor cell cancels it out). This means the caret look is the host terminal's cursor and is not theme-colored; that tradeoff is intentional.
- **The TUI does not disambiguate Shift-Enter; Ctrl-j is the supported soft-newline key.** In interactive mode the TUI forwards raw stdin bytes to the child PTY verbatim and never pushes the Kitty keyboard-enhancement flags (`PushKeyboardEnhancementFlags`). Under the legacy terminal protocol the host sends the *same* byte (CR, `\r`/0x0D) for both Enter and Shift-Enter, so there is no distinct Shift-Enter for dux to forward. Making it distinct would require pushing enhancement flags, which (a) only works on host terminals that implement the Kitty protocol and (b) changes the encoding of *every* key — and because interactive input is a verbatim passthrough, those re-encoded bytes reach the child, so it would break providers that don't speak the protocol. We deliberately do **not** do this. `Ctrl-j` already sends LF (0x0A), which agent CLIs treat as a soft newline, so it is the supported way to insert a newline without submitting in the TUI. Users who want a literal Shift-Enter binding can get it by running dux inside a multiplexer/terminal already configured for the Kitty protocol (e.g. tmux). Only the **web UI** rewrites Shift-Enter to LF (see below), because there the browser key event is available before xterm encodes it.

### Web UI (server mode)

The web UI (`crates/dux-web/web/`, React + Vite + Tailwind v4) has its own conventions, distinct from the TUI's `theme.rs` engine above. It is currently **dark-only** (`main.tsx` force-adds the `.dark` class); the light `:root` tokens exist but are inert. Style through the shadcn/base-ui token CSS variables (`--primary`, `--muted-foreground`, `--destructive`, …), never hardcoded colors.

- **Components: shadcn/base-ui first.** Reuse an existing `components/ui/*` primitive (`DropdownMenu`, `Dialog`, `Button`, `Tooltip`, …) before hand-rolling one. Hover hints go through the shared `SimpleTooltip`, never a native `title=`.
- **Row actions collapse into one `⋯` menu.** When a list row (changed files, projects, sessions) needs more than one action, put them in a single `DropdownMenu` opened by an `Ellipsis`/`EllipsisVertical` trigger — not a strip of inline buttons. The trigger reveals on hover and consumes **no layout space** when idle: animate it in with a `max-width`+`opacity` transition (or, in the sidebar, the absolute `translate-x`+`opacity` of `SidebarMenuAction showOnHover`). Keep it revealed while the menu is open via the Base UI trigger's `data-popup-open` attribute (`md:has-[[data-popup-open]]:…`, or `data-[popup-open]:…` on the trigger itself) — Base UI does **not** set `aria-expanded=true` on an open menu trigger, so keying off `aria-expanded` silently never matches and the action un-reveals (dragging the anchored popover) the instant the cursor leaves the row. Always show it on touch (`max-md:` overrides), and add `motion-reduce:transition-none`. The trigger must `stopPropagation` so it doesn't fire the row's own click.
- **Menu items: icon + neutral color; "…" marks a further step.** Every item in a dropdown `⋯` menu keeps a leading lucide icon — this applies to all of them (agent, Changes, project); none ship an iconless item. Append a trailing ellipsis `…` to any item that opens a dialog or needs confirmation (matching the app menu and the project/session menus). **Default destructive items to neutral color** — the `…` plus the confirmation dialog are the danger signal, not the color. (Most destructive `DropdownMenuItem`s use neutral text; reserve `text-destructive`/`variant="destructive"` for confirm buttons inside the dialog.) **The one deliberate exception is the agent ⋯ menu's "Delete agent…" entry**, which is tinted red at rest and brighter on hover (`variant="destructive"` plus `not-focus:text-destructive/70!` to dim the rest state). It is the most consequential per-agent action, so it carries the extra visual weight; the confirmation dialog still gates it. Do not propagate this red treatment to other destructive menu items without a deliberate decision.
- **Destructive actions always confirm.** A destructive item opens a dedicated `Dialog` (Cancel `autoFocus`, the confirm button `variant="destructive"`, misclick-safe spacing) gated by a store target — follow the existing per-action dialog pattern (e.g. `ConfirmDiscardFileDialog`); there is no shared `useConfirm` hook. Target-keyed dialogs route their open state through the shared `useVanishedTargetGuard` hook (`hooks/use-vanished-target.ts`) so a dialog whose entity vanishes from the live ViewModel closes itself, with `RemoveProjectDialog` and `CreateAgentDialog` as the deliberate exceptions. **A monitoring surface confirms its stops too.** Being a screen *about* destructive actions is not a licence to act on one click: `TaskManagerDialog` is a surface you leave open and read numbers off, so every stop it offers (per-row and "Stop all…") routes through a confirmation, and the per-row ones reuse the existing `ConfirmCloseTabDialog` / `ConfirmDeleteTerminalDialog` rather than adding new ones. This also matches the TUI, which already gates every kill behind `ConfirmKillRunningPrompt`. Keep the confirm cheap to dismiss so the hung-agent escape hatch stays fast.
- **Shift-Enter inserts a soft newline (LF), not a submit.** The terminal pane intercepts keystrokes at the key-event layer via xterm's `attachCustomKeyEventHandler`, because xterm collapses both Enter and Shift-Enter to CR before `onData` sees them — they are indistinguishable at the data layer. The decision lives in the pure, unit-tested helpers in `lib/termkeys.ts`, not in the component: `softNewline(event)` matches only a bare Shift-Enter `keydown` (no other modifier, and **never mid-IME-composition** — it bails on `isComposing`/`keyCode === 229` so a CJK confirm keystroke is never rewritten), and `softNewlineAction(event, ctx)` folds in the runtime context (ownership, armed latch) to return what the handler must do. The component closure is a thin applicator: on a match it `preventDefault`s (so the browser drops no stray newline into the hidden textarea) and `stopPropagation`s (so the handled key doesn't bubble to window shortcuts) and returns `false` (so xterm emits no CR); only the input owner then writes the `LF` (0x0A, the Ctrl-j byte), and only the owner's path scrolls to the live edge, clears any selection, and consumes an armed one-shot Ctrl/Alt latch — matching the side effects `onData` would otherwise provide. Every other key returns `true` and is encoded by xterm as usual. Because a mobile soft keyboard can't produce the chord, the mobile accessory bar carries a dedicated `⇧↵` key as a second entry point; both it and the physical-key handler write through the one shared `writeSoftNewline(term, pty)` helper so their landing behavior (scroll/clear/send) can never drift. This is web-only on purpose (the TUI cannot disambiguate Shift-Enter — see the TUI tenet above). Keep the branching in the `termkeys.ts` helpers so it stays testable without mounting xterm.
- **On phones, the compose bar is the typing surface; xterm is never typed into directly while it is on.** Typing into xterm's hidden textarea fights the soft keyboard (autocorrect/swipe/IME have no buffer to fix), so the mobile shell renders a third row below the accessory bar: `ComposeBar`, a controlled, buffered textarea with native keyboard assistance ON, plus a Send button. Send = deliver + submit, as MACRO-style keystrokes with the Enter travelling alone: the pure `composeSendWrites(text)` in `lib/composebar.ts` (unit-tested, no xterm import) plans the writes as `[macroPayloadBytes(text), CR]` (every `\r\n`/`\n`/`\r` newline becomes Alt+Enter, ESC CR, the newline-without-submit keystroke; the bare CR is the submitting Enter), and the caller delivers the CR `COMPOSE_SUBMIT_DELAY_MS` (150ms) after the body, guarded against pane unmount and socket drop. The delay is MEASURED, not folklore: Claude Code (2.1.217 bundle) merges stdin chunks into one paste through a 50ms debounce (and force-classifies any single key event over 800 chars as a paste), so an Enter arriving with or within that window of the body is swallowed into the paste as a newline, intermittently; 150ms is 3x the window. An EMPTY Send is a single immediate bare CR (a lone keystroke, no body to merge into, never delayed), which is how the user confirms TUI menus without focusing xterm. Deliberately NOT bracketed paste (and `bracketedPasteMode` is not consulted): the keystroke stream keeps "line break" and "Enter" distinct on the wire and reuses the transform the macro quick-picker already proves against these same PTYs. **Non-owners get no typing surfaces**: the accessory bar and compose bar render only for the input owner (the take-over card is a viewer's only interaction); the per-write owner gates stay behind the hidden UI as defense in depth, and an in-progress draft survives an ownership round-trip because its state lives in `TerminalPane`. Enter inside the box inserts a newline, never sends. The buffer STATE lives in `TerminalPane` (value/onChange), not in `ComposeBar`, so a preference flip or rotation unmounting the bar never destroys a draft. `sendCompose` returns a boolean and a refused send (not the input owner, socket not open, payload over `MAX_COMPOSE_SEND_BYTES`, a 2 MiB client cap under the server's 16 MiB WS frame limit that would abort the socket) KEEPS the buffer and toasts why; the bar clears only on true. A tap on the terminal redirects focus to the compose textarea (the touchend tap branch `preventDefault`s to suppress the synthetic mousedown xterm focuses from), and when the app in the PTY has mouse tracking on the tap is still delivered as a synthetic SGR click (`sgrClickSeq` in `lib/termkeys.ts`), so clickable TUIs keep working. **That same `preventDefault` is why a tap has to hit-test an OSC 8 hyperlink itself.** Suppressing the synthetic mouse events suppresses the only thing that can follow a link: xterm's `Linkifier` resolves the hovered link from `mousemove` and fires `link.activate` from `mouseup`, so a tap on a link used to do nothing but raise the keyboard. xterm publishes no "what link is at this cell" query and the OSC 8 uri lives in an internal service, so dux does NOT hit-test the point itself (tracking OSC 8 ranges in dux would be a much bigger thing than this bug is worth); `lib/termlink.ts`'s `activateLinkAtPoint` instead REPLAYS the suppressed sequence at the Linkifier and lets xterm answer. Three details are load-bearing. The events go to `.xterm-screen`, which is the element xterm hands the Linkifier, with `bubbles: false`, because the focus grab, the selection service and the mouse-report forwarding are all bound one level up on `Terminal.element` and a non-bubbling event cannot reach any of them. A PRIMING move at a different cell on the same row comes first, because the Linkifier only re-runs its providers when the CELL changes and two taps on one link report the same cell (MEASURED: without it the second tap on a link opens nothing). And a trailing `mouseleave` returns it to rest so a tapped link is not left underlined. Whether a link was hit is read from a counter the pane bumps inside its own `linkHandler.activate`, so the open stays in ONE place and keeps the `linkActivateAction` gating and the `noopener,noreferrer` window; `terminalTapAction` then decides the rest, and it deliberately still forwards the SGR click on a link tap (a desktop click does both, since the two paths sit on different elements) while NOT pulling focus into the compose box (the tab is already opening, and raising the keyboard over a terminal the user is leaving costs half the screen for a message they never started). Every refocus-after-action goes through `focusTypingSurface()` (compose textarea while the bar is up, xterm otherwise); do not add a bare `term.focus()` call site. Send fires on pointerdown with preventDefault (never blurs the textarea, keyboard stays up) plus a `detail === 0` click handler for keyboard/AT activation. Gated by `ui.compose_bar` (default on); off restores tap-focuses-xterm exactly. Scroll gestures blur the compose input too (reading dismisses the keyboard).
- **Every toast dismisses itself, on a severity-graded window, and severity is VISIBLE.** A toast the user has to hunt down and close is friction, so there is no such thing as a permanent web toast any more: the previous policy pinned warning, error and busy at `Infinity` and the bottom of the screen slowly silted up with statuses nobody had clicked away. The windows are graded rather than uniform, because an error that vanishes as fast as a success defeats the point of an error, and they are all derived from the one user-configurable base (`ui.status_clear_seconds`, default 6) by `lib/statusToast.ts`: info/success 1x, warning 2x, error 4x. A configured `0` keeps its documented meaning of "disable auto-clear" and applies to FINAL states only. **A busy toast is a different animal and needs its own guard.** sonner deliberately refuses to retire a `loading` toast: its close-timer effect returns early on `type === 'loading'`, it renders no close button for that type, and its pointerdown handler ignores the swipe, so a busy toast has NO exit of any kind (all three pinned by tests in `components/ui/sonner.test.tsx`, so a sonner upgrade that loosens any of them fails loudly). The store therefore schedules the dismissal itself, at `BUSY_TOAST_MAX_MS` (60s), cancelling the guard whenever anything else touches that id so it can only ever retire the exact spinner it was armed for. 60s is chosen to sit well clear of `dux_core::statusline::BUSY_TIMEOUT` (20s), after which the engine upgrades a stranded keyed Busy to a Warning and pushes that replacement: the guard must never fire while an operation is still live, or work that is still running would look like it stopped. **Severity reads at a glance**: the toast icons are colored per tone (`text-destructive` for error, amber for warning, sky for info, green for success, muted for the busy spinner) AND stay shape-distinct, so color is never the only signal. **Swipe dismisses**, because the close button is a ~20px target and that is not a touch target. sonner infers swipe directions by splitting the position string, so `bottom-center` yields `["bottom", "center"]` and a sideways swipe was inert; `TOAST_SWIPE_DIRECTIONS` names `bottom`/`left`/`right` explicitly. `top` is deliberately absent (dragging a bottom toast upward pulls it further into the screen).

- **Web terminal clipboard is wired explicitly, not left to xterm defaults, and follows the classic-terminal model: selecting copies, right-click pastes, no menu.** xterm.js renders selection as a painted overlay (no DOM Selection) and, on Linux/Windows, turns `Ctrl+c`→`\x03` and `Ctrl+v`→`\x16` — and that `\x16` reaches the *remote* agent, which pastes the *server's* clipboard. So `TerminalPane.tsx` owns clipboard. **Selecting copies** (copy-on-select, in the `mouseup`/`touchend` user gesture so `copyToClipboard`'s `execCommand` fallback is permitted over plain-HTTP; gated by the `ui.copy_on_select` preference, default on). **A mouse/pen right-click pastes** the browser clipboard (a touch long-press is left alone so the native selection gesture works; owner-gated; via `navigator.clipboard.readText`, guarded because it throws synchronously off a secure context, and it toasts a "use Ctrl+v" hint on plain-HTTP where the read is blocked). Copy chords: `Ctrl+Shift+c` + `Ctrl+Insert` + `Cmd+c`. Paste chords: `Ctrl+v` (intercepted via `attachCustomKeyEventHandler` returning `false` so xterm emits no `\x16` and the browser's native `paste` event feeds xterm's handler — secure-context-free, so it is the robust fallback when right-click-paste can't read the clipboard) plus `Ctrl+Shift+v` / `Cmd+v`. **Classify clipboard chords by physical key (`code`/`keyCode`), never `ev.key`** — xterm decides `\x16` positionally by `keyCode`, so a `key`-based match silently misses on non-Latin layouts and re-opens the remote-clipboard leak (`classifyClipboardKey` in `lib/termkeys.ts`). `Ctrl+c` stays SIGINT; on Mac a lone `Control` passes through to the app. **When the app in the PTY enables mouse reporting, xterm forwards a drag to the host instead of selecting locally**, so copy-on-select gets nothing and the highlighted text lands on the *host's* clipboard, not the visitor's. The escape hatch is a modifier that forces a LOCAL selection: `Shift` on Linux/Windows (xterm default), and on macOS `Option` — but only because we set `macOptionClickForcesSelection: true` (xterm gates the Mac path behind that flag; without it a Mac-browser visitor cannot select at all). When a drag yields no local selection while `term.modes.mouseTrackingMode !== "none"`, `onMouseUp` surfaces a one-time hint toast pointing at that modifier. The copy/hint/ignore decision lives in the pure `copyOnSelectAction` (`lib/termkeys.ts`). Keep this when touching `TerminalPane.tsx`.
- **A forwarded touch-scroll sends at most ONE wheel notch per touch-move; never a magnitude burst.** When the app in the PTY has mouse tracking on (an alt-screen TUI like Claude Code), a one-finger drag is forwarded to it as SGR wheel reports (`sgrWheelSeq`), not scrolled locally. `onTouchMove` fires at ~60-120Hz and a fast flick accumulates many rows, so forwarding the raw `dragScrollLines` magnitude would emit that many reports (e.g. 12) as a **dense burst in a single frame**. A real desktop mouse wheel forwards exactly **one report per discrete notch** at human cadence, and mouse-tracking apps are built for that 1:1 shape: Claude Code's scrollback-pager repaint survives 1:1 but **corrupts under the burst**, duplicating lines into the render, and because an alt-screen has no client scrollback and a touch-scroll triggers no reconnect/replay, the corruption **persists** (backgrounding the tab does not heal it). So the forward path caps to one notch per move via the pure `dragWheelReport` (`lib/viewport.ts`) — `Math.sign` of the drag magnitude — reproducing the desktop cadence while still tracking the finger across successive moves. The byte encoding of `sgrWheelSeq` is deliberately byte-identical to xterm's own SGR wheel report (`CSI < 64/65 ; col ; row M`, no release); the bug was never the encoding, only the burst, so do not "fix" it by touching the encoding. The LOCAL (normal-buffer / plain-shell) path keeps the full `dragScrollLines` magnitude — bursts are harmless when scrolling xterm's own scrollback. Do not restore the raw magnitude to the forward path.
- **The soft keyboard is handled by the browser, not JS, and the web UI has NO fullscreen mode (the TUI keeps its own).** `index.html` sets `interactive-widget=resizes-content` on the viewport meta so the soft keyboard shrinks the *layout* viewport (and `window.visualViewport.height` with it); the mobile shell pins its root to that height, and the terminal + accessory bar sit flush on the keyboard with no per-pane keyboard math. Without the directive, Chromium/Android's `visualViewport.height` still counts the keyboard's toolbar strip and the bottom accessory row renders behind the keyboard. The directive is Chromium-only; iOS/Firefox fall back to the same (already-accurate) `visualViewport` handling. The viewport meta's two other directives are equally deliberate (this tenet is their documentation; `index.html` itself carries only a pointer): `viewport-fit=cover` lets the page draw under the notch/home indicator AND is what makes `env(safe-area-inset-*)` report real insets (they are 0 without it) — the mobile root's `env()` padding in `App.tsx` and the fullscreen terminal column in `TerminalPane.tsx` depend on it; and `maximum-scale=1` exists for one reason: the compose bar's textarea uses 14px type and iOS Safari auto-zooms the page when an input under 16px gains focus — this is the standard accessibility-preserving fix, since Chromium ignores `maximum-scale` entirely and iOS 10+ ignores it for USER pinch-zoom (accessibility zoom keeps working) while still suppressing the input-focus auto-zoom. **There is deliberately no browser-Fullscreen-API button in the web UI.** It was removed because on Chromium/Android the Fullscreen API forces the fullscreen element to the `resizes-content`-shrunk layout viewport and hard-clips content, leaving an unfixable gap between the accessory bar and the keyboard, and its only real benefit (Keyboard-Lock capturing `Ctrl+t`/`Ctrl+w`) is obsolete now that those shortcuts have in-app equivalents. Do not reintroduce `requestFullscreen`, the Keyboard Lock API, or a fullscreen toggle in `crates/dux-web/web`. (The TUI's fullscreen agent pane is a separate Rust feature and is unaffected.)
- **The URL is the source of truth for position, and NOTHING in the web UI navigates relatively.** The hash names the whole position: the focused target, and a `/changes` suffix for the mobile changes screen. `mobileScreen` is kept in LOCKSTEP with the focused target rather than tracked independently: `setState` repairs it in the same commit as any patch touching `selectedTarget`, and a patch that states the screen outright wins, which is how the changes screen opens. `syncUrl` then writes both halves into the hash as one route, so state to URL is the normal direction and URL to state happens only on popstate, boot, and the not-found retry. `routeScreen` is the INVERSE, and its only job is telling `syncUrl` whether a move crosses a screen boundary and therefore pushes. `syncUrl` writes the hash and PUSHES only when the destination is a different screen from the one the URL currently names, REPLACING otherwise, so switching agents or tabs never piles up entries while every screen change stays one Back away. Two different things replace, and conflating them is how the previous round got this wrong. A RESTORE names a position the browser is ALREADY parked on (the boot deep-link, the reconnect re-restore), where a push would grow the back stack once per reconnect until Back was no longer one press from home. A CORRECTION retires an address that no longer names anything, and there are four: the destination chosen when the focused agent vanishes, a vanished tab and a vanished terminal falling back, and the way out of the not-found screen. A correction discards the entry the dead address occupied, so one later Back can land on the screen already showing and look inert; that is accepted, because the alternative leaves a Back that bounces onto a dead link. `history.go`, `history.back` and `history.forward` appear NOWHERE in the application code under `crates/dux-web/web/src`, and must not come back. The routing tests do call them, deliberately, on a fake history object of their own, because simulating the user pressing Back is the only honest way to test this; that is the one permitted use and it never touches the real browser. That includes the in-app chevrons: they are UP controls, not Back, and they call `navigateUp` (changes goes up to its agent, everything else to home), which NAMES the destination and PUSHES it like any other move between two real positions. `navigateUp` is the only push-by-default path, and its one exception is the way out of the not-found screen, which REPLACES for the reason above: pushing there would leave the dead end one Back away. The reason is that a relative step has no floor: a deep-link boot pushes nothing, so on that first screen dux's own entry is the bottom of the stack and one step walks out of the application onto whatever page preceded it. That is the original reported bug, and keeping the chevrons on `history.back()` reproduced it exactly, on the terminal, changes and not-found screens alike. Going in and back out does NOT net to zero, and nothing short of a relative step could make it: ten trips leave twenty entries. What matters is that every one of them is a real position, so Back always visibly moves rather than silting up with identical entries that appear to do nothing. When a focused agent vanishes the app NAVIGATES to a destination, the next active agent from the list's own ordering (`nextActiveSessionId` in `flatList.ts`, composed from `partitionQuiet` + `sortMainSessions`, so it follows whatever sort the user is looking at) or home when every survivor is dormant. A URL naming an agent the workspace does not have sets `routeNotFound` and renders `AgentNotFound` on both surfaces; it must never silently fall back to home, because pressing Back onto a deleted agent is ordinary and deserves a truthful screen. `retryRouteNotFound` retires that screen the moment a later spine carries the agent again, since nothing else on the spine path can (the prune has no selection to prune), and on a phone the screen replaces the entire shell. Terminal ids are deliberately exempt from not-found: they are ephemeral, so a vanished terminal falls back to its owner or home, but it still falls back OUT LOUD, rewriting the URL, because a silent return would leave the address bar naming something the app is not showing.
- **A reconnect onto a DIFFERENT run of the server hard reloads the page, and that is the only reload in the app.** A tab left open across a dux restart keeps running the interface the old server sent it, so it reconnects and renders the new server's data through old code, which is silently wrong exactly where nobody looks. `GET /api/v1/build` answers `{ version, process }`: `version` is the display version, `process` is a uuid minted once per server run. The tab reads it at boot (`loadServerIdentityBaseline`) and again on every RE-connect (`reloadIfServerChanged`, fired from `eventsSocket.onOpen`); either field moving calls `reloadPage()`, with no prompt, no toast and no banner, because the page is stale by definition and a notice the user has to act on is a notice they can dismiss and then trust. Both fields are needed and neither is redundant: `version` is the literal string `development` for every build that is not a tagged release, so it would never move between two dev builds, and `process` is what actually fires there; `version` is what names a release upgrade to a human. The run id is a `LazyLock`, NOT a per-request value, and that is the whole difference between "restarted" and "reconnected": mint it per request and every blip reloads the tab forever, which is why `the_run_id_is_stable_for_the_life_of_the_process` exists. An unknown answer (the probe failed, or a baseline never learned) is NOT a change, so a flaky network never reloads anything. Keep it NARROW: this says which run of which build is answering and must not grow into a schema or data-shape version, because the interface ships inside the server binary and a shape change cannot reach a client without a new build and a restart carrying it. `window.location.reload()` lives in `lib/reloadPage.ts` and has exactly one caller; do not add a second.

When a preference needs a side effect on write (e.g. `ui.github_integration` arms/disarms PR sync), give its descriptor a bespoke `writeTarget` routed to the existing dedicated endpoint. - **Dropping a file saves it and pastes its PATH; it never sends the file's bytes, and the upload route never writes to a terminal.** Both halves of that are load-bearing and both were got wrong once. Sending bytes cannot work: no agent CLI reads a file from its input stream, they take a path or read the clipboard of the machine THEY run on, which for a browser user is the wrong computer, and every terminal emulator whose source was read inserts the path on a drop. And the route saving the file must not also inject the text, because writing to a terminal is gated on holding input, enforced server-side on the websocket, so a handler injecting text would walk straight past that gate. The browser pastes the returned path over its own already-gated socket. The route's check of the connection id it was told about is a COURTESY for a clearer error, it is not the protection, and it must carry the TERMINAL SOCKET's numeric id, never the `X-Connection-Id` header (which names the events socket and explicitly refuses a PTY-class id). Naming rules: validate, never rewrite, so accented and non-Latin names survive; create exclusively relative to a PINNED directory handle so nothing is overwritten and a symlink at ANY candidate fails the request instead of being renamed around; the collision suffix carries a counter as well as a timestamp, because two uploads land in the same second, and reserves its room in BYTES up front. **The destination depends on which pane was dropped on, because the two panes carry two INTENTS.** A drop on an AGENT is "look at this for me": it lands in the agent's upload directory, `<worktree>/<ui.upload_directory>` (default `.dux/uploads`), created on first use by the one place that creates it, `file_drop::DropDir::open_uploads`. INSIDE the worktree, not beside it, because the path is handed to a CLI to read and some CLIs refuse to read outside their workspace; and inside it is also what makes cleanup free, since deleting the agent removes the worktree and the uploads with it. It hides itself with a `.gitignore` holding a single `*`, which ignores everything in the directory INCLUDING ITSELF (MEASURED on git 2.55: `git status --porcelain` then prints nothing at all, not even the directory as untracked). Writing `.git/info/exclude` instead is FORBIDDEN, and the reason is measured on the same version: in a linked worktree `git rev-parse --git-path info/exclude` resolves to the COMMON dir, so a write from inside a worktree edits the MAIN checkout and changes what git ignores in every other worktree, which is exactly the pollution this feature removes. An existing `.gitignore` is never overwritten (`O_CREAT | O_EXCL`, so the seed is also race-free between concurrent uploads and never follows a symlink), and `ui.upload_write_gitignore = false` skips it for a user who means to commit what they drop. `ui.upload_directory` is checked for SHAPE at load with the warn-once-and-degrade precedent (`normalized_upload_directory` pure, `upload_directory_load_warning` logged from `load_config`): absolute, `..`-bearing, `.`-bearing and empty values degrade to the default. That check cannot see a SYMLINKED component, and is not asked to: the walk that creates the directory opens one component at a time from a pinned worktree handle with `O_NOFOLLOW`, so a link out of the tree is refused rather than followed. The two settings live on `[ui]` rather than in an `[uploads]` section of their own because a top-level section would imply the feature exists in the TUI, and it does not. A drop on a TERMINAL is unchanged and is the narrower rule now: its destination is discovered LIVE from the process (foreground group, then shell, then the spawn directory) because a shell moves the moment someone types `cd`, and that stays true for all three owners, since an agent's companion terminal is not that agent's pane and a standalone terminal has no worktree to upload into at all. The policy lives in one named method on the PTY handle, `PtyClient::working_directory`, and must not migrate out to call sites. Pasting is one file per paste, absolute, one trailing space and NO newline (a newline submits), in DROPPED order, through xterm's own `paste` so bracketed paste is applied by the code that already does it. That last point deliberately differs from the compose bar's refusal of bracketed paste, and the reason belongs in a comment at the call site: compose text must keep a soft line break and a submitting Enter distinct, and a path contains neither. **The FORM the path takes is a per-provider CONFIG SETTING, `providers.<name>.web_dragdrop_paste`, and not a rule in the code**, because the receiving agent CLIs genuinely disagree about how they read a pasted path and the point of a setting is that somebody adding a provider picks the right form rather than writing code. The `web_` prefix is load-bearing: this is browser-only, since dropping a file on a terminal window in the TUI is the host emulator's job. Four forms, `bare`, `single_quoted`, `double_quoted` and `backslash_escaped`, all produced by the pure `pastePayload(path, form)` so every case is testable without mounting xterm, with `bare` the default for anything unlisted. The defaults are MEASURED, by running each CLI's own normalizer over the exact bytes dux sends, and the table lives on `dux_core::config::WebDragDropPaste`: Claude Code 2.1.220 and OpenCode take the whole string and never split on whitespace, so `bare`; Codex lexes with POSIX shell rules and accepts the paste only if it comes out as exactly ONE token, so a bare path with a space is silently ignored and it gets `single_quoted`; Copilot is closed source, unverified, and defaulted to `bare` as the do-nothing option. Do NOT reinstate a single hardcoded form in either direction: quoting everything was wrong (it breaks Claude Code on an apostrophe, because POSIX writes that apostrophe as close-escape-reopen and Claude Code's unescape collapses it into three) and so is bareness everywhere (it loses a spaced path on Codex). Two failures are properties of the receiving tools and must not be worked around: single-quoting a path with an APOSTROPHE breaks Claude Code, and any form carrying a BACKSLASH is mangled by that same unescape step. A misspelled config value degrades to `bare` with one warning at load, the `capabilities.clipboard_passthrough` convention. **The form and the length limit are published in TWO places, and which one carries which is decided by what EVENT can change it.** What a live process launched with rides the SPINE, per tab, in `AgentTabView.drop_paste` (`Engine::launched_drop_paste`, retired by `clear_tab_runtime`), because it changes when a process LAUNCHES or TERMINATES and `sessions.changed` is what fires for both; what CONFIG says rides the bootstrap document, in `provider_drop_paste`, because `config.changed` is what fires for that. Publishing the per-tab half on the bootstrap document was a real defect: the browser refetched it only on a config change, so its copy went stale for the whole life of a process and a tab relaunched under a different provider was still quoted for the previous one until a reconnect. A live tab's launched entry WINS over config for as long as its process runs, because the tab keeps reporting the provider name it launched as and a user renaming that `[providers.<name>]` block out of config would otherwise drop it to `bare` mid-session; a config edit takes effect on that tab's next launch. The browser resolves ONE profile per pane and reads both halves out of it, never one from each, and it resolves it IMMEDIATELY BEFORE EACH PASTE out of refs rather than once per drop (a config reload or a retarget lands between two files of a multi-file drop); the bootstrap load is seq-guarded like the spine load so an overtaken reply cannot restore a stale form. A plain TERMINAL never reads the setting at all and always gets `single_quoted`. Running a shell is the REASON it must be quoted, not a reason it can go bare, and getting that backwards is the specific mistake this sentence exists to prevent: dux permits `$`, a backtick, a space, a semicolon, a quote and parentheses in a destination path, and a bare path carrying any of them is pasted onto a command line the user is about to press Enter on, where the shell splits it, expands it or RUNS a command substitution in it. The owning agent's CLI preference must not reach it either, for the separate reason that a companion terminal is not that agent. LENGTH is a second failure mode and is checked on the FINAL payload, quoting included, not on the path on disk: Codex files any paste over `LARGE_PASTE_CHAR_THRESHOLD` (1000 characters) away as generic large content BEFORE it looks for a path, so an over-limit payload is not sent at all and is reported as a stranded saved-but-not-sent file with its full path, rather than pasted and claimed as attached. **That limit is keyed by the COMMAND being run, compared on its file name, never by the provider's block NAME and never by the form.** A provider's name is free text and its `command` is independent of it, so `[providers.myagent] command = "codex"` is a real Codex and `[providers.codex] command = "something-else"` is not; keyed by the name it was wrong in both directions at once, letting a real Codex under an alias be handed oversized paths it silently ignores while withholding valid long paths from an unrelated CLI. Keyed by the FORM it was wrong in both directions too, giving a terminal codex's composer limit (a shell has none) and letting codex escape it on any of the three other forms it can be configured with. The limit is a MEASUREMENT of a third-party CLI, so it stays a compile-time table beside the forms rather than becoming a config setting nobody has anything to base a value on. One toast per drop, not per file, chosen by the first applicable rung of nothing-saved / saved-but-not-sent / refused / success, with renamed files NAMED as original-and-saved rather than counted. **PASTING AN IMAGE IS THE SAME JOURNEY ENTERED BY A DIFFERENT GESTURE, and it must stay that way**: it reuses the route, the per-provider `pastePayload` form, the command-keyed length limit, the collision naming and that one toast, and the ONLY thing it varies is WHERE the path lands, which is an `UploadSink` (`terminalUploadSink` / `composeUploadSink`, chosen by `activeUploadSink` on exactly the rule `focusTypingSurface` uses) rather than a second copy of the loop. It reads the `paste` EVENT and never `navigator.clipboard.read()`, because dux is routinely served over plain HTTP on a Tailscale address where the async read is blocked outright and the keystroke IS the permission, the same constraint the Ctrl+v path above is built around. The decision is the pure `clipboardPasteAction` in `lib/clipboardPaste.ts` (nothing / take-it-as-an-image / leave-it-to-xterm, plus a fourth REFUSED for a non-owner, because an image paste that saves nothing has to SAY so). An image WINS over text in the same event, since a screenshot copied out of an application arrives as `image/png` beside a `text/html` snapshot; a non-image file item is deliberately left alone. Image-wins is a DEFAULT and not a trap, because `Ctrl+Shift+v` forces the text: the argument for ignoring a non-image file item (it is usually an artifact of how an app puts rich content on the clipboard) applies just as well to an `image/png` from a rich source, and a copied spreadsheet range really does carry a bitmap beside the numbers. The chord ARMS a one-shot latch in the key handler (`termkeys::forcesTextPaste`) that the paste listener consumes into `ClipboardPasteContext.forceText`, checked BEFORE the ownership gate so a viewer using the hatch is not told an image was refused, and expired on the next task turn so a chord that produces no paste event cannot disarm the following one. It is deliberately a SEPARATE predicate rather than a fourth `classifyClipboardKey` action: every Cmd combo classifies as `passthrough` before any other rule, so folding it in would have given `Cmd+Shift+v` no hatch at all and made the feature Linux-only. The listener is registered on the terminal container in the CAPTURE phase, and that is load-bearing: `attachCustomKeyEventHandler` returns false WITHOUT preventDefault for Ctrl+v precisely so the browser's native paste still fires and xterm's own handler reads the text, so image handling cannot live in the key handler (a key event carries no clipboard) and must run BEFORE xterm's handler on the hidden textarea INSIDE that container. It cancels the event only for an image; every other paste is passed through untouched. `defaultPrevented` staying false is NOT enough to pin that, and believing it was is how the suite came to pass with the listener deleted outright: a stray unconditional `stopPropagation` kills every text paste in a real browser while leaving that flag false the whole time. So the stub `open()` appends a real textarea to the container and registers a spy `paste` listener on it, standing in for xterm's own, and the tests assert the spy FIRES for text and does NOT for an image. That is also the only way the CAPTURE registration is exercised at all: with the event dispatched at the container itself, an ancestor-capture listener and a plain bubble listener are indistinguishable. And the key handler must NOT swallow a paste chord for a non-owner. Past `ui.upload_pasted_text_chars` characters a text paste onto an AGENT becomes a `.txt` file through the same route, the same upload directory, the same `pastePayload` form, the same command-keyed length limit, the same collision naming and the same one toast. Strictly greater, matching `pasteExceedsAttachmentLimit`. Be exact about two things rather than claiming absolute fidelity, because both were claimed wrongly once. And this is a claim about the JS string `getData("text/plain")` returned, not about the OS clipboard, whose bytes the browser has already normalised before dux sees them. A refusal carries a `subject` (`image`/`text`) so the two land on two toast ids instead of replacing each other. The default of 1000 is deliberately CONSERVATIVE, and the measurements are evidence of SCALE rather than the reason for the number: Codex's `LARGE_PASTE_CHAR_THRESHOLD` is 1000 and Claude Code force-classifies a key event over 800 characters as a paste, so a low four-figure count is where CLIs start reclassifying, but both answer a different question (what a CLI does with a paste it received). ANY command can be a provider here, including unmeasured ones that may cut off sooner, so dux sits at the low end and lets anyone who wants more text arriving as text raise it. Do not "correct" it upward on the argument that ordinary prose runs past it; that argument was made and declined. `0` disables it, the floor and ceiling clamp with the warn-once-and-degrade pair (`normalized_upload_pasted_text_chars` pure, `upload_pasted_text_chars_load_warning` from `load_config`), and the bootstrap projection normalizes AGAIN because `set_settings` and the raw config editor both put a value in memory without going back through `load_config`. Web-only, deliberately: a real terminal emulator already types a dropped path in for you, so the TUI gets no counterpart.
- **Dropping a file on the EDITOR'S FILE TREE is the OTHER intent, and it is durable.** The tenet above is the whole story for a drop on a PANE, which means "look at this for me" and lands in the invisible upload directory. A drop on the tree means "add this file to my PROJECT", and the editor is where that belongs because the editor is the only surface where the user PICKS the destination by pointing at it. So it lands as an ordinary VISIBLE file that git can see, in the directory dropped on, and it must never touch the uploads directory, never write a `.gitignore`, and never paste a path into any terminal. Where it lands is decided by the row: a FOLDER row takes the files, a FILE row hands them to its PARENT (a file is not a place to put a file, and it is the same `targetDirForCreate` mapping New File… already uses, reused rather than re-derived), and empty tree space is the worktree ROOT. The receiving row must HIGHLIGHT before the drop lands, or the user learns where the file went by reading the toast afterwards, and the highlight is asserted as the CLASSES the row paints: it carried a `data-drop-target` marker no CSS ever read, so deleting every `dropClass` call left the tree visually inert with the highlight tests still green. **A drop that MISSES every row must be swallowed** (`swallowMissedFileDrop`, on the overlay's `DialogContent` and the standalone shell's root): the browser's default action for a dropped file is to NAVIGATE to it, so a near-miss on Monaco or the tab strip throws the editor away, and the tree's rows already `stopPropagation` so the ancestor handler sees the misses and nothing else. **dux takes files, not folders**, and a folder is a natural thing to drop on a tree, so it is a NAMED refusal ("dux cannot take a folder, drop its files") sorted out of the `DataTransfer` by `classifyDroppedItems` in the one place that can see it, matched by NAME rather than by index because `items` and `files` only line up when every item is a file; a drop delivering nothing identifiable at all gets its own message rather than silence, because letting go of a folder must never look like letting go of nothing. It reuses the ONE upload route rather than getting a second one, because everything except the destination is the part that is easy to get wrong (the size cap, the permit taken before the body is buffered, the name validated and never rewritten, the create relative to a pinned handle, the symlink refusal at any candidate, the collision suffix), and the two are told apart by ONE query parameter, `dir`, distinguished by PRESENCE and not by emptiness: the empty string is the worktree root, which is an ordinary place to drop. That presence is ALSO what skips the route's input-ownership courtesy check, since a tree drop pastes into nothing and a browser really does carry a terminal-socket `conn` from the pane it came from; the skip has a test in both directions, because deleting `query.dir.is_none() &&` otherwise breaks nothing. Server-side it is a third `FileDropDestination` variant whose `DropDir::open_tree_dir` walks components with `O_NOFOLLOW` exactly as the uploads walk does but CREATES NOTHING (which is STRICTER than create/rename/move, all three of which canonicalize and permit an in-worktree symlinked directory; stricter is the safe direction so it stays, and both docs pages say so rather than implying parity), and that is a separate function rather than a flag on `open_uploads` because a boolean deciding whether a walk may create directories in the user's project is the kind of switch that gets passed the wrong way round. A terminal id must answer `None` there rather than falling back to the terminal's own directory: silently serving the other intent puts the file somewhere the user never pointed. Every refusal it produces is a SENTENCE: a missing component is `TreeDirMissing` naming the folder (the stale-tree journey, which answered a raw errno), and it uses `verified_path_of` rather than `reportable_path_of`, because the absolute/UTF-8/no-control-character bar exists so a path can be TYPED INTO A PTY and this destination types nowhere, so a folder legitimately named with a control character was being refused with a sentence about a terminal. The identity half of that check is kept, since it is about correctness. **On a collision it SUFFIXES where the editor's move REFUSES**, and both are right for the same reason: a move names one exact destination so silently using a different one would be a different operation, while a drop names only a folder, so the next free name is the honest answer. Neither overwrites, and the toast must say which name was actually used. The client toast is `editorDropToast`, deliberately NOT `dropToastFor`: that one's entire vocabulary (`sent`, `saved-not-sent`, "pasted the path") describes a delivery that does not happen here, so every distinction it carries would have to be stubbed out with a lie. Afterwards, refresh what went stale exactly as the MOVE path does: `revalidateDirs` for the affected directory and `refreshSearchIndex` for the flat index.
- **In-browser file editing is web-only, and the TUI gets no counterpart.** The Monaco editor overlay (file tree, tabs, save, search, file create/rename/move/delete/info) and the config-file editor exist so a user can edit files ON THE GO, from a phone or a borrowed machine, where nothing else is available. Anyone sitting at a terminal already has vim or helix, so a TUI file editor would be a worse copy of a tool they already have. Do not build one. The TUI's answer is `open-worktree`, which hands the directory to the user's own editor.
  - **A move is a MODAL, it is a RENAME on the wire, and an occupied destination is REFUSED rather than confirmed.** All three halves are decisions, not accidents. Cut/copy/paste was declined because a file clipboard needs somewhere to hold a pending entry across unrelated interactions, a way to SHOW that something is held, and its own conflict rules on paste, which is a lot of machinery for a question ("where should this go?") that one dialog answers in one interaction. There is deliberately no `move` route: a move IS `rename` with a destination in another directory, so it reuses `dux_core::worktree_file::rename_entry` and every containment guard already proven there, and a second endpoint doing the same rename would be a second place for those guards to drift. And an occupied destination is refused outright, with no overwrite confirmation offered, because there is no trash on the server: the destination's bytes would be gone with nothing to undo them, and the escape hatch (rename one of the two, then move) costs one extra step. `rename_entry` already refuses it, so the UI matches the server rather than inventing a confirm the backend would reject anyway. Do not "improve" this into overwrite-with-confirmation without a real undo behind it. **That refusal has to be ATOMIC, and a stat in front of `std::fs::rename` is not it.** `rename(2)` silently OVERWRITES (measured: file-onto-file and directory-onto-empty-directory both succeed), so a stat-then-rename pair leaves a window another client can create the destination in, and dux is explicitly multi-client with nothing to recover the bytes from. `worktree_file::rename_no_replace` therefore uses `rustix::fs::renameat_with` with `RenameFlags::NOREPLACE`, which rustix maps to `RENAME_NOREPLACE` on Linux and to `renameatx_np`'s `RENAME_EXCL` on macOS, dux's two supported targets. The fallback is narrow and must stay named rather than quietly reinstated as the main path: a filesystem with no `renameat2` (and macOS before 10.12, where rustix finds no `renameatx_np`) answers `ENOSYS`/`EINVAL`/`ENOTSUP`, and only there does the old racy pair run, so only there does the window still exist. The SOURCE of a rename is resolved with the no-follow resolver `delete_entry` uses (`entry_literal_path` plus `check_entry_parent_contained`), because `rename(2)` moves the directory ENTRY: moving a symlink moves the link and never touches its target, exactly as deleting one does, so a link whose target escapes the worktree is a legitimate thing to move and refusing it named a file the user never touched. The DESTINATION keeps the following resolver, because a destination reached through a symlinked directory really would write outside the tree. The destination is chosen by BROWSING through the same lazy `tree` endpoint the explorer uses, one directory per request, so an empty directory is still reachable (a list derived from file paths would omit it) and a huge worktree costs nothing to open; the browser lists entries on `is_dir` alone, and there is deliberately no second `expandable` check, because `git::list_dir` sets `is_dir` and `expandable` to the SAME value on every branch (a symlinked directory escaping the worktree comes back `is_dir: false`), so a wire state of "a directory that cannot be walked into" does not exist and a guard for it would only look like it was doing something.
  - **The info panel is the ONE editor dialog with a live truth to close itself on, the wire says which answer it got, and its freshness is exactly two fetches and no poll.** The other four (New, Rename, Move, Delete) key off the file tree, which is a client-owned lazy cache and not a broadcast ViewModel slice, so there is nothing for `useVanishedTargetGuard` to watch and they deliberately skip it. The info panel asks the server for a fresh stat, so it learns the truth directly, and the route distinguishes the two failures instead of collapsing them: a path that resolved cleanly but is GONE answers **404** (`dux_core::worktree_file::EntryMissing`, and the panel dismisses itself), while a path that was REFUSED (traversal, `.git`, an escaping symlink, live or DANGLING) answers **400** and stays on screen with its reason. A refusal that vanished silently would hide why. `FileApiError` carries the status for exactly this; keep the two answers apart. **Be precise about WHEN it learns any of that, because an earlier round of this was written as though the panel watched the file.** It does not: there is no poll and no subscription, and the fetch runs on exactly two events, the panel opening and the WINDOW REGAINING FOCUS. The second is the whole reason a file can vanish "while the panel is open" at all, and it is what covers the real journey (delete the file in a terminal or another tab, come back to this one) for one request per return and no timer. A file deleted by an agent while this tab stays focused is NOT noticed, and that gap is accepted, stated here, stated in `web-editor.md` and stated at the fetch. If you add a poll, rewrite all three.
    - **`GitStatusView` has a variant per genuinely different answer, and two of them exist because `git status` is SILENT rather than reassuring.** An ignored path and anything inside a nested repository or submodule are listed by no status call at all, so with only `Clean` to fall back on the panel called every file under `node_modules`, `target` and every vendored subrepo "tracked and unmodified" (MEASURED). The editor's tree is a plain filesystem browser with no ignore filter, so those paths are one right-click away. `Ignored` comes from `git::path_is_ignored` and `OtherRepository` from `git::repository_root` compared against the worktree, both pathspec-scoped and cheap. Note the one place the discipline differs: `check-ignore` takes plain PATHNAMES and REJECTS the `:(literal)` magic `file_status` needs (MEASURED on git 2.55: "pathspec magic not supported by this command", exit 128), so it gets `--` and nothing else, which is correct because a pathname is already matched literally. `check-ignore` also consults the index by default, so a TRACKED file matching an ignore rule answers "not ignored", which is what we want. The panel's facts come from ONE no-follow stat plus that scoped git work, so a symlink is described as a symlink and never as the file it points at. That refusal of an escaping symlink is about the TARGET PATH STRING, which the panel prints verbatim, and NOT about the target's metadata: the stat is `symlink_metadata`, which reports the link's own lstat and never the target's size, mode or mtime. The web mirror keeps the same vocabulary once: `fileInfo.ts`'s `codeLabel` takes its noun from the shared `fileStatusMeta` and only adds which SIDE the change is on, so an unrecognised code reads as the shared neutral word instead of leaking the raw letter.

### Agents and Providers

- **A provider is supported if and only if it supports PTY mode.** dux embeds the CLI's interactive session in a pseudo-terminal; that is the only thing a provider has to support.
- **Any CLI tool can be a provider.** Configure `command` in `config.toml` and dux spawns it. No adapters, no protocol layer. Adding a new provider is a config-only change, not a code change.
- **Claude, Codex, OpenCode, and Copilot are the defaults.**
- **No protocol layer.** No JSON-RPC, no custom message format, no adapter binaries. The CLI runs exactly as it would in a normal terminal.

### Agent Tabs

- **A tab is a provider session inside the agent's one shared worktree, not a new worktree.** One `AgentSession` (one branch, one sidebar row) hosts N provider tabs; every tab runs against the same checkout and edits the same files. **The strip carries provider tabs only.** Companion terminals are never folded into it: a terminal is owned by either an agent session (spawned in that agent's worktree) or a project (a "project terminal", spawned at the project's repo root with no agent attached), and neither kind ever appears in the tab strip. Tabs are never separate sidebar agents. The strip renders at the top of the center/PTY pane and appears only when the agent has **two or more tabs**; with a single tab the pane looks exactly as it does today.
- **All tabs are generic — there is no Main/Support distinction.** Every tab renders and behaves uniformly: no marker, no pin, no "Main"/"Support" labels in any user-facing copy. The one internal, load-bearing invariant is the **session-slot tab**: the tab with `tab_id == session_id`, which has no `agent_tabs` row (it is derived from the `agent_sessions` row). This is an implementation detail that keeps every session-keyed runtime lookup working; it is **not** a privileged tab and must never surface to the user as one.
- **Resume is decided dynamically by liveness, and it is per-provider.** A launching tab uses the provider's resume flag (e.g. `--continue`) **only when it is the sole tab of that provider coming up** — no *other* tab of the agent running the **same** provider is live or launching. Provider `continue` is directory-scoped **and** per-provider for the resume-capable defaults (Claude, Codex, OpenCode): each of those CLIs keeps its own conversation history in the worktree, so a claude tab and an opencode tab can BOTH resume simultaneously; only two tabs of the *same* provider would collide on the same most-recent conversation. Copilot is currently excluded from resume entirely (`resume_args: None` in `config.rs`), so a Copilot tab never resumes regardless of liveness — `should_resume_provider` returns `false` for it and `tab_resume_decision` always starts it fresh. The decision lives in exactly one place — `Engine::tab_resume_decision(session, tab_id, provider, requested)` ANDs the caller's request with `should_resume_provider(P)` (the effective provider `P = tab_provider.unwrap_or(session.provider)` must support resume and have started here) and a check that no *other* tab of the session whose `tab_running_provider` equals `P` is in `providers` or has an in-flight `AgentLaunch`. `build_tab_launch_request` and every reopen path (web `launch_agent`, TUI `launch_focused_support_tab`) route through it, so the render badge, the launch paths, and reconnect all agree. (There is no `resume_eligible_tab`; do not reintroduce a positional/first-tab notion of resume, and do not gate resume on `session.provider` when the tab runs a different provider.)
- **Closing a tab ends that tab; closing the last live tab detaches the agent.** Closing any tab tears down its PTY. Closing an **extra** tab also deletes its `agent_tabs` row — destructive and unrecoverable, so confirm it. Closing the **session-slot** tab has no row to delete; it goes through the single-tab `KillSessionPty` path, which detaches the agent only when it was the last live tab (siblings keep running). The distinct agent-level **"Detach agent"** action (`DetachAgent`, the web `POST .../kill`) tears down **every** tab at once and marks the agent Detached — that is separate from closing one tab. Deleting the agent tears down *every* tab's PTY. Extra tabs render in creation order and **do not reorder**; `sort_order` is an append-only stamp. **A clean exit closes the tab by itself.** When an extra tab's CLI exits with code 0 (the user deliberately ended the conversation, e.g. `/exit`), the tab's row is deleted along with the prune — no confirm, because there is no process to kill and the row keeps nothing (the provider's conversation history lives in the worktree, and a fresh tab of that provider can resume it). A non-zero exit keeps the dormant tab as the crash-diagnosis/relaunch surface. The rule lives in one place, `dux_core::engine::clean_exit_closes_tab_row`, honored by both the TUI exit loop and the web's `prune_exited_ptys`; when the closed tab was the one on screen the pane minimizes, landing in the list when no live sibling remains (exactly like a single agent's clean exit).
- **New tabs default to the project provider and start fresh; provider is per-tab.** Adding a tab spawns the project `default_provider` immediately (fresh); retarget a tab via `ctrl+p` (TUI) or its `⋯` menu (web), effective on the tab's next launch. There is a **per-agent cap (default 20, configurable via `agent_tabs_max`)**; the web "+" affordance disables at the cap. The TUI deliberately has **no "+" button in the strip** — tabs are added via the `new-agent-tab` palette command (or the NewTab keybinding), and the cap is enforced inside that flow.
- **Restart brings tabs back dormant, not running.** On reopen each tab reopens as a pill with **no process spawned**, and its content surface shows a **provider-agnostic** message (dux doesn't restore a tab's conversation across a restart; recover the prior conversation from a fresh session using the provider's own conversation-history command — do not name a specific command, providers differ). **Focus alone never launches** — only an **explicit action** (Enter in the TUI, a button in the web) launches it, and that launch's resume eligibility follows the same per-provider dynamic-liveness rule as any other launch (`tab_resume_decision`): it resumes that provider's prior conversation when this tab is the sole live/launching tab of that provider, and starts fresh otherwise. There is no separate "always fresh" explicit-action path — the explicit action is what *triggers* the launch, not what decides whether it resumes. On the web this means a dormant tab must render from a `has_live_process` flag *without* opening the PTY socket, because subscribing force-launches the provider.
- **Tab state is derived runtime state: keep it in SQLite, never in config.** Persist extra tabs in an additive `agent_tabs` table (backward compatible — existing databases start with zero rows). The session-slot tab has no row. Do not write tab provider or order into portable project config.
- **Runtime provider state is keyed by tab id, with the session-slot tab id equal to the session id.** The `providers` map, `running_provider_pins`, resume-fallback state, and the PTY activity/streaming maps all key by tab id; `tab_id == session_id` for the session-slot tab keeps every existing session-keyed lookup working. **Sidebar liveness is any-tab: the sidebar row and `SessionView.working`/`has_output` OR across *all* of the agent's tabs**, so an agent shows Active while any tab is live and stops working only when every tab is idle. **Auto-reopen intent (`desired_running`) stays agent-level (session-slot-scoped)** — it is not OR-ed across tabs — so restart/auto-reopen semantics don't churn as extra tabs come and go. Only the center pane resolves the focused tab. Store `agent_tabs` in memory as `HashMap<tab_id, AgentTab>` (value carries `session_id`) so ownership resolves O(1) with no side index. When a tab's process exits while siblings are still live it shows a **quiet, tab-scoped** message ("Tab exited", or "exited cleanly and was closed" when the clean-exit auto-close removed it), never the workspace-wide "Agent exited" warning; that warning fires only when the **last** live tab exits (the pruned entry's `agent_detached`). If the session-slot tab exits while another tab is focused, stay on that tab.
- **Tabs honor each surface's existing UI tenets.** TUI: the strip is themed through `theme.rs` (reuse existing semantic fields where they fit; add a `dux.tab_*` token only where none does), and tab actions are Center-scope — switch keys (`Ctrl-Left`/`Ctrl-Right`, `Ctrl-1..9`, configurable) work in non-interactive mode only and there is **no tab switching in fullscreen** (drop to non-interactive), and the strip is **not rendered** in fullscreen at all — that surface exists for maximum terminal space. Web: Chrome-style pills at the top of the terminal pane, deep-linkable (`#/agent/<sid>/tab/<tabId>` for extra tabs; the session-slot tab stays the bare `#/agent/<sid>`), reusing the shared `⋯`-menu, destructive-confirm, touch-target, and working-bob tenets above.

### Terminals

- **A terminal is owned by exactly one owner: an agent session, a project, or nothing at all.** A session-owned terminal spawns in that agent's worktree; a project-owned terminal (a "project terminal") spawns at the project's repo root with no agent attached; a **standalone terminal** is owned by NOTHING and spawns in the user's home directory. Ownership never changes after spawn. `TerminalOwner::Standalone` is a real variant carrying no id, not an `Option` and not a sentinel, and every ownership question is answered by an EXHAUSTIVE method on the type (`is_at_route`, `closed_by_session_delete`, `closed_by_project_removal`, `as_ref`) rather than a `matches!` at a call site, so a fourth kind is a compile error at every site that has to answer for it. On the web the same discipline is `matchOwner`/`matchWireOwner` in `lib/terminalOwner.ts`, whose switches end in `assertNever`.
- **A standalone terminal opens in the home directory, from `home::home_dir()`, falling back to `/`.** Deliberately NOT the config-directory resolver (`Paths::config_root`), which also consults `DUX_HOME`/`XDG_CONFIG_HOME` and answers a different question: where dux keeps its own files. The rule and its `~`-shortening twin live in `dux_core::home_path`, split into a function taking the resolved home and a thin wrapper that resolves it, so "home cannot be resolved" is testable without mutating the process environment. An unresolvable home opens at `/` rather than refusing: the user asked for a shell and a shell runs anywhere. **What is resolved is a USABLE DIRECTORY, not merely a path**: the directory goes straight to the spawn as the child's working directory, so a home that is a regular file, a dangling symlink, or a directory dux may not search would fail the spawn and produce no terminal at all, which is exactly the outcome the fallback exists to prevent. `dir_is_usable` answers all three with one `stat` on `path/.` (effective credentials, symlinks followed, `.` needing search permission) and an unusable home takes the same `/` fallback. An EMPTY resolved home is rejected BEFORE that probe rather than by it, because the empty path is the one input where joining a component changes the question being asked: `"".join(".")` is `"."`, the current directory, so the probe said yes about a directory nobody asked about and the empty path itself then went to the spawn and failed. Every other shape keeps its subject, which is measured rather than assumed (`joining_a_dot_only_changes_the_subject_for_the_empty_path`). It chooses a DIRECTORY and nothing more: never retry a failed spawn at `/`, because a missing shell or a bad `[terminal] command` is a configuration problem the user has to see.
- **A standalone terminal gets the global environment and no project overlay**, because it has no project. The two owned kinds merge `config.env` with their project's `env`; this one has only the global half.
- **A standalone terminal is addressable at UN-NESTED addresses** (`POST /api/v1/terminals`, `DELETE /api/v1/terminals/:tid`, `/ws/terminals/:tid/pty`, hash route `#/terminal/<id>`), because there is no owner to nest it under. Those addresses serve standalone terminals ONLY: an owned terminal is a 404 there, so the un-nested address is not a way around the nested routes' cross-owner rejections. Its palette command is `new-standalone-terminal` on both surfaces (the TUI palette and the web cog menu), and it is called a "standalone terminal" wherever it must be named.
- **A standalone terminal's row names the DIRECTORY, not an owner.** The second line is the spawn directory with the home directory collapsed to `~` (`~`, `~/code`), which is also what the sidebar search matches. It travels on the wire as `TerminalOwnerView::Standalone { cwd_label }` because the browser is not necessarily on the server's machine. It is the SPAWN directory, not a live probe: this string feeds the coarse change fingerprint, so a value that moved on every `cd` would churn the sidebar and make the search key unstable.
- **Terminals are runtime-only.** No SQLite row, no config entry, no restore across restarts. Existence equals a running PTY.
- **Project and standalone terminals do not run the project's `startup_command`.** That command is a worktree provisioning step for new agents; a terminal of any owner is a plain shell running `[terminal] command`/`args` with the resolved environment.
- **Removing a project closes its project terminals** (graceful SIGTERM plus SIGHUP — interactive shells ignore SIGTERM, so the hangup is what actually ends them — then the reaper), exactly as deleting an agent closes that agent's terminals. Detaching an agent leaves its terminals running; projects have no detach.
- **NOTHING closes a standalone terminal automatically.** Removing a project closes that project's terminals and deleting an agent closes that agent's; neither event has anything to do with a terminal that belongs to neither. It ends when the user closes it or dux shuts down. This is a DECISION, not an oversight, and it is written in a comment beside both `begin_close_session_terminals` and `begin_close_project_terminals` (and on the two `closed_by_*` methods) precisely so nobody later "fixes" the omission.
- **A terminal row is an agent row. It renders through the same shared row component and in the same idiom, on both surfaces.** Terminals are NOT a lesser, single-line list item. In the TUI they build their `ListItem` through the shared `framed_row_item` (two content lines plus a trailing blank spacer) and paint their selection through the shared `paint_framed_row_selection` (the hand-painted half-cell tint frame, a `▄`/`▀` edge on the spacer rows, tint on the two content rows only so each row keeps its own text colors) exactly like agent rows, with the same reserved top-margin row and `LEFT_PANE_GUTTER` left/right padding. Never render a terminal row with the ratatui widget `highlight_style` (a full-cell flood): that is the terminal idiom we deliberately removed. On the web the terminal row is the same two-row shape as the agent row. When you change the agent row's framing/selection/spacing, the terminal row must move with it because they share the code.
- **The row content is a two-line, two-column contract: two left elements ellipsize, two right elements survive.** Per line the layout is `[fixed leading glyph] [left text (ellipsizes)] … [right text (survives)]`. The agent row fills it as name/PR on line one and project/state (plus branch and tab count folded in) on line two; the terminal row fills it as the primary label/(nothing) on line one and owner/state on line two (the owner is `agent@project` for a companion terminal, or the project name for a project terminal). The TUI realizes this through `fit_agent_meta_line` (marker + state word + tab count survive; project name + branch ellipsize) and `right_align_line`; the terminal row reuses those same helpers, which is what keeps the agent row byte-identical while terminals adopt the design. Keep branch and tab count on the agent row: if they exist, they must render.
- **A terminal has three states only: idle, running, typing. It never shows detached or needs-attention** (a terminal is a live PTY: alive or gone). The state PRIORITY mirrors the agent row exactly (`agent_state_word` / the web `stateWord`): typing outranks busy outranks idle. The WORDING deliberately differs for the busy state: a terminal shows **"Running"** (a terminal runs a process; it does not "work" like an agent), while an agent shows "Working". Idle and Typing read the same on both. Only the sidebar row shows these; the terminal-management surfaces (TUI kill overlay, web task manager) are separate.
- **A terminal is busy (shown as "Running") when it is streaming output OR a foreground app is running in it, even while quiet.** This is the shared `Engine::terminal_is_working` predicate (the field/predicate keep the `working` name; only the user-facing word is "Running") that both the viewmodel (`TerminalView.working`) and the TUI terminal row read, so the surfaces agree. `PtyClient::foreground_process_name` returns `None` at an idle shell prompt and `Some(app)` once a real command runs, so a set `foreground_cmd` means an app owns the terminal; a running-but-quiet dev server / editor / watcher reads busy, not idle. Typing still takes precedence. **A forwarded pointer report suppresses the FIRST half only, and that asymmetry is deliberate.** The streaming half is an INFERENCE from repaint text, and a repaint the user's own wheel provoked is no evidence about the agent at all, so the pointer window discounts it. The foreground-app half is a FACT read off the kernel: a `vim` that repaints because somebody scrolled it is still `vim` running, and a scroll cannot make that less true, so nothing suppresses it. Suppress both and every terminal with a real process in it flickers to Idle the moment the user scrolls to read its output.
- **Typing is a real keystroke within the input window, and a forwarded pointer report is neither typing nor evidence of work.** `pty::classify_pty_write` is the one classifier both surfaces call (through `Engine::note_pty_write`), and it sorts a write into three kinds. `Typing` (a real keystroke or paste) stamps `pty_input`. `Ignored` (an empty frame, a focus report `CSI I`/`CSI O` which xterm forwards on select/focus, or a mouse report dux could not decode) stamps nothing. `Pointer` stamps `pty_pointer` and never `pty_input`, because selecting or scrolling a terminal is not typing. The bytes still reach the PTY in every case; the classification only decides which window gets stamped. **The two stamps exist because a pointer report answers a second question a keystroke does not**: it makes a mouse-tracking child repaint its whole grid, and while `pty_pointer` is fresh `Engine::is_agent_streaming` stops inferring "working" from output text and defers to the agent's own `OSC 9;4` report, falling back to not-working. Be honest about what that costs: only Claude Code and Copilot emit `OSC 9;4`, so for Codex and OpenCode a genuinely busy agent reads idle for the length of the window. **How long the suppression lasts is per gesture**, decoded from the report's button field rather than guessed from its prefix (`pty::decode_mouse_report`, `engine::pointer_suppression_window`): a WHEEL notch arms `POINTER_REPAINT_WINDOW` (1250ms, because scrolling is continuous and the notches keep coming), a BUTTON press or release arms the much shorter `POINTER_CLICK_REPAINT_WINDOW` (500ms, because a click causes one repaint and is over, and a click that STARTS work must let the Working cue appear promptly), and MOTION arms nothing at all (an any-event-tracking app emits one per cell crossed, so suppressing on motion would blank a busy agent for as long as the mouse moved). Both surfaces are affected, not just the web: the TUI forwards its own SGR reports to the child too, and reading those as typing is exactly the bug this replaced.
- **State colors are theme-derived, and Idle is the only unstyled state word.** The busy state (agent "Working" / terminal "Running") is green (`Theme::session_working` in the TUI, `text-green-500` on the web), Typing is the theme's violet (`Theme::session_typing` in the TUI, the `--dux-typing` token on the web), Detached is amber, Needs-you is cyan; Idle alone uses the muted line color so it blends into its line. Never hardcode a state color; add a semantic theme field wired through every theme (as `session_typing`/`session_working` are) when a new meaning is needed. This working green was added to reach web/TUI parity and deliberately changes the agent row too.
- **Line one (glyph + name/label) carries no live-state color; the "operating" cue is animation, not color.** On both surfaces the agent name / terminal label keeps a stable IDENTITY color, neutral while live (`session_active`) and dimmed when detached/exited, and NEVER takes the typing/working color. Operating (Working/Running) is shown by the animated braille spinner glyph PLUS a name shimmer (TUI `shimmer.rs`, a wall-clock brightness wave built per-character; web `.agent-name-shimmer`); typing shows a caret glyph; attention keeps its accent blink. The live-state COLOR lives only on the line-two state word (above). The TUI run loop polls at ~30fps while `any_row_animating` (so the spinner/shimmer/blink stay smooth) and drops back to the lazy 100ms cadence when every row is quiet, so animation cost is paid only while something animates.
- **An idle terminal's sidebar name is a plain "Terminal"; the identifying "Terminal N" label survives everywhere identity matters.** In the sidebar row (TUI `terminal_row_lines`, web `TerminalFlatRow`) an idle terminal reads "Terminal" (the owner on line two and row order distinguish several); a running one shows its foreground command. The `Terminal N` model label still drives the web tooltip, the breadcrumb, and the task manager's per-terminal stop buttons via `terminalTitle`, so nothing that must pick one terminal out of several loses its number.
- **Every sidebar element carries a position; both surfaces sort terminals by the active sort mode.** The same sort control that orders agents (TUI `Ctrl-p`, the web sort dropdown) orders terminals too, with manual = drag order. Terminals get a runtime-only `sort_order` (stamped monotonically at spawn, reset on restart, never persisted) and a `ReorderTerminals` command behind `POST /api/v1/terminals/reorder`; the web reorders terminals within their own `SortableContext` (a terminal never crosses into the agents list). The sort comparators are duplicated per surface (Rust `terminal_items` / TS `sortFlatTerminals`) and must stay in lockstep.
- **Web only: the Terminals section is a collapsible divider with a chevron and no leading icon, matching the Inactive (Quiet tail) toggle, but defaulting OPEN** (a live terminal is worth surfacing, unlike dormant Inactive agents, which default closed).

### Git and Data Safety

- **Worktrees are user data.** Never removed or mutated casually. Deletion requires explicit user confirmation.
- **Git operations are conservative.** Source checkout refresh uses `--ff-only`. Destructive operations require confirmation.
- **Commit messages are plain sentences.** Do not use conventional commit prefixes such as `feat:`, `fix:`, or `chore:`. Do not add structured commit trailers such as `Constraint:`, `Confidence:`, `Scope-risk:`, or `Tested:` unless the user explicitly asks for them.
- **Prefer explicit failure over silent waiting.** If something fails, say so immediately with context.
- **A refname is a POSITIONAL, so every git call that takes one needs `--`.** This is the rule the next person adding a git call will get wrong, so it is written here rather than left to be rediscovered. A branch, tag or commit-ish sitting in a positional slot is read by git as an OPTION when it begins with a dash, and git then obeys the flag and exits 0, so the wrong thing happens and dux reports success. `git branch` refuses to CREATE a dash-leading name, which is why this looks impossible, but plumbing (`update-ref`) creates such a ref outright and a non-leading component may begin with a dash (`foo/-bar`), so these names really do reach dux. Measured on git 2.55: `git worktree add <path> --force` checks out HEAD; `git switch --detach` detaches; `git branch -m --force <new>` renames the CURRENT branch forcibly and leaves the requested one alone; `git push -u origin --all` pushes EVERY branch. Put the `--` in, and pin the reading with a test in the family already in `git.rs`.
  - **There are TWO exceptions, and in both of them `--` is NOT enough.** They share one mechanism: a porcelain command that consumes the separator itself and then forwards the positional to an INNER git command carrying no separator of its own. `git push -u origin -- <name>` and `git branch -m -- <old> <new>` were both verified to be genuinely protected, so the plain rule above really does hold everywhere else; these two are not.
    - **`git worktree add`.** Measured: it forwards the start point to an internal `git branch <name> <start-point>`, so a start point named `--force` or `--quiet` is obeyed by that inner command even with `--` or `--end-of-options` in place. `create_worktree_from_start_point` therefore resolves the start point to an OBJECT ID first (`rev-parse --verify --end-of-options <sp>^{commit}`), because 40 hex characters can never be read as an option.
    - **`git pull`.** Measured with `GIT_TRACE=1` on git 2.55: `git pull --ff-only origin -- --force` runs `git fetch --update-head-ok origin --force`, separator gone. A branch named `--force`, `--prune` or `--all` is therefore never fetched, pull exits 0 saying "Already up to date." and dux reports a successful refresh of something it did not touch; a branch named `--depth=1` writes `.git/shallow` into the user's SOURCE CHECKOUT and converts it to a shallow clone, with an unrelated error on screen so the damage is not attributed. The object-id trick does not apply, because the refspec names a ref on the REMOTE. `pull_origin_branch` therefore passes a FULLY QUALIFIED `refs/heads/<branch>` refspec, which cannot lead with a dash (measured: `git pull --ff-only origin -- refs/heads/--force` fetches and fast-forwards correctly).
    - When a separator does not visibly work, measure what the subcommand does with the argument rather than assuming the separator handled it. Every one of these gets a test in the `*_reads_an_option_looking_*` family in `git.rs`, no exceptions.
- **Every file dux keeps for itself is owner-only, and the config root's `0700` is what actually enforces it.** The per-file `0600` on `config.toml`, `sessions.sqlite3`, its SQLite sidecars and `dux.log` is defence in depth for a file copied out of the directory; the directory's own mode is the real boundary, and it has to be, because SQLite creates its sidecars itself at runtime with no mode dux can choose. The one place that decides any of this is `crates/dux-core/src/file_modes.rs`; do not chmod at a call site, and every file dux keeps must actually HAVE one: `config.toml` was promised the every-start treatment by the shipped template comment and by `introduction.md` while nothing tightened it at all, reaching `0600` only because `write_config_atomic` renames a fresh `0600` temp over it, which happens on first creation or on a save that changed the document, so a config chmod'd to `0644` by hand stayed `0644` for good. `DuxPaths::ensure_dirs` now tightens it beside the root. Three rules hold there. Tightening only ever CLEARS group and other bits, never touches the owner's, so it is idempotent and safe to run on every startup, which is required or the change reaches nobody already installed. It is BEST EFFORT: a mode dux cannot set is a warning, never a reason to stop logging, stop opening the database, or refuse to start, and getting that wrong turned a `logging.path` dux could not chmod into no logging at all and no message anywhere. And it NEVER follows a symlink, because the mode it would change belongs to somebody else's file, which a `config.toml` linked into a dotfiles repository makes routine. What dux does NOT tighten is the user's own data: `worktrees/`, `dux.lock`, and a `themes/` directory they created. Those are covered by the root above them, and preserving their mode is deliberate, so a change that starts tightening one of them must be argued for, not slipped in.
  - **"A `0400` config stays read-only" is a statement about the TIGHTENING PASS and about nothing else. Do not let it drift into a claim about writing.** It shipped in the template comment and on the docs site as though it meant a read-only config would not be modified, and it does not: `write_config_atomic` renames a fresh `0600` temp over the destination, a rename needs write permission on the DIRECTORY and not on the file, so the read-only file is replaced and comes back `0600`. Both surfaces now say that outright. Preserving the destination's mode was considered and deliberately declined: it would carry a `0644` forward on every save and undo the startup tightening on the one file that holds `[env]` tokens, and preserving `0400` would make dux LOOK as though it had honoured the file while having overwritten it anyway. The behaviour is pinned by `write_config_atomic_replaces_a_read_only_config_and_resets_its_mode`.
  - **Best-effort is a claim about an error path, so test the error path.** Making the tightening fatal in `create_private_dir_all` and `open_log_file` left every `dux-core` test green, because the tests that looked like coverage took the SYMLINK branch, which returns `Ok(())` before any chmod is attempted and so has no error to swallow. The docstring claiming the real case could not be built unprivileged was wrong. Two MEASURED shapes build it: `create_dir_all` on `/proc/self/fdinfo` succeeds while the chmod is refused with `EPERM` for every caller including root (procfs rejects `ATTR_MODE` outright, so it is root-safe), and `/dev/null` can be appended to while a non-root chmod on it is refused. Any new best-effort call site gets a test in that shape.

### Tone

- **Welcome tips are playful and sassy.** They should feel fun, not like a manual. Lead with surprise or delight, highlight non-obvious features that differentiate dux, and keep keybinding references secondary to the feature discovery. Avoid dry "press X to do Y" phrasing.

### Quality

- **Prove your work with tests.** Every change should include unit tests. When feasible and low-lift, add integration tests as well.
- When debugging a problem, before fixing it, **aim to prove your findings with a unit test**.

## Project Summary

`dux` is a Rust terminal UI for orchestrating AI coding sessions per git worktree.

The current app provides:

- A left pane for projects and agent sessions
- A center pane showing the agent's terminal output (embedded via PTY) or diff viewing
- A right pane for changed files and diffs
- Commented user config in the platform-specific dux config directory (`~/.dux/` on macOS, `~/.config/dux/` on Linux)
- Session persistence in `sessions.sqlite3` alongside the config
- Logging in `dux.log` alongside the config
- PTY-based agent startup: spawns CLI tools (`claude`, `codex`, `opencode`, `copilot`) directly in a pseudo-terminal

## Important Constraints

- The app spawns CLI tools directly via PTY (portable-pty) and renders their output using an embedded terminal emulator built on alacritty_terminal. There is no protocol layer (no ACP, no JSON-RPC).
- Long-running actions should not block the UI thread.
- All periodic or potentially-blocking work (git commands, file I/O, network) must run in background workers, never on the main UI thread. Even fast operations like `git symbolic-ref` should use workers to prevent UI freezes if the filesystem or git lock stalls.
- Async operations must keep the status line updated for the full operation lifecycle: set a Busy message when the worker starts, then replace it with a clear success or failure message when the worker completes. Do not start background work silently.
- User state lives under `~/.dux/` on macOS and `$XDG_CONFIG_HOME/dux/` (or `~/.config/dux/`) on Linux.
- **The web server (server mode) is single-tenant / trusted-access by design.** There is no login of any kind. The server binds `127.0.0.1` by default and optionally a Tailscale address; access control is delegated to loopback scope, Tailscale ACLs, or an upstream proxy the operator may add. A Host-header allowlist and same-origin check guard against DNS-rebinding and cross-site requests. Every client that reaches the server shares one workspace: it can attach to and drive any agent or terminal PTY, browse the server's filesystem (project picker), and see every session's status and changed files. This is intentional for a per-developer or trusted-team tool, with no per-user ownership or path sandboxing by design. Do not add features that assume mutually-distrusting web users without first designing a real per-user isolation model (session ownership enforced on subscribe/write, a sandboxed file browser, per-user status scoping).
- Worktrees are user data and should not be removed or mutated casually.
- Git operations should be explicit and conservative, especially around the source checkout.
- **Target platforms are macOS and Linux only.** Windows users run dux through WSL2, which is Linux. Do not add `#[cfg(windows)]` branches, `cfg!(windows)` checks, or Windows-specific code paths. Assume Unix throughout.

## App Module Structure

The `crates/dux-tui/src/app/` directory splits the TUI into focused submodules. Each file contains an `impl App` block for a specific concern:

- **`mod.rs`** — `App` struct, types, enums, bootstrap, run loop, and state helpers. Read this first to understand the data model.
- **`input.rs`** — All keyboard/mouse event handling (`handle_key`, `handle_left_key`, etc.).
- **`render.rs`** — All rendering methods (`render`, `render_header`, `render_left`, etc.) and UI helper functions.
- **`sessions.rs`** — Project and session CRUD (create agent, delete, reconnect, refresh, project browser).
- **`workers.rs`** — Background thread management (`drain_events`, `spawn_*`, `run_create_agent_job`).

When making changes, edit only the relevant submodule. If you need to add a new method to `App`, place it in the submodule that matches its concern. If adding a new type or enum, add it to `mod.rs`.

## Recommendations For Future Changes

- Keep the status line centralized. New async operations should report progress through the shared status API, not ad hoc strings.
- The core keyed status controller (`dux_core::statusline::KeyedStatusController`) is the single source of truth for engine status across the TUI and the web. The **TUI renders it as a single status line** (most-recent-wins; documented-lossy for concurrent statuses, since it shows only the most recent). The **web renders it as toasts** (sonner), one per open keyed status, and **every web toast auto-dismisses, whatever its tone** (see the web toast tenet above for the windows and the reasoning). **Correlation is by per-operation key:** a `Busy` and its eventual success/error/`StatusCleared` carry the same key so the surfaces replace/dismiss the right entry. Every `Busy` must be followed by a final (success, error, or clear); a keyed `Busy` left open expires to a Warning after the busy timeout. Do NOT add a third surface; do NOT emit an unkeyed `Busy` for a multi-step web operation (it strands the anonymous slot on a spinner until the leak guard retires it).
- Status messages auto-clear on a tone-aware policy owned by the controller: **Busy/pending persists until a final state replaces it** (a `set_busy` must be followed by a `set_info`/`set_error`; an unresolved pending intentionally shows as a stuck spinner rather than vanishing), **Info/success auto-clears** after `ui.status_clear_seconds` (default 6; 0 disables), and **Warning/Error persist until the next status replaces them**. That is the ENGINE-side policy, and it is what the TUI status line shows; the web's toast layer has its own dismissal policy on top of it (every tone dismisses) because a toast the user must click away is friction in a way a single status line never is. New status call sites must follow the pending→final convention; never leave a Busy hanging. On the web surface, the key correlation ensures the right toast is dismissed when the final arrives.
- Status line messages must be verbose and actionable. Do not write terse messages like "Done." or "Pushed." — instead explain what happened and, when relevant, what the user can do next. Example: "Changes committed successfully. Press ^U to push to remote." rather than "Committed."
- Code must be production ready and modular to allow future Open Source contributors to integrate new features with ease. Do not take shortcuts.
- Route new modal UI through `PromptState` so `Esc` keeps working uniformly.
- Prefer command-palette actions over adding many more global hotkeys. **This is per surface: in the TUI, that means the `Ctrl-p` palette. In the web UI there is no palette; the equivalent home is the cog app menu (`appMenu.ts`), and it deliberately has NO keybinding of its own.** Do not add a global hotkey to the web UI to reach a menu action; add the action to the menu.
- Keybinding labels shown to the user should use proper casing (e.g. `Ctrl-g`, not `ctrl-g` or `CTRL-G`). Title-case modifiers (`Ctrl`, `Shift`, `Alt`) distinguish them visually from the key itself. The `^X` notation (e.g. `^P`) is acceptable in footer hint bars since its meaning is explained in the help overlay.
- Keybinding parsing from config is case-insensitive for modifiers and control keys — `CTRL-g`, `Ctrl-g`, and `ctrl-g` all parse identically (crokey lowercases the input). Letter keys are also lowercased during parsing, so `P` and `p` are the same binding; to bind uppercase P the user must write `shift-p`.
- Never hardcode keybinding labels in user-facing strings (config comments, status messages, UI text). All keybindings are user-configurable — always look up the actual binding via `RuntimeBindings::label_for()` so labels stay accurate after rebinding. The only exceptions are pure text-input contexts (typing characters, backspace, cursor movement in text fields) and palette-only command names (actions with no keybinding that are invoked exclusively through the command palette).
- Keep agent creation and other blocking git/provider work in background workers.
- The PTY approach is CLI-agnostic: any terminal command can be used as a provider. Keep it generic.

## Keeping Documentation In Sync

- When adding, removing, or changing keybindings, update `README.md` if it documents controls or shortcuts.
- **The TUI has a command palette; the web has an app menu. They are different surfaces, so never conflate them in docs or UI copy.** The TUI palette opens with `Ctrl-p` (a rebindable `[keys]` default, defined in `keybindings.rs`). The web has **no command palette and no keyboard shortcut for its menu**: it is an app menu opened by the cog button in the top-right (desktop) or the mobile hub header, reachable by Tab and operable with Enter/arrows/Escape. Writing `Ctrl-k` anywhere is now wrong on both surfaces: the web palette was removed, and in a TUI context terminals commonly treat `Ctrl-k` as readline's kill-line. Never suggest `ctrl-k` as a TUI rebind example. When docs must name the key, scope the sentence explicitly ("in the web UI…" / "in the TUI…").
- **The two surfaces are now independent, so keep them in step by hand.** `dux_core::palette` is the source of truth for the **TUI palette only**; the web app menu is defined client-side in `crates/dux-web/web/src/lib/appMenu.ts`. There is no longer a projection or a cross-language pin holding them together (both were deleted with the web palette: a pin implying a relationship that no longer exists is worse than no pin). **When you add a `Ctrl-p` palette command, decide, explicitly, whether it warrants a corresponding entry in the web app menu**, and say so in the PR. A global, parameter-free command usually does; a per-project/per-session/per-terminal one usually belongs in the web's `⋯` row menu instead. Nothing will fail if you skip this, which is exactly why it must be a deliberate step.
- When changing features, pane layouts, config paths, or provider behavior, verify that `README.md` still accurately describes the application.
- The README intentionally omits a full keybinding reference to avoid staleness. Do not add a section listing specific key combinations back to it. The in-app `?` help overlay is the authoritative reference for key combinations. Documenting how to configure keybindings (the `[keys]` config format, syntax, and examples) is acceptable — just avoid enumerating individual bindings that would go stale.
- The marketing/documentation site lives in `website/` and is published to `getdux.app` (GitHub Pages). When a change affects anything the site describes or shows — features, command-palette actions, pane layout, install methods, config format, provider defaults, the resource footprint, screenshots, or the install script — update `website/` in the same change so the site stays accurate. Match the site's existing playful tone and never hardcode anything that drifts: avoid counting features/methods in headings and avoid enumerating specific keybindings (the in-app `?` overlay remains authoritative). New copy that references real values (paths, commands, version, RAM usage) should reflect what the app actually does.
- **No half-width prose unless something sits in the other half.** A section intro capped at `max-w-2xl` with nothing to its right is a column of text and then a hole. The cap exists to keep a reading measure comfortable NEXT TO something, so it is right in `LatestPosts.astro`, where the blog link sits beside the heading, and wrong everywhere the intro stands alone. Four sections had it wrong and were widened; that was the third time the maintainer asked for the same fix, which is why it is written down. If a full-width line feels too long to read, the answer is shorter copy or a second column with something real in it, not a cap that leaves the page looking unfinished.

- **In `.astro` templates, write the space between a tag and the text next to it as `{" "}`.** Astro eats the line break after a closing inline tag, so this perfectly ordinary source ships welded together:

  ```astro
  <strong>Bind wider and dux says so, loudly.</strong>
  Point it at a LAN address and the banner tells you...
  ```

  That renders as `loudly.Point it at a LAN address`. Nothing warns you: the build succeeds, the markup is valid, and the sentence is simply wrong on the page. Nine of these were shipped on the live site before anyone noticed, and they were found by eye rather than by any check. So put the space in explicitly, on the line the tag ends: `</strong>{" "}`.

  There is deliberately NO automated check for this. One existed briefly and was removed: it could only fire when a closing inline tag was followed by a WORD character, which is the easy half. Widening it to cover tag-next-to-tag produced 57 hits that were almost all legitimate markup, because heading anchor links, syntax-highlighting token spans and the footer's adjacent spans all put two inline tags side by side. So the shape that matters most is not machine-checkable, the half that is checkable was not worth a build step, and this is caught by writing it correctly and by looking at the rendered page. `Loopback by default.dux server binds127.0.0.1:8080` is what it looks like when nobody does either.

- The docs section at `getdux.app/docs` is generated from plain Markdown in `website/docs/`. Add a `.md` file there with `title`, `description`, `group`, and `order` frontmatter and it becomes a page at `/docs/<filename>` automatically — the sidebar (grouped by `group`, ordered by `order`), heading anchors, table of contents, and sitemap entry are all derived for you. When a feature change touches themes, config, providers, or anything a docs page explains, update the relevant Markdown in the same change. Keep prose accurate to the app and avoid enumerating individual keybindings.

## Recommendations For Debugging

- First check the `dux.log` file in the dux config directory (`~/.dux/` on macOS, `~/.config/dux/` on Linux).
- Confirm whether the provider command in `config.toml` is installed and on PATH.
- If agent creation fails, determine whether it stopped in:
  - worktree creation
  - PTY spawn (command not found)
  - PTY process early exit
- If the UI appears frozen, verify the operation is on a worker path rather than the main event loop.

## Git Command Safety

When shelling out to git, **always ensure the command output is immune to user-specific git configuration**. User settings like `color.diff`, `diff.noprefix`, `status.branch`, `status.renames`, `core.quotePath`, and others can alter output in ways that break parsing.

- **Prefer plumbing commands** (`cat-file`, `rev-parse`, `for-each-ref`) over porcelain when you need machine-readable output. Plumbing commands are guaranteed stable.
- **Use `--porcelain`** for `git status`. Never use `--short` — it is affected by user config (`status.branch`, `status.relativePaths`, etc.).
- **Prefer `--porcelain=v1 -z` when parsing status paths.** Parse NUL-delimited records instead of line-based output so spaces, quotes, Unicode, and embedded newlines in paths are handled safely.
- **Use `--numstat`** for line-level diff statistics. It outputs tab-separated values unaffected by config.
- **Prefer `--numstat -z` when parsing file paths from diff stats.** Rename and copy records should be parsed from NUL-delimited output, not from whitespace- or newline-delimited text.
- **Override config with `-c`** when a porcelain/plumbing alternative doesn't exist (e.g., `git -c color.diff=false diff`).
- **Imperative commands** that aren't parsed (`worktree add`, `branch -D`, `pull`) are fine as-is.
- **For imperative git commands, rely on exit status rather than parsing stdout.** Treat stdout/stderr as user-facing diagnostics only unless Git explicitly documents the format as machine-stable.
- **Do not parse human-facing commands like `git branch --show-current` when a plumbing-style alternative exists.** Prefer commands such as `symbolic-ref --quiet --short HEAD` or `rev-parse`.
- **Avoid shelling out to `git diff` for display** — the project computes diffs in-process using the `similar` crate and applies syntax highlighting with `syntect`. Use `git::file_at_head()` to get the base version and read the working copy from disk.

## Recommendations For Editing

- Follow the existing `crates/dux-tui/src/app/` submodule pattern when adding new concerns. If a new feature area grows beyond ~200 lines, extract it into its own submodule with `use super::*;` and an `impl App` block.
- Keep changes scoped to one submodule at a time; avoid cross-cutting edits across multiple app submodules in the same PR when possible.
- Use `theme.rs` constants for all colors and styles — never use raw `Color::*` values in rendering code.
- When adding new UI elements, reuse existing semantic color names in `Theme` when they fit. Define a new semantic color only when no existing token fits, and update every supported theme/default mapping in the same change. `theme.rs` is the single source of truth for visual styling.
- The canonical config renderer produces a fully commented config on first creation. Subsequent saves preserve user edits via `toml_edit`. Users can run `dux config diff` to see what changed or `dux config regenerate` to get the latest canonical template.
- **`dux config diff` is DERIVED from the config structure, and adding a setting requires nothing of you.** `collect_config_changes` in `crates/dux-tui/src/cli.rs` projects both the parsed file and `Config::default()` to `serde_json::Value` and walks them structurally. It used to be a hand-maintained list whose own doc comment conceded that a key missing from it was a key the command silently ignored, and it had already drifted: every web-only `[ui]` field was absent. `serde_json` rather than `toml` is load-bearing, because TOML has no null and its serializer omits a `None` struct field, which would hide every default-`None` setting. Three things are worth knowing before you touch it. It compares the PARSED FILE against `Config::default()` and deliberately does not call `load_config` or `ensure_defaults`, so it reports what the user wrote rather than what dux normalizes it into. Each subtree gets a POLICY, either RECURSE or SUMMARIZE, and `env` and `projects` are summarized so a token or a local path can never reach the output (there is no third "ignore" policy on purpose: a setting dux reads and never reports is the drift this replaced). And the emitted dotted paths are sorted explicitly, because provider and macro names live in an `IndexMap` whose order is insertion order; paths are built from structural segments and quoted when a user-controlled key is not a bare TOML key, never reparsed with string-prefix checks. The exhaustiveness test mutates every leaf of the serialized default config in turn and asserts a path is emitted for each, which is what actually catches a newly added key, so do not weaken it into a walk that merely visits leaves.
- **`dux config diff --raw` prints the whole config, `[env]` values included.** The plain summary is safe to paste into a bug report and `--raw` is not; say so wherever either is documented.
- When a setting can have a sensible default at first boot (e.g., the user's home directory, platform-specific paths), resolve and store the concrete value in `config.toml` right away — do not leave it commented out or empty. Users should see a working value they can edit, not a placeholder they have to fill in.
- Preserve safe failure behavior around project refresh and failed agent startup.
- **Never use byte-based `.len()` or `[..n]` slicing to truncate user-visible strings.** Terminal output, file paths, and UI text can contain multi-byte UTF-8 characters (box-drawing, block elements, CJK, emoji). Always use `.chars().count()` for length and `.chars().take(n).collect()` (or `char_indices().nth()`) for truncation. Byte-based slicing will panic if the index falls inside a multi-byte character.

## Verification

Use:

```bash
cargo fmt
cargo clippy --all-targets --all-features -- -D warnings
cargo test
```

`cargo clippy --all-targets --all-features -- -D warnings` is a CI gate — the `Clippy` check on every pull request runs this exact command and fails the PR if it emits any warning. Run it locally before committing so a toolchain bump or a newly introduced lint doesn't surface only once the PR is pushed. A new stable Rust release can enable lints that previously passed; when that happens, fix the code rather than suppressing the lint unless there is a specific, documented reason.

For interactive smoke testing, ask the user to run `cargo run` as a final sanity check rather than running it automatically.

**Seeing the web UI: use the preview container at `tools/preview-env/`, never a directly-run dux.** It builds the binary on the host, mounts it into an isolated Docker container (own config/sessions in named volumes, loopback-only port), ships a `fake` streaming provider so no real agent CLI needs to exist or be authenticated inside, and screenshots via `./up.sh` + `./shot.sh` (see its README; for click-through journeys, write a throwaway `puppeteer-core` script from `shot.js`'s boilerplate or drive the REST API, and delete the script after). **Never run `dux server` or the TUI directly on the host to inspect UI work, and never kill dux processes on the host**: a directly-run instance shares the developer's real `~/.config/dux` with their own live dux — which may be the very instance this session is running inside — so a stray instance corrupts shared state and a killed process can destroy the user's active session.

**The web UI is compiled into the binary, and a failed frontend build is a HARD build failure.** `crates/dux-web/build.rs` runs `npm run build` and panics if it fails, so `cargo build` fails. It deliberately no longer writes a placeholder page, and no longer falls back to a previously built `dist/`: both existed only to let a failure continue quietly, and the effect was that a release could ship four platform binaries serving `web assets not built` with every check green. The escape hatch for Rust-only work is `DUX_DISABLE_UI_BUILD` (any non-empty value), which SKIPS the build rather than tolerating a failure. With it set and no existing `dist/`, the binary embeds a notice page, `dux server` adds a banner warning row plus a `dux.log` WARN, and the tests in `crates/dux-web/tests/static_serving.rs` that need a real build print a `SKIPPED` reason and return instead of passing. Because a skipped test is itself a hiding place, `pr.yml` and `release.yml` both fail fast when `DUX_DISABLE_UI_BUILD` is set, and `release.yml` additionally starts the packaged archive (`.github/scripts/smoke_archive.sh`) before uploading it. The real-build assertion is "the served page references a content-hashed bundle AND that bundle downloads"; a doctype and a root element are not evidence of a build, which is exactly why the old assertion passed on the placeholder. Contributor-facing docs for all of this live in `CONTRIBUTING.md`.
