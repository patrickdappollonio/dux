# CLAUDE.md

## Design Tenets

Principles that guide every decision in dux. If a change conflicts with a tenet, the tenet wins.

### Configuration

- **All settings are configurable.** Every single one. If a user can't change it, it shouldn't be hardcoded.
- **The config file is the documentation.** It must clearly explain what each setting does through inline comments. A user should never need to leave the config file to understand an option.
- **Project config is portable desired state, not runtime cache.** `[[projects]]` may store portable user intent (id, path, name, default provider, auto-reopen, startup command). Do not write runtime-derived git or agent state into config.
- **Keep derived project state in SQLite.** Branch status, worktree paths, agent branch names, and provider process/session state belong in SQLite/runtime memory only. Saved config must omit derived values like the leading branch so autodetection is not pinned into portable config.
- **Startup command execution shell is global config, not project state.** Project config owns the command text; the global `[startup_command_terminal]` section owns the shell used to run it.
- **Config wins for explicit project preferences.** When a project exists in both config and SQLite, explicit config values for safe preference fields update SQLite on startup/reload. SQLite may fill missing config fields but never overrides a value the user wrote. Reserve hard sync conflicts for genuine identity ambiguity (duplicate ids or paths that disagree).

### UI and Navigation

- **New UI must use the theme engine.** Every screen, pane, dialog, and visual state derives colors and styles from `Theme`/`theme.rs`, never hardcoded values. Reuse an existing semantic field when it matches the meaning; add a new one only when none does, and wire it through every supported theme in the same change.
- **Tab and Shift-Tab navigate between panes.** This is the primary spatial navigation model.
- **Panes have local key combinations.** A key combo bound in one pane does not necessarily work in another.
- **Panes have interactive and non-interactive modes.** In interactive mode all key combos (including global ones) are suppressed and input is forwarded to the PTY. In non-interactive mode both local and global combos are active.
- **Key combinations are documented in the help page.** The in-app `?` overlay is the authoritative reference. External docs describe how to configure bindings, not enumerate them.
- **Line-scroll keys are gated by context.** In interactive (PTY) mode, arrow keys and Space only scroll when already scrolled back; otherwise they pass through to the child. Non-interactive views scroll unconditionally. Page-scroll keys always initiate scrolling.
- **Movement keys move focus; Space and Enter act on what has focus.** Movement keys never change a value. Space activates the focused button or checkbox in every dialog (a universal accessibility convention, not a configurable binding), and types a space when a text field has focus. Any modal with more than one focusable control needs an explicit focus concept, and the focused control must visibly render as focused. Bindings are user-configurable, so never name specific keys for these roles in code, copy, or docs; resolve them through the bindings.
- **Every modal declares its family in the registry.** `crates/dux-tui/src/app/modal.rs` holds an exhaustive registry with no wildcard arm: a new modal does not compile until it is assigned one of four families, derived from what a keystroke means, not how the modal looks. Report (read-only, scrollable, no focus), Confirm (prose plus buttons, movement moves focus), Picker (rows with a selection cursor; picking confirms, so no button pair unless the buttons are genuinely distinct actions), Form (fields plus buttons; horizontal keys belong to the caret). A modal's family may depend on its state, not just its variant.
- **A modal with a full-text (multiline) field must have a confirm button; a modal with only single-line fields must not need one.** In a multiline field Enter is content, so the form needs a button to say "done"; in a single-line form Enter submits unambiguously. The registry enforces this and the known-violations list is empty and must stay that way. This is house style for modals, not a logical necessity.
- **A shared component probably already exists; ask before you invent one.** The modal chrome, focus ring, key ladder, click routing, hint bar, and text input are all extracted in `crates/dux-tui/src/app/components/` and `modal.rs`. A second copy of any of them is the drift this rule exists to prevent.
- **All text entry goes through the one shared `TextInput`.** It owns caret motion, word motions, and multiline scrolling. Never hand-roll a buffer; a new typing surface gets a `TextInput` field, not a `String` you push characters onto.
- **Two kinds of text field, told apart by a real flag.** Single-line fields have no mode: typing is immediate and the arrow keys must reach the caret, so the binding lookup is suppressed while one has focus (otherwise an arrow key silently triggers whatever it is bound to; that bug shipped). Multiline fields have an explicit engage step tracked as a mode: unengaged, the modal owns every key; engaged, every key goes to the text and the exit-edit binding leaves the modal open. Engaging is always an explicit act, never a side effect of typing. The reason for the mode is Enter, which is content in a multiline field and the confirm key everywhere else; it is not Tab.
- **An unengaged field must look unengaged and say how to start.** Focus and engagement render differently: focused-but-unengaged gets the focus border and no caret, and the footer names the engage key. Both surfaces go through the shared field-frame renderer.
- **Filters, search rows, and the command palette are deliberately type-immediately.** Keystrokes go straight into their `TextInput` with no engage step. Adding a mode to a search box is friction, not consistency.
- **Escape never saves.** It abandons, or it exits edit mode.
- **A field the user cannot click into is a gap.** Every caret-bearing field publishes its rect into the overlay mouse layout so a click can land the caret. Caret positions are display columns, never byte offsets or char counts; use the shared column/byte conversion helpers, and render single-line fields through the shared renderer, which is char-safe and takes a focused flag.
- **Clickable controls need misclick-safe spacing.** Separate adjacent click targets enough that an imprecise click cannot activate a different item.
- **Animations and periodic refreshes use wall-clock time, not tick counts.** Use elapsed real time so animations stay smooth regardless of tick cadence.
- **The embedded-PTY caret is the host hardware cursor, never a painted block.** The OS anchors CJK IME composition popups to the hardware cursor, and pre-painting the cell breaks hosts that draw their cursor by inverting it. The caret look is the host terminal's cursor and is not theme-colored; that tradeoff is intentional.
- **The TUI does not disambiguate Shift-Enter; Ctrl-j is the supported soft-newline key.** Interactive input is a verbatim passthrough, and pushing Kitty keyboard-enhancement flags would re-encode every key for the child, breaking providers that don't speak the protocol. Users who want Shift-Enter can run dux inside a terminal or multiplexer that already speaks the Kitty protocol. Only the web UI rewrites Shift-Enter, because there the key event is available before encoding.

### Web UI (server mode)

The web UI (`crates/dux-web/web/`, React + Vite + Tailwind) has its own conventions, distinct from the TUI's theme engine. It is currently dark-only. Style through the shadcn/base-ui token CSS variables, never hardcoded colors.

- **Components: shadcn/base-ui first.** Reuse an existing `components/ui/*` primitive before hand-rolling one. Hover hints go through the shared tooltip component, never a native `title=`.
- **Row actions collapse into one `⋯` menu.** A list row needing more than one action gets a single dropdown menu behind an ellipsis trigger that reveals on hover, consumes no layout space when idle, stays revealed while its menu is open, and always shows on touch. Every menu item carries a leading icon; a trailing `…` marks any item that opens a dialog or needs confirmation. Destructive menu items default to neutral color: the ellipsis and the confirmation dialog are the danger signal. (The agent menu's Delete entry is the one deliberate red exception; do not propagate it without a deliberate decision.)
- **Destructive actions always confirm.** A destructive item opens a dedicated dialog (Cancel autofocused, destructive-styled confirm, misclick-safe spacing), following the existing per-action dialog pattern. Target-keyed dialogs close themselves when their entity vanishes from the live view model. A monitoring surface confirms its stops too: being a screen about destructive actions is not a licence to act on one click. Keep confirms cheap to dismiss so the hung-agent escape hatch stays fast.
- **Shift-Enter inserts a soft newline, not a submit.** The terminal pane intercepts it at the key-event layer (the data layer cannot distinguish it), the decision lives in pure, unit-tested helpers in `lib/termkeys.ts`, and it never rewrites a keystroke mid-IME-composition. Only the input owner writes the newline. The mobile accessory bar carries a dedicated soft-newline key; both entry points share one write helper so their behavior cannot drift.
- **Width decides the layout; the pointer decides the typing surface. Two separate rules.** The mobile breakpoint picks which shell you get. Pointer coarseness picks whether typing goes through the buffered compose bar (where autocorrect, swipe, and IMEs have something to work with) or directly into xterm. They are orthogonal: a tablet in landscape gets the desktop layout and still gets the compose bar.
- **The compose bar is the typing surface wherever a finger types; xterm is never typed into directly while it is on.** Send delivers the body as macro-style keystrokes with the submitting Enter travelling separately and delayed (deliberately not bracketed paste: the wire keeps "line break" and "Enter" distinct); an empty Send is a single bare Enter for confirming TUI menus. Draft state outlives the bar, so rotation or a preference flip never destroys a draft, and a refused send keeps the buffer and toasts why. Non-owners get no typing surfaces. The gating preference's `auto` mode alone consults a transient, locally-stored toggle in the accessory bar, because the browser cannot tell a tablet with a keyboard case from one without; the toggle writes nothing to config. The virtual input is the textarea PLUS the key rows (Esc, Tab, soft-newline, Ctrl/Alt, arrows, PgUp/PgDn): they appear and disappear together on the pointer, never on the layout, and the only state where they diverge is keys hidden while the input stays (the accessory-bar preference), which is why the way back to the keys renders wherever the keys themselves would.
- **`lib/notify.ts` is the one place that raises a notification, and a boundary test keeps it that way.** No other module imports the toast library directly. The library stays the countdown mechanism; dux owns the policy. A toast id means replacement, not de-duplication, so repeat-raising on a fixed id pins a toast open. The configured display window lives inside the raiser, not at call sites, so it can never be captured stale. The standalone editor tab shows only what it raised itself or what the wire addressed to its own connection, and it carries no attention count: workspace-wide messages live in the workspace tab.
- **Every toast dismisses itself on a severity-graded window derived from the one configurable base, except the few marked sticky.** Sticky is a boolean orthogonal to tone, reserved for when the user must act outside the toast to recover or something may be lost or left half-done; keep the sticky population in single digits, and when in doubt record at the site that it was weighed. Busy toasts need their own retirement guard because the library refuses to retire a loading toast, timed to fire only after the engine's own busy timeout would have upgraded a stranded spinner. Severity reads at a glance through icon color and shape (never color alone), and swipe dismisses because the close button is not a touch target.
- **One marker for git status.** Every changed-file status marker renders through the shared `FileStatusIcon`, backed by the one pure status-interpretation helper. Never re-implement it inline.
- **Touch targets have a 40px floor, and any exemption is per axis and justified at the call site.** The floor exists so an imprecise tap cannot hit a different control. A control may shrink along an axis only when every neighbour on that axis is non-interactive, absorbs a stray tap harmlessly, or is separated by measured clear spacing, and it keeps the floor on the other axis. A bare smaller class with no comment naming the neighbours is a bug, not an exemption.
- **A control's height is set explicitly, never inherited from padding or content.** Controls that sit together share one height token and vary only in width. On phones prefer icon-only, except where the text is data (a count, a size). Verify group heights are identical rather than asserting it.
- **An action cluster shares one variant (outline); navigation stays quieter.** A control that navigates rather than acts may match the cluster on geometry and differ on weight, but decide and write the reason at the site.
- **The working-agent icon bob is required and must settle back to rest.** It animates only while the agent works, and when work stops it eases back to the rest position rather than freezing mid-cycle (keep the transition class paired with the conditional animation class). The bob and the name shimmer fire on the same flag so they stay in lockstep.
- **Terminal clipboard is wired explicitly and follows the classic-terminal model: selecting copies, right-click pastes, no context menu.** xterm's defaults would leak the paste chord to the remote machine's clipboard, so the pane owns clipboard. Classify clipboard chords by physical key, never by `ev.key`, or non-Latin layouts reopen the leak. When the app in the PTY has mouse reporting on, a drag is forwarded instead of selecting locally; a force-local-selection modifier is the escape hatch and a one-time hint toast points at it. The suppressed native context menu requires wiping the selection xterm stuffs into its hidden input, for every pointer type. Keep all of this when touching `TerminalPane.tsx`.
- **A finger selects text with a long press, and dux drives xterm's selection model itself.** The browser can neither select inside the terminal nor synthesize mouse events for a touch drag, so the pane selects via xterm's public API, drags re-select, and the lift copies through the same copy-on-select preference while cancelling the browser's synthetic events. The arithmetic and word rules are pure in `lib/termselect.ts` and reuse xterm's own word-boundary behavior, because a long press and a desktop double-click are the same intent. A long press always selects locally, even under mouse tracking.
- **A forwarded touch gesture is a replayed DOM event, never a mouse report dux encodes itself.** Mouse protocol and encoding are negotiated by the app and xterm publishes no read of them, so `lib/termmouse.ts` plans DOM events and lets xterm resolve the cell and encode with whatever was negotiated; tapped hyperlinks are resolved the same way in `lib/termlink.ts`. Subscribe to both data and binary output streams or some protocols' reports are dropped. A forwarded touch-scroll sends at most one wheel notch per touch-move, reproducing desktop wheel cadence; magnitude bursts corrupt real TUIs' repaints. Local scrolling of xterm's own scrollback keeps the full magnitude.
- **The soft keyboard is handled by the browser, not JS, and the web UI has no fullscreen mode.** Every directive on the viewport meta in `index.html` is deliberate and measured (keyboard-resize behavior, safe-area insets, suppressing the input-focus auto-zoom without harming accessibility zoom). Do not reintroduce the browser Fullscreen API, Keyboard Lock, or a fullscreen toggle: on Android the Fullscreen API hard-clips against the keyboard-shrunk viewport, and the shortcuts it captured have in-app equivalents. The TUI's fullscreen pane is separate and unaffected.
- **The URL is the source of truth for position, and nothing navigates relatively.** The hash names the whole position; state-to-URL is the normal direction. Moves within a screen replace, screen changes push, so Back always visibly moves. In-app chevrons are Up controls that push a named destination, never `history.back()`: a relative step has no floor and can walk out of the app. A URL naming a missing agent renders a truthful not-found screen (never a silent fallback to home), retired automatically when the agent reappears; vanished ephemeral targets fall back out loud, rewriting the URL.
- **A reconnect onto a different run of the server hard reloads the page, and that is the only reload in the app.** The server publishes a version and a once-per-run process id; either moving on reconnect reloads with no prompt, because a stale page is wrong exactly where nobody looks. An unknown answer is not a change, so a flaky network never reloads. Keep it narrow: this identifies the server run, and must not grow into a schema version.
- **Settings live in exactly one place: the Preferences dialog.** A preference is a row in the settings descriptors, not a menu item; the app menu carries actions and dialogs. A preference needing a write side effect gets a bespoke write target routed to the existing dedicated endpoint, never a fork of the generic settings patch.
- **The Add-project control is a split button, and the starter-.gitignore list is deliberately not a setting.** Both surfaces share one menu-items component. The seed list for newly initialized repos is a compile-time constant extended via PR, a deliberate, documented exception to "all settings are configurable" (a config surface would invite unreviewable divergence in what dux writes into users' repos).
- **One menu definition drives both presentations.** `lib/appMenu.ts` is pure data; the desktop flyout and the mobile bottom sheet both render it and neither hand-authors items.
- **Dropping a file saves it and pastes its path; it never sends the file's bytes, and the upload route never writes to a terminal.** No agent CLI reads a file from its input stream, and injecting text server-side would bypass the input-ownership gate on the socket, so the browser pastes the returned path over its own already-gated connection. File names are validated, never rewritten; creation is symlink-refusing relative to a pinned directory handle; collisions get suffixed, never overwritten.
- **The drop destination follows the intent of the pane.** A drop on an agent means "look at this": it lands in a hidden, self-gitignoring upload directory inside the worktree (so CLIs can read it and deletion is free; directory name and gitignore seeding are configurable). A drop on a terminal lands in the shell's live working directory, discovered from the process at drop time. A drop on the editor's file tree means "add this to my project": an ordinary visible file in the directory pointed at, never the upload directory, never a paste into a terminal. All three share the one upload route; the tree destination is stricter (it creates nothing and refuses symlinked components).
- **How the pasted path is quoted is a per-provider config setting with measured defaults, and the paste length limit is keyed by the command being run.** Receiving CLIs genuinely disagree about how they read a pasted path, so the form is config, not code; the length cap is a measurement of a third-party CLI, so it stays a compile-time table keyed by the command's file name, never the provider's free-text block name. A plain terminal always gets a quoted path, because a shell is the reason it must be quoted. What a running process launched with wins over config while it runs; each half reaches the browser on the event that can change it.
- **One toast per drop, with an explicit sticky decision per rung.** The outcome ladder is nothing-saved / saved-but-not-sent / refused / success; only the rungs where something may be lost are sticky (a saved file whose path exists nowhere else on screen, a cancelled paste whose text is now only on the clipboard).
- **Pasting an image, and pasting text past the configurable size threshold into an agent pane, are the same journey entered by different gestures.** Both reuse the route, the form, the limit, the naming, and the one toast; the pure decision lives in `lib/clipboardPaste.ts`, reading the paste event (never the async clipboard API, which is blocked on the plain-HTTP origins dux routinely serves on). An image wins over text in the same event; a force-text chord bypasses both behaviors; long text pasted into a terminal stays verbatim at any length, because it may be a command or heredoc. The threshold counts code points and is conservative on purpose. Ownership and socket state are rechecked immediately before each paste, and the toast must say where the path actually landed (sent to the agent versus joined a compose draft). Web-only: a real terminal emulator already types a dropped path for you.
- **In-browser file editing is web-only, and the TUI gets no counterpart.** The editor exists for editing on the go; anyone at a terminal already has vim. The TUI's answer is open-worktree.
- **A move is a modal, it is a rename on the wire, and an occupied destination is refused, atomically.** There is no separate move route (a second endpoint would let the containment guards drift) and no overwrite-with-confirmation, because there is no trash behind it; the refusal uses a no-replace rename, not a racy stat-then-rename. Moving a symlink moves the link (the entry, never the target); a destination reached through a symlinked directory is still refused. Destination browsing reuses the same lazy tree endpoint as the explorer.
- **The editor's info panel is the one dialog with a live truth to close itself on.** It distinguishes "gone" (dismiss) from "refused" (stay and say why), stats the link itself rather than the target, and refreshes on exactly two events: opening, and the window regaining focus. There is no poll; a file deleted while the tab stays focused is not noticed, and that gap is accepted and stated. Git status has a variant per genuinely different answer, including ignored paths and nested repositories, because `git status` is silent rather than reassuring about both.

### Agents and Providers

- **A provider is supported if and only if it supports PTY mode.** dux embeds the CLI's interactive session in a pseudo-terminal; that is the only thing a provider has to support.
- **Any CLI tool can be a provider.** Configure `command` in `config.toml` and dux spawns it. No adapters, no protocol layer. Adding a new provider is a config-only change, not a code change.
- **Claude, Codex, OpenCode, and Copilot are the defaults.**
- **No protocol layer.** No JSON-RPC, no custom message format, no adapter binaries. The CLI runs exactly as it would in a normal terminal.

### Agent Tabs

- **A tab is a provider session inside the agent's one shared worktree, not a new worktree.** One agent session (one branch, one sidebar row) hosts N provider tabs; every tab edits the same files. The strip carries provider tabs only (companion terminals never fold into it), renders only when there are two or more tabs, and tabs are never separate sidebar agents.
- **All tabs are generic; there is no Main/Support distinction.** The one internal invariant is the session-slot tab, the tab whose id equals the session id and which has no table row of its own. It keeps every session-keyed runtime lookup working and must never surface to the user as privileged.
- **Resume is decided dynamically by liveness, per provider, in exactly one place.** A launching tab resumes the provider's prior conversation only when it is the sole live-or-launching tab of that provider in the session, because a provider's conversation history is directory-scoped and per-provider. The decision lives in `Engine::tab_resume_decision` and every launch and reopen path routes through it; do not reintroduce a positional or first-tab notion of resume.
- **Closing a tab ends that tab; closing the last live tab detaches the agent.** Closing an extra tab deletes its row (destructive, so confirm it); a clean exit closes the tab by itself with no confirm, because nothing is lost (conversation history lives in the worktree). A non-zero exit keeps the dormant tab as the crash-diagnosis surface. The distinct agent-level detach action tears down every tab at once. Extra tabs render in creation order and never reorder.
- **Restart brings tabs back dormant, not running.** Each tab reopens as a pill with no process; only an explicit action launches it (focus alone never launches, and on the web a dormant tab must render without opening the PTY socket, because subscribing force-launches). The launch's resume eligibility follows the same dynamic rule as any other launch.
- **Tab state is derived runtime state: SQLite, never config.** Extra tabs persist in an additive `agent_tabs` table; the session-slot tab has no row.
- **Runtime provider state is keyed by tab id, with the session-slot tab id equal to the session id.** Sidebar liveness ORs across all of an agent's tabs; auto-reopen intent stays agent-level. A tab exiting while siblings live shows a quiet tab-scoped message, never the workspace-wide agent-exited warning, which fires only when the last live tab exits.
- **Tabs honor each surface's existing UI tenets.** TUI: themed through `theme.rs`, switch keys work in non-interactive mode only, and the strip is not rendered in fullscreen. Web: deep-linkable pills reusing the shared menu, confirm, touch-target, and working-bob tenets. New tabs default to the project provider and start fresh; provider is per-tab, retargeted for the next launch; a configurable per-agent cap applies.

### Terminals

- **A terminal is owned by exactly one owner: an agent session, a project, or nothing at all.** Session-owned terminals spawn in the agent's worktree, project terminals at the repo root, standalone terminals in the user's home directory. Ownership never changes after spawn. Standalone is a real variant, not an option or sentinel, and every ownership question is answered by an exhaustive method on the owner type (both in Rust and in the web's owner helpers), so a fourth kind is a compile error everywhere it must be answered for.
- **A standalone terminal opens in the home directory, falling back to `/`.** What is resolved is a usable directory, not merely a path, because the value goes straight to the spawn; an unusable or unresolvable home takes the fallback rather than refusing. Never retry a failed spawn at `/`: a missing shell is a configuration problem the user must see. It gets the global environment with no project overlay, is addressable at un-nested routes (which serve standalone terminals only), and is named a "standalone terminal" wherever it must be named; its row names its spawn directory (home-collapsed), which travels on the wire because the browser may not be on the server's machine.
- **Terminals are runtime-only.** No SQLite row, no config entry, no restore across restarts. Existence equals a running PTY.
- **Project and standalone terminals do not run the project's `startup_command`.** That command is a worktree provisioning step for new agents; a terminal is a plain shell.
- **Removing a project closes its project terminals; deleting an agent closes that agent's; nothing closes a standalone terminal automatically.** The last is a decision, not an oversight, and is documented beside both close paths so nobody later "fixes" the omission. Detaching an agent leaves its terminals running.
- **A terminal row is an agent row.** It renders through the same shared row component and idiom on both surfaces (the framed two-line row, the same selection painting), never through a lesser single-line item. The row contract is two lines of `[glyph] [left text that ellipsizes] … [right text that survives]`; when the agent row's framing changes, the terminal row moves with it because they share the code.
- **A terminal has three states only: idle, running, typing.** Never detached or needs-attention (a live PTY is alive or gone). Priority mirrors the agent row; the busy word is "Running" rather than "Working" on purpose. A terminal is busy when it is streaming output or a foreground app is running in it, even while quiet; the predicate lives once in the engine so both surfaces agree.
- **Typing is a real keystroke; a forwarded pointer report is neither typing nor evidence of work.** One classifier in core sorts every PTY write into typing, pointer, or ignored, and both surfaces route through it. A pointer report makes mouse-tracking children repaint, so while the pointer window is fresh the engine stops inferring "working" from output text and defers to the agent's own progress reports; the suppression window is per gesture (longer for wheel, short for click, none for motion). Only the streaming inference is suppressed, never the foreground-app fact.
- **State colors are theme-derived, and Idle is the only unstyled state word.** Busy is green, typing violet, detached amber, needs-you cyan, on both surfaces through semantic tokens. Line one (glyph plus name) carries no live-state color: the operating cue is animation (spinner plus name shimmer), not color, and the animation cadence is paid only while something animates.
- **Every sidebar element carries a position; both surfaces sort terminals by the active sort mode.** Terminals get a runtime-only sort order and their own reorder command; the sort comparators are duplicated per surface and must stay in lockstep. The web's Terminals section is a collapsible divider defaulting open (a live terminal is worth surfacing, unlike dormant agents).

### Git and Data Safety

- **Worktrees are user data.** Never removed or mutated casually. Deletion requires explicit user confirmation.
- **Git operations are conservative.** Source checkout refresh uses `--ff-only`. Destructive operations require confirmation.
- **Commit messages are plain sentences.** No conventional-commit prefixes, no structured trailers unless the user explicitly asks.
- **Prefer explicit failure over silent waiting.** If something fails, say so immediately with context.
- **A refname is a positional, so every git call that takes one needs `--`.** A dash-leading branch name in a positional slot is read as an option, git obeys it and exits 0, and dux reports success for the wrong operation. Such names really do reach dux (plumbing creates them, and non-leading components may lead with a dash). Two measured exceptions where `--` is not enough, because a porcelain command consumes the separator and forwards the positional to an inner command without one: `git worktree add` (resolve the start point to an object id first) and `git pull` (pass a fully qualified `refs/heads/` refspec, which cannot lead with a dash). When a separator does not visibly work, measure what the subcommand does rather than assuming; every case gets a test in the existing option-looking-name family in `git.rs`.
- **Every file dux keeps for itself is owner-only, and the config root's own mode is what actually enforces it.** Per-file modes are defence in depth; the directory is the boundary, because SQLite creates its sidecars with modes dux cannot choose. The one place that decides any of this is `crates/dux-core/src/file_modes.rs`; never chmod at a call site. Tightening only clears group/other bits (idempotent, safe every startup), is best-effort (a mode dux cannot set is a warning, never a reason to stop logging or refuse to start, and best-effort error paths get tests), and never follows a symlink. dux does not tighten the user's own data (worktrees, the lock, user-created theme directories); a change that starts must be argued for. Note that "a read-only config stays read-only" is a claim about the tightening pass only: the atomic config write replaces the file and resets its mode, and both user-facing surfaces say so.

### Tone

- **Welcome tips are playful and sassy.** They should feel fun, not like a manual. Lead with surprise or delight, highlight non-obvious features that differentiate dux, and keep keybinding references secondary to the feature discovery. Avoid dry "press X to do Y" phrasing.

### Quality

- **Prove your work with tests.** Every change should include unit tests. When feasible and low-lift, add integration tests as well.
- When debugging a problem, before fixing it, **aim to prove your findings with a unit test**.

## Project Summary

`dux` is a Rust terminal UI for orchestrating AI coding sessions per git worktree.

The current app provides:

- A left pane for projects and agent sessions
- A center pane showing the agent's terminal output (embedded via PTY) or diff viewing
- A right pane for changed files and diffs
- Commented user config in the platform-specific dux config directory (`~/.dux/` on macOS, `~/.config/dux/` on Linux)
- Session persistence in `sessions.sqlite3` alongside the config
- Logging in `dux.log` alongside the config
- PTY-based agent startup: spawns CLI tools (`claude`, `codex`, `opencode`, `copilot`) directly in a pseudo-terminal

## Important Constraints

- The app spawns CLI tools directly via PTY (portable-pty) and renders their output using an embedded terminal emulator built on alacritty_terminal. There is no protocol layer (no ACP, no JSON-RPC).
- Long-running actions should not block the UI thread.
- All periodic or potentially-blocking work (git commands, file I/O, network) must run in background workers, never on the main UI thread. Even fast operations like `git symbolic-ref` should use workers to prevent UI freezes if the filesystem or git lock stalls.
- Async operations must keep the status line updated for the full operation lifecycle: set a Busy message when the worker starts, then replace it with a clear success or failure message when the worker completes. Do not start background work silently.
- User state lives under `~/.dux/` on macOS and `$XDG_CONFIG_HOME/dux/` (or `~/.config/dux/`) on Linux.
- **The web server (server mode) is single-tenant / trusted-access by design.** There is no login. The server binds loopback by default and optionally a Tailscale address; access control is delegated to loopback scope, Tailscale ACLs, or an upstream proxy. A Host-header allowlist and same-origin check guard against DNS rebinding and cross-site requests. Every client shares one workspace: it can drive any PTY, browse the server's filesystem, and see every session. This is intentional for a per-developer or trusted-team tool. Do not add features that assume mutually-distrusting web users without first designing a real per-user isolation model.
- Worktrees are user data and should not be removed or mutated casually.
- Git operations should be explicit and conservative, especially around the source checkout.
- **Target platforms are macOS and Linux only.** Windows users run dux through WSL2, which is Linux. Do not add `#[cfg(windows)]` branches, `cfg!(windows)` checks, or Windows-specific code paths. Assume Unix throughout.

## App Module Structure

The `crates/dux-tui/src/app/` directory splits the TUI into focused submodules. Each file contains an `impl App` block for a specific concern:

- **`mod.rs`**: `App` struct, types, enums, bootstrap, run loop, and state helpers. Read this first to understand the data model.
- **`input.rs`**: All keyboard/mouse event handling (`handle_key`, `handle_left_key`, etc.).
- **`render.rs`**: All rendering methods (`render`, `render_header`, `render_left`, etc.) and UI helper functions.
- **`sessions.rs`**: Project and session CRUD (create agent, delete, reconnect, refresh, project browser).
- **`workers.rs`**: Background thread management (`drain_events`, `spawn_*`, `run_create_agent_job`).

When making changes, edit only the relevant submodule. If you need to add a new method to `App`, place it in the submodule that matches its concern. If adding a new type or enum, add it to `mod.rs`.

## Recommendations For Future Changes

- Keep the status line centralized. New async operations should report progress through the shared status API, not ad hoc strings.
- The core keyed status controller (`dux_core::statusline`) is the single source of truth for engine status across the TUI and the web. The TUI renders it as a single most-recent-wins status line; the web renders it as toasts, one per open keyed status. Correlation is by per-operation key: a Busy and its eventual final carry the same key so the surfaces replace or dismiss the right entry. Every Busy must be followed by a final; a keyed Busy left open expires to a warning. Do not add a third surface, and do not emit an unkeyed Busy for a multi-step web operation.
- The controller has two retention policies, chosen at construction, because the surfaces ask different questions: the TUI retains statuses for its single line, while the web emits finals as events, retaining them only for a short fixed replay window so a reconnecting client still learns the outcome without every new page load replaying hours-old errors. The window is deliberately a constant, not the user's clear-seconds setting: how long a status stays replayable and how long a toast stays on screen are different questions. The doc comments on the controller carry the full reasoning.
- Status line messages must be verbose and actionable. Do not write terse messages like "Done." or "Pushed."; explain what happened and, when relevant, what the user can do next.
- Code must be production ready and modular to allow future Open Source contributors to integrate new features with ease. Do not take shortcuts.
- Route new modal UI through `PromptState` so `Esc` keeps working uniformly.
- Prefer command-palette actions over adding many more global hotkeys. This is per surface: in the TUI that means the `Ctrl-p` palette; the web has no palette, and its equivalent home is the cog app menu, which deliberately has no keybinding of its own. Do not add a global web hotkey to reach a menu action; add the action to the menu.
- Keybinding labels shown to the user should use proper casing (e.g. `Ctrl-g`, not `ctrl-g` or `CTRL-G`). The `^X` notation is acceptable in footer hint bars since its meaning is explained in the help overlay.
- Keybinding parsing from config is case-insensitive for modifiers and control keys; letter keys are lowercased during parsing, so binding uppercase requires an explicit `shift-` prefix.
- Never hardcode keybinding labels in user-facing strings. All keybindings are user-configurable; always look up the actual binding via `RuntimeBindings::label_for()` so labels stay accurate after rebinding. The only exceptions are pure text-input contexts and palette-only command names.
- Keep agent creation and other blocking git/provider work in background workers.
- The PTY approach is CLI-agnostic: any terminal command can be used as a provider. Keep it generic.

## Keeping Documentation In Sync

- When adding, removing, or changing keybindings, update `README.md` if it documents controls or shortcuts.
- **The TUI has a command palette; the web has an app menu. Never conflate them in docs or UI copy.** The TUI palette opens with a rebindable key; the web menu is a button, reachable by Tab, with no keyboard shortcut. When docs must name a key, scope the sentence explicitly to a surface. Never suggest `ctrl-k` as a TUI rebind example (terminals commonly treat it as readline's kill-line).
- **The two surfaces are independent, so keep them in step by hand.** `dux_core::palette` is the source of truth for the TUI palette only; the web app menu is defined client-side in `lib/appMenu.ts`. When you add a palette command, decide explicitly whether it warrants a web app-menu entry, and say so in the PR: a global, parameter-free command usually does; a per-entity one usually belongs in the web's row menu instead. Nothing fails if you skip this, which is exactly why it must be a deliberate step.
- When changing features, pane layouts, config paths, or provider behavior, verify that `README.md` still accurately describes the application.
- The README intentionally omits a full keybinding reference. The in-app `?` overlay is the authoritative reference; documenting how to configure keybindings is fine, enumerating them is not.
- The marketing/documentation site lives in `website/` and is published to `getdux.app`. When a change affects anything the site describes or shows, update `website/` in the same change. Match the site's playful tone, avoid counting features in headings, avoid enumerating keybindings, and make sure copy referencing real values reflects what the app actually does.
- No half-width prose unless something sits in the other half: a width-capped section intro with nothing beside it is a column of text and a hole. If a full line reads too long, shorten the copy or add a real second column.
- In `.astro` templates, write the space between a closing inline tag and adjacent text explicitly as `{" "}`; Astro eats the line break after a closing inline tag and welds the words together, the build succeeds, and nothing warns you. There is deliberately no automated check (the checkable half produced mostly false positives); catch it by writing it correctly and looking at the rendered page.
- The docs section at `getdux.app/docs` is generated from plain Markdown in `website/docs/`; add a `.md` file with `title`, `description`, `group`, and `order` frontmatter and everything else is derived. When a feature change touches anything a docs page explains, update the Markdown in the same change.

## Recommendations For Debugging

- First check the `dux.log` file in the dux config directory (`~/.dux/` on macOS, `~/.config/dux/` on Linux).
- Confirm whether the provider command in `config.toml` is installed and on PATH.
- If agent creation fails, determine whether it stopped in:
  - worktree creation
  - PTY spawn (command not found)
  - PTY process early exit
- If the UI appears frozen, verify the operation is on a worker path rather than the main event loop.

## Git Command Safety

When shelling out to git, **always ensure the command output is immune to user-specific git configuration**. User settings like `color.diff`, `diff.noprefix`, `status.branch`, `status.renames`, `core.quotePath`, and others can alter output in ways that break parsing.

- **Prefer plumbing commands** (`cat-file`, `rev-parse`, `for-each-ref`) over porcelain when you need machine-readable output. Plumbing commands are guaranteed stable.
- **Use `--porcelain`** for `git status`. Never use `--short`; it is affected by user config.
- **Prefer `--porcelain=v1 -z` when parsing status paths.** Parse NUL-delimited records so spaces, quotes, Unicode, and embedded newlines in paths are handled safely.
- **Use `--numstat`** for line-level diff statistics; prefer `--numstat -z` when parsing file paths from diff stats, especially rename and copy records.
- **Override config with `-c`** when a porcelain/plumbing alternative doesn't exist (e.g., `git -c color.diff=false diff`).
- **Imperative commands** that aren't parsed (`worktree add`, `branch -D`, `pull`) are fine as-is; rely on exit status rather than parsing their stdout.
- **Do not parse human-facing commands like `git branch --show-current` when a plumbing-style alternative exists.** Prefer `symbolic-ref --quiet --short HEAD` or `rev-parse`.
- **Avoid shelling out to `git diff` for display**; the project computes diffs in-process using the `similar` crate and applies syntax highlighting with `syntect`. Use `git::file_at_head()` for the base version and read the working copy from disk.

## Recommendations For Editing

- Follow the existing `crates/dux-tui/src/app/` submodule pattern when adding new concerns. If a new feature area grows beyond ~200 lines, extract it into its own submodule with `use super::*;` and an `impl App` block.
- Keep changes scoped to one submodule at a time; avoid cross-cutting edits across multiple app submodules in the same PR when possible.
- Use `theme.rs` constants for all colors and styles; never use raw `Color::*` values in rendering code. `theme.rs` is the single source of truth for visual styling.
- The canonical config renderer produces a fully commented config on first creation. Subsequent saves preserve user edits via `toml_edit`. Users can run `dux config diff` to see what changed or `dux config regenerate` to get the latest canonical template.
- **`dux config diff` is derived from the config structure; adding a setting requires nothing of you.** It compares the parsed file against the defaults structurally, so new keys are reported automatically; sensitive subtrees (env, projects) are summarized so tokens and local paths never reach the output, and there is deliberately no "ignore" policy. An exhaustiveness test mutates every leaf of the default config and asserts each is reported; do not weaken it. The `--raw` form prints the whole config, `[env]` values included: the plain summary is safe to paste into a bug report and `--raw` is not, and docs must say so.
- When a setting can have a sensible default at first boot, resolve and store the concrete value in `config.toml` right away; users should see a working value they can edit, not a placeholder.
- Preserve safe failure behavior around project refresh and failed agent startup.
- **Never use byte-based `.len()` or `[..n]` slicing to truncate user-visible strings.** Terminal output, paths, and UI text contain multi-byte UTF-8; byte slicing panics inside a multi-byte character. Use char-based counting and truncation.

## Verification

Use:

```bash
cargo fmt
cargo clippy --all-targets --all-features -- -D warnings
cargo test
```

`cargo clippy --all-targets --all-features -- -D warnings` is a CI gate; the same command runs on every pull request and fails it on any warning. Run it locally before committing. When a new stable Rust release enables lints that previously passed, fix the code rather than suppressing the lint unless there is a specific, documented reason.

For interactive smoke testing, ask the user to run `cargo run` as a final sanity check rather than running it automatically.

**Seeing the web UI: use the preview container at `tools/preview-env/`, never a directly-run dux.** It runs the host-built binary in an isolated Docker container with its own config, a loopback-only port, and a fake streaming provider, and screenshots via its scripts (see its README). Never run `dux server` or the TUI directly on the host to inspect UI work, and never kill dux processes on the host: a directly-run instance shares the developer's real config directory with their own live dux, so a stray instance corrupts shared state and a killed process can destroy the user's active session.

**The web UI is compiled into the binary, and a failed frontend build is a hard build failure.** The build script deliberately writes no placeholder and falls back to nothing, so a broken frontend cannot ship quietly. The escape hatch for Rust-only work is `DUX_DISABLE_UI_BUILD`, which skips the build rather than tolerating a failure; CI fails fast if it is set, and the release workflow smoke-tests the packaged archive. Contributor-facing detail lives in `CONTRIBUTING.md`.
