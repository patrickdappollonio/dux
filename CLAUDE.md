# CLAUDE.md

## Design Tenets

Principles that guide every decision in dux. If a change conflicts with a tenet, the tenet wins.

### Configuration

- **All settings are configurable.** Every single one. If a user can't change it, it shouldn't be hardcoded.
- **The config file is the documentation.** Inline comments must clearly explain every setting; a user should never need to leave the config file to understand an option.
- **Project config is portable desired state, not runtime cache.** `[[projects]]` may store portable user intent such as `id`, env-expanded `path`, `name`, `default_provider`, `auto_reopen_agents`, and `startup_command`. Do not write runtime-derived git or agent state into config.
- **Keep derived project state in SQLite.** `leading_branch`, `current_branch`, branch status, agent worktree paths, agent branch names, and provider process/session state belong in SQLite/runtime memory only. `leading_branch` may be parsed from older config files to repair SQLite, but saved/generated config must omit it.
- **Startup command execution shell is global config, not project state.** Project config owns the command text; `[startup_command_terminal]` owns the system-wide shell and args. Keep this out of SQLite and UI-only state.
- **Config wins for explicit project preferences.** Explicit config values for safe preference fields update SQLite on startup/reload. SQLite may fill missing config fields, but never overrides a value the user wrote. Reserve hard sync conflicts for identity ambiguity: duplicate ids/paths, same id with different expanded paths, or same expanded path with different ids.

### UI and Navigation

- **New UI must use the theme engine.** Derive all colors and styles from `Theme`/`theme.rs`; never hardcode visual values. Prefer reusing an existing semantic theme field; add a new one only when no existing meaning fits, wiring every supported theme/default mapping in the same change.
- **Tab and Shift-Tab navigate between panes.** The primary spatial navigation model.
- **Panes have local key combinations.** A combo bound in one pane does not necessarily work in another.
- **The agent pane has three input regimes: fullscreen (verbatim), windowed typeable, and non-typeable.** Fullscreen suppresses all key combos (including global) and forwards raw stdin bytes to the PTY verbatim, with only minimal byte-pattern intercepts (fullscreen toggle, scroll keys, macro bar). In the windowed typeable center pane (focused, showing a live tab): **chords belong to dux; typing belongs to the agent.** Ctrl/Alt chords, Tab/Shift-Tab and the page keys resolve as dux bindings; unmodified printables, Enter, Backspace, Delete, Esc, arrows and Home/End are encoded to bytes for the PTY. Two deliberate exceptions cross the chord line: Ctrl-c forwards SIGINT (quit stays reachable via `q` from any non-typeable pane and the palette), and Ctrl-\ opens the macro bar (also why `select_tab_4` ships unbound, see the tabs tenet). A literal "dux always wins" was unworkable: `q`, `?`, `[` and `]` are dux bindings AND ordinary characters, so plain letters must type. In every non-typeable state (unfocused pane, dormant or exited tab, diff view, any overlay or prompt open), local and global combos are active. **Typeability is a derived predicate, never stored state**: `center_typeable()` is computed from focus, overlay/prompt state, what the pane shows, and the focused tab's liveness, so nothing can desync. The windowed pane's crossterm-to-bytes encoding is the one deliberate, scoped exception to "the TUI never re-encodes keys"; fullscreen stays byte-for-byte. The confirm key with the pane focused TYPES into a live agent and LAUNCHES a dormant or exited one; a completed launch lands focused-but-minimized, and only fullscreen-seeking gestures (left-pane jump-to-fullscreen, fullscreen toggle on a dormant tab, double-click maximize, reconnect from fullscreen) land fullscreen. Losses while typing windowed are documented loudly: Tab completion and readline chords the dux bindings claim (word-erase, clear-screen, the palette key) do not reach the agent; fullscreen is the escape hatch. Bracketed paste is captured at both terminal setup sites: a paste lands in the focused typing surface (modal field, filter, palette, commit box; single-line fields collapse interior newlines to one space), or, when the center pane is typeable, goes to the PTY wrapped in `ESC[200~`/`ESC[201~` iff the child enabled mode 2004, else raw with newlines normalized to CR.
- **Key combinations are documented in the help page.** The in-app `?` overlay is the authoritative reference. External docs describe how to configure bindings, not enumerate them.
- **Line-scroll keys are gated by context.** In any typeable PTY surface (fullscreen and windowed typeable alike), arrow keys, Space, `q`, Home and End only scroll when already scrolled back (`scrollback_offset > 0`); otherwise they pass through to the child. Non-typeable views (diff overlay, dormant or exited agent pane, help overlay) scroll unconditionally. `PgUp`/`PgDn` follow the per-provider `forward_scroll` policy in BOTH windowed and fullscreen modes: on auto they forward to a child that owns the screen (an alt-screen, mouse-aware app) and scroll dux's host scrollback otherwise; `forward_scroll = true`/`false` pins either direction.
- **Space activates the focused button in confirmation dialogs.** Every modal with buttons must treat Space as Enter, executing the highlighted button. Hardcoded, not configurable: a universal accessibility convention. New dialogs must include it.
- **Movement keys move focus; Space acts on what has focus.** Movement keys (horizontal navigation keys, arrows, Tab/Shift-Tab) only ever MOVE FOCUS between a modal's controls, never change a value. Space toggles a focused checkbox, activates a focused button, types a space in a focused text field. Any modal with more than one focusable control needs an explicit focus concept (a `…Focus` enum on its `PromptState`), and the focused control must render as focused. Wiring a movement key straight to a value is the bug this prevents (`RenameSession`'s Tab flipped the rename-branch checkbox instead of highlighting it). Bindings are user-configurable: never name specific keys for these roles in code, copy, or docs; resolve through the bindings.
- **Every modal belongs to one of four families, and the registry makes you say which.** `crates/dux-tui/src/app/modal.rs` holds `modal_spec`, an EXHAUSTIVE match with no `_` arm over every `PromptState` variant; a new modal does not compile until a family is chosen on purpose. Families are what a keystroke MEANS, not how the modal looks:
  - **Report**: read-only, scrollable, no focus concept. (Agent Info, Add-Project-Failed, First Load, Help.)
  - **Confirm**: prose, two buttons, sometimes a checkbox. Horizontal keys move FOCUS and change nothing; Space and Enter act on whichever control has it.
  - **Picker**: rows with a selection cursor, maybe a filter. Up/Down move the SELECTION (a value, not focus); Enter picks. A picker confirms by PICKING and needs no buttons (the three provider pickers lost their Cancel/Apply pair; now one `App::handle_provider_picker_key` selected by `input::provider_picker_kind`). The kill-running dialog is the one picker with footer buttons, kept because they are DISTINCT ACTIONS, stated at its render site. Removing a picker's Apply button: check what else it was saying; the provider one's greyed-out "already active" cue moved onto the row as a text marker, because `Theme::selection_style` patches over the row's own style and a dimmed row loses the cue exactly while highlighted.
  - **Form**: fields plus buttons. Horizontal keys belong to the CARET and must never reach the binding lookup (`keybindings::text_field_owns_key`).
  `EditMacros` is deliberately state-dependent (Picker while its list shows, Form once an edit opens, Confirm during its nested delete-confirm); `modal_spec` answers as a function of the value, not the discriminant. The registry covers `PromptState` and nothing else: the commit-message pane and startup-log viewer are not variants, which is stated in the module docs and must stay stated.
- **A modal with a full-text field must have a confirm button; a modal with only simple fields must not need one.** Like `<input>` vs `<textarea>`: single-line Enter submits unambiguously, so no button; multiline Enter is content, so the modal carries a button and Enter has three meanings by focus (ENGAGE the unengaged field, NEWLINE while engaged, ACTIVATE a focused control). Enforced by `ModalSpec::satisfies_dual_mode_rule` plus fixtures that BUILD every variant and RENDER it ("has a multiline field" is a runtime flag; "publishes a confirm button" is only knowable from `OverlayMouseLayout`). `KNOWN_DUAL_MODE_VIOLATIONS` is EMPTY and must stay that way, asserted as an EXACT set: a new violator must be named there and defended in review. House style for MODALS, not a logical necessity: the commit-message pane is a dual-mode field with no confirm button because submit there is bound to a different key.
- **A shared component probably already exists, ask before you invent one.** Look in `crates/dux-tui/src/app/components/` and `crates/dux-tui/src/app/modal.rs` first; if close, ASK. Already extracted, not to be re-hand-rolled: `App::open_modal_frame` (frame/dim/rect chrome), `components::focus_ring::next_focus`, `modal::modal_key_step` and `modal::binding_lookup_is_suppressed` (key ladder and text-field gate), `modal::click_target`, `components::hint_bar::modal_hint_line`, and the one shared `TextInput`.
- **All text entry goes through the one shared `TextInput`** (`crates/dux-tui/src/app/text_input.rs`: caret motion, word motions, multiline scrolling). Never hand-roll a buffer; a new typing surface gets a `TextInput` field, not a `String`.
- **There are two kinds of text field, and a real flag tells them apart.** `TextInput::with_multiline(n)` is what makes a field full-text, not height, label, or modal. Only a handful are multiline (commit message, startup command, project and global env, macro body); every other field is simple.
- **Simple (single-line) fields need no mode.** One focus stop, typing immediate, arrows reach the caret. `keybindings::text_field_owns_key` guarantees it: while a text field has focus, plain characters and horizontal arrows belong to the field and the binding lookup is skipped. The shipped bug this prevents: the selection-toggle action's default keys include the horizontal arrows, so pressing left in the rename-agent modal silently flipped the "also rename the git branch" checkbox.
- **Full-text (multiline) fields need the engage step, and engaging is always an explicit act.** A mode tracked by `App::input_target`. While NOT engaged the field owns no keys: movement keys move focus, a plain character is dropped. In a MODAL there are exactly three ways in, all offered by every modal full-text field: the CONFIRM key with focus on the field, the `EngageCommitInput` binding (default vim-style `i`; resolve through the bindings, never hardcode the letter), and a DOUBLE CLICK. (The commit-message pane is not a modal and predates this: it engages through `EngageCommitInput`, the files pane's open action, and a click on an already-selected commit section; leave it alone unless deliberately unifying.) Typing does not engage; auto-engage was removed. While engaged every key goes to the text; the exit-edit binding leaves edit mode and leaves the modal OPEN. Never let it close the modal, and never let it save.
- **An unengaged field must LOOK unengaged and must SAY how to start.** Focused-but-unengaged: focus border, NO caret (a caret on a field that will not receive keys is a lie), footer names the engage key. Engaged: additionally the `editing:` marker on the bottom border naming the stop key. Both go through the one shared `App::render_modal_text_field_frame`; an overflowable field carries the shared `components::scroll_marker`. Do not re-implement either.
- **The reason for that mode is Enter, not Tab.** The Tab rationale is wrong: dux cannot insert a tab character anywhere, and `text_input::tests::handle_key_returns_false_for_tab` pins Tab as unconsumed, so Tab stays a focus key. The real collision is Enter, content in a multiline field and the confirm key in every modal; only a mode tells them apart. A reader who believes the Tab story will build the wrong thing.
- **Space is content in both kinds of field.** Space-as-activate keys off focus actually sitting on a button or checkbox, never off the modal containing one, never off hover (there is no hover state). With a text field focused, Space is typed.
- **Filters, search rows, and the command palette are deliberately type-immediately.** Every one (palette, agent-list filter, files-pane search, macro bar, project browser and chooser filters, kill-running filter, startup-log filter and viewer search) puts keystrokes straight into its `TextInput` with no engage step. A key that opens a search row is a filter toggle, not an engage step. Do not "fix" the palette.
- **Escape never saves.** It abandons, or exits edit mode. (The macro editor was the one violation, corrected.)
- **A field the user cannot click into is a gap.** Publish the field's rect into `OverlayMouseLayout` every frame and route the click to a setter calling `cursor_from_single_line_position`. Every caret-bearing single-line field now does (the project chooser's `/`-search and the startup-log picker's filter were the last holdouts; both publish an `input: Option<Rect>` that is `Some` exactly while drawn). A new field publishes its rect in the same change.
- **A single-line field is rendered by `render_single_line_cursor_input`, never by hand.** It takes a `focused` flag and clamps the caret to a character boundary (hand-rolled BYTE splits like `after.split_at(1)` crashed dux on any accent or emoji, and drew the caret unconditionally). Pair the flag with `Theme::overlay_field_border_style(focused)`. The shared renderer does NOT scroll horizontally; no single-line field does, so a wide value runs off the end. Known gap, not a property of the renderer; converting a field does not close it.
- **A caret position is a DISPLAY column, never a byte offset and never a character count.** `input::cursor_from_single_line_position` (clicked column to byte caret) and `render::single_line_caret_column` (byte caret to hardware-cursor column) are exact inverses; use them. Wide glyphs (CJK, emoji) are two cells, so char counts and byte offsets both drift (clicking the `a` in `"日本語abc"` used to land the caret at the END). A click on the SECOND cell of a wide glyph resolves to the caret position BEFORE that glyph. Pass `prefix_width: 1` when the renderer pads one leading space; 0 lands the caret one character past the click.
- **Clickable controls need misclick-safe spacing.** A checkbox above modal buttons gets a blank row or equivalent.
- **Animations and periodic refreshes use wall-clock time, not tick counts.** Use `Instant::elapsed()` (or equivalent).
- **The embedded-PTY caret is the host hardware cursor, never a painted block.** Move the real cursor onto the PTY cursor cell (`set_cursor_position`); never pre-paint a styled block. Chosen for CJK IME accessibility (the OS anchors composition popups to the hardware cursor), and pre-painting reintroduces an invisible-caret bug under hosts like Alacritty that invert the cell. The caret look is the host terminal's cursor, not theme-colored; intentional.
- **The TUI does not disambiguate Shift-Enter; Ctrl-j is the supported soft-newline key.** Fullscreen forwards raw stdin verbatim and never pushes the Kitty enhancement flags (`PushKeyboardEnhancementFlags`): the legacy protocol sends the same byte (CR, `\r`/0x0D) for Enter and Shift-Enter, and pushing the flags re-encodes every key straight into the child, breaking providers that don't speak the protocol. `Ctrl-j` sends LF (0x0A), which agent CLIs treat as a soft newline; users wanting a literal Shift-Enter can run dux inside a Kitty-protocol multiplexer (e.g. tmux). The windowed typeable pane's key encoder deliberately maps Shift-Enter to plain CR so the two TUI regimes agree. Only the **web UI** rewrites Shift-Enter to LF (below), where the browser key event is available before xterm encodes it.

### Web UI (server mode)

The web UI (`crates/dux-web/web/`, React + Vite + Tailwind v4) has its own conventions, distinct from the TUI's `theme.rs` engine. Currently **dark-only** (`main.tsx` force-adds the `.dark` class); the light `:root` tokens exist but are inert. Style through the shadcn/base-ui token CSS variables (`--primary`, `--muted-foreground`, `--destructive`, …), never hardcoded colors. Recurring conventions leaned on below rather than restated per tenet: decision logic lives in pure, unit-tested helpers under `lib/`, never in the component; boundaries are pinned by exact-set tests; every deviation or relaxation is justified in a comment at the call site; a fact marked MEASURED was verified against shipped code or a real device and must not be "corrected" from memory.

- **Components: shadcn/base-ui first.** Reuse an existing `components/ui/*` primitive (`DropdownMenu`, `Dialog`, `Button`, `Tooltip`, …) before hand-rolling one. Hover hints go through the shared `SimpleTooltip`, never a native `title=`.
- **Row actions collapse into one `⋯` menu.** A list row needing more than one action gets a single `DropdownMenu` opened by an `Ellipsis`/`EllipsisVertical` trigger, not inline buttons. The trigger reveals on hover and consumes no layout space when idle (a `max-width`+`opacity` transition, or in the sidebar `SidebarMenuAction showOnHover`'s absolute `translate-x`+`opacity`). Keep it revealed while the menu is open via the trigger's `data-popup-open` attribute (`md:has-[[data-popup-open]]:…` or `data-[popup-open]:…`); Base UI does NOT set `aria-expanded=true` on an open menu trigger, so keying off `aria-expanded` silently never matches. Always show on touch (`max-md:` overrides), add `motion-reduce:transition-none`, and `stopPropagation` so the trigger doesn't fire the row's own click.
- **Menu items: icon + neutral color; "…" marks a further step.** Every dropdown `⋯` menu item keeps a leading lucide icon, no exceptions. Append a trailing `…` to any item that opens a dialog or needs confirmation. Default destructive items to NEUTRAL color: the `…` plus the confirmation dialog are the danger signal; reserve `text-destructive`/`variant="destructive"` for confirm buttons inside the dialog. One deliberate exception: the agent ⋯ menu's "Delete agent…" entry, red at rest and brighter on hover (`variant="destructive"` plus `not-focus:text-destructive/70!`), the most consequential per-agent action; do not propagate the red treatment without a deliberate decision.
- **Destructive actions always confirm.** A destructive item opens a dedicated `Dialog` (Cancel `autoFocus`, confirm button `variant="destructive"`, misclick-safe spacing) gated by a store target, following the per-action dialog pattern (e.g. `ConfirmDiscardFileDialog`); no shared `useConfirm` hook. Target-keyed dialogs route open state through the shared `useVanishedTargetGuard` (`hooks/use-vanished-target.ts`) so a dialog whose entity vanishes from the live ViewModel closes itself; `RemoveProjectDialog` and `CreateAgentDialog` are the deliberate exceptions. A monitoring surface confirms its stops too: every stop `TaskManagerDialog` offers (per-row and "Stop all…") routes through a confirmation, reusing `ConfirmCloseTabDialog` / `ConfirmDeleteTerminalDialog`, matching the TUI's `ConfirmKillRunningPrompt`. Keep the confirm cheap to dismiss so the hung-agent escape hatch stays fast.
- **Shift-Enter inserts a soft newline (LF), not a submit.** xterm collapses Enter and Shift-Enter to CR before `onData`, so the pane intercepts at the key layer via `attachCustomKeyEventHandler`. In `lib/termkeys.ts`: `softNewline(event)` matches only a bare Shift-Enter keydown (no other modifier, never mid-IME-composition, bailing on `isComposing`/`keyCode === 229`); `softNewlineAction(event, ctx)` folds in ownership and the armed latch. The component is a thin applicator: on a match it `preventDefault`s, `stopPropagation`s and returns `false` so xterm emits no CR; only the input owner writes the LF (0x0A), and only the owner's path scrolls to the live edge, clears selection, and consumes an armed one-shot Ctrl/Alt latch. Every other key returns `true`. The mobile accessory bar's dedicated `⇧↵` key and the physical-key handler both write through the one shared `writeSoftNewline(term, pty)`. Web-only on purpose; keep the branching in `termkeys.ts`.
- **Where a finger is doing the typing, the compose bar is the typing surface; xterm is never typed into directly while it is on. TWO SEPARATE RULES: WIDTH decides the LAYOUT (`useIsMobile`, the 768px breakpoint, nothing else); THE POINTER decides the TYPING SURFACE (`useIsCoarsePointer` and `touchSurfacesApply(mode, coarse)`, nothing else).** They are orthogonal: a tablet in landscape gets the desktop layout AND the buffered input. Load-bearing details:
  - The accessory and compose bars render wherever the pointer is coarse, including inside the desktop shell, where they take height out of the terminal rather than growing the `ResizablePanel` (the pane's ResizeObserver tells the PTY). `TerminalPane`'s `inColumn` says a pane has something below it. Deliberate corollary: a FINE pointer in a narrow window gets NEITHER bar.
  - `ComposeBar` is a controlled, buffered textarea with native keyboard assistance ON, plus a Send button (xterm's hidden textarea gives autocorrect/swipe/IME nothing to work with). Send = deliver + submit as MACRO-style keystrokes with the Enter travelling alone: `composeSendWrites(text)` in `lib/composebar.ts` plans `[macroPayloadBytes(text), CR]` (every `\r\n`/`\n`/`\r` becomes Alt+Enter, ESC CR; the bare CR is the submitting Enter); the caller delivers the CR `COMPOSE_SUBMIT_DELAY_MS` (150ms) after the body, guarded against unmount and socket drop. MEASURED: Claude Code (2.1.217 bundle) merges stdin chunks into one paste through a 50ms debounce and force-classifies any single key event over 800 chars as a paste; 150ms is 3x the window. An EMPTY Send is a single immediate bare CR, never delayed (confirms TUI menus without focusing xterm). Deliberately NOT bracketed paste (`bracketedPasteMode` not consulted): keeps "line break" and "Enter" distinct on the wire, reusing the macro quick-picker's proven transform.
  - Non-owners get no typing surfaces (the take-over card is a viewer's only interaction); the per-write owner gates stay as defense in depth. Buffer STATE lives in `TerminalPane` (value/onChange), not `ComposeBar`, so unmounting the bar never destroys a draft, and a draft survives an ownership round-trip. Enter inside the box inserts a newline, never sends. `sendCompose` returns a boolean; a refused send (not the input owner, socket not open, payload over `MAX_COMPOSE_SEND_BYTES`, a 2 MiB client cap under the server's 16 MiB WS frame limit) KEEPS the buffer and toasts why; the bar clears only on true.
  - A tap on the terminal redirects focus to the compose textarea (the touchend tap branch `preventDefault`s to suppress the synthetic mousedown xterm focuses from); with mouse tracking on, the tap is still delivered to the app as a click, via REPLAY (see the mouse-report tenet).
  - That same `preventDefault` is why a tap must hit-test an OSC 8 hyperlink itself: xterm's Linkifier resolves links from `mousemove`/`mouseup`, both suppressed, and publishes no "what link is at this cell" query, so `lib/termlink.ts`'s `activateLinkAtPoint` REPLAYS the suppressed sequence at the Linkifier rather than hit-testing in dux. Load-bearing: events go to `.xterm-screen` with `bubbles: false` (focus grab, selection service and mouse-report forwarding sit one level up on `Terminal.element`); a PRIMING move at a different cell on the same row comes first (MEASURED: the Linkifier only re-runs providers when the CELL changes; without it the second tap on a link opens nothing); a trailing `mouseleave` returns it to rest. Whether a link was hit is read from a counter bumped inside the pane's own `linkHandler.activate`, keeping `linkActivateAction` gating and the `noopener,noreferrer` window in one place; `terminalTapAction` deliberately still forwards the click on a link tap while NOT pulling focus into the compose box.
  - Every refocus-after-action goes through `focusTypingSurface()` (compose textarea while the bar is up, xterm otherwise); no bare `term.focus()` call sites. Send fires on pointerdown with preventDefault (keyboard stays up) plus a `detail === 0` click handler for keyboard/AT activation. Scroll gestures blur the compose input (reading dismisses the keyboard).
  - Gated by `ui.compose_bar` (default `auto`); off restores tap-focuses-xterm exactly. **The SETTING is the only configuration surface; the accessory-bar toggle is not a second one.** The toggle exists because a tablet with and without a keyboard case are indistinguishable to the browser (measured); transient UI state in `localStorage` (`lib/typingSurface.ts`), writing NOTHING to config. Precedence in `composeBarShown(mode, coarse, choice)`: `always`/`never` win outright; only `auto` consults the choice, which is why `typingSurfaceToggleOffered` renders the control under `auto` alone. It lives in the ACCESSORY bar (present in both states; inside the compose bar it would vanish when it turned the bar off), NAMES its state ("Box" / "Direct", full sentence on the aria-label), sits behind its own divider for misclick-safe spacing, and is text-only on the KEY row for room, MEASURED at 390px (an eighth navigation-row cell pushed it off-screen; an icon costs another 22px).
- **`lib/notify.ts` is the ONE place that raises a notification, and an exact-set test keeps it that way.** The only other file permitted to import sonner is `components/ui/sonner.tsx` (the Toaster component). Second attempt (`finalToast.ts` was meant to be the single raiser; 91 call sites imported sonner directly and took the bare 4000ms over the user's configured window, including the `0` opt-out), so `notifyBoundary.test.ts` asserts the permitted set as an EXACT equality. Stated reach: it strips comments with no string awareness and misses `require`, side-effect imports and template-literal dynamic imports; it catches ACCIDENTS, not evasion, and review handles the rest. **sonner stays the countdown MECHANISM and dux owns the POLICY** (pause-on-hover, hidden-tab pause, swipe, stacking come free). Two consequences: an **id means REPLACEMENT, not de-duplication** (sonner resets remaining time only when DURATION changes while re-running its close timer on every re-raise, so a repeated raise on a fixed id pins the toast open forever; measured: `term-copy` held 90s across 30 re-raises, so the copy/paste confirmations carry no id). And the configured window lives at **module scope** in the raiser, not threaded to call sites: nothing is left to capture stale.

- **Every toast dismisses itself, on a severity-graded window, EXCEPT the few that must wait for the user, and severity is VISIBLE.** Auto-dismissal is the default for every tone (the old Infinity policy silted the screen up). Windows derive from the one user-configurable base (`ui.status_clear_seconds`, default 6) in `lib/notify.ts`: info/success 1x, warning 2x, error 4x; a configured `0` keeps meaning "disable auto-clear" and applies to FINAL states only.
  - **`sticky` is the exception, a boolean ORTHOGONAL to tone**, not a fifth tone. It gets `duration: Infinity` and stays ESCAPABLE (measured: sonner gates the close button and swipe on `toastType === 'loading'`, not on duration, including when a sticky final REPLACES a spinner on the same id). **The rule, written down because "serious" inflates: sticky if and only if the user must act OUTSIDE the toast to recover, or something may have been lost or left half-done.** Qualifies: a file saved but never handed to the agent (the toast holds the only on-screen copy of its path); a git operation leaving a worktree orphaned or the database and `config.toml` disagreeing; "resolve in your terminal". Does not: a failed pull, a failed editor save (dirty buffer still on screen), a failed commit (nothing partial, `CommitDialog` keeps the draft; marked sticky once and REMOVED). Target: single digits out of roughly a hundred sites; when in doubt leave non-sticky and record at the site that it was weighed.
  - **Stacking**: `visibleToasts` is 5 on desktop, sonner's 3 on phones.
  - **A busy toast needs its own guard.** sonner refuses to retire a `loading` toast: no close timer, no close button, no swipe (all three pinned in `components/ui/sonner.test.tsx`, so a sonner upgrade that loosens any fails loudly). `lib/notify.ts` schedules the dismissal itself at `BUSY_TOAST_MAX_MS` (60s), cancelling the guard whenever anything else touches that id. 60s sits well clear of `dux_core::statusline::BUSY_TIMEOUT` (20s), after which the engine upgrades a stranded keyed Busy to a Warning; the guard must never fire while an operation is still live.
  - **Severity reads at a glance**: per-tone icon colors (`text-destructive` error, amber warning, sky info, green success, muted busy spinner) AND shape-distinct icons; color is never the only signal.
  - **Swipe dismisses** (the ~20px close button is not a touch target). sonner infers swipe directions by splitting the position string, so `bottom-center` left sideways swipes inert; `TOAST_SWIPE_DIRECTIONS` names `bottom`/`left`/`right` explicitly, `top` deliberately absent (upward pulls a bottom toast into the screen).
- **One marker for git status.** Every changed-file status marker renders through the shared `FileStatusIcon` (Primer Octicons `Diff-*` glyphs, colored GitHub-style), in the changes pane and the editor's tree/search alike. The raw status is interpreted once by the pure `fileStatusMeta(status) → { kind, label }` in `lib/changedFiles.ts`; the icon carries a tooltip label naming the status.
- **Touch targets ≥40px, and the exemption from that floor is PER AXIS.** Controls get at least `max-md:min-h-10` / `max-md:size-10` (40px) on phones; desktop density restored with `md:`. Primary hub controls (search, session/back) stay `size-11` (44px); denser terminal-screen chrome (accessory-bar keys, changed-files chip) uses the 40px floor. The floor exists so an imprecise tap does not hit a DIFFERENT control, so a control may go below 40px along an axis where every neighbour ON THAT AXIS is non-interactive or absorbs a stray tap harmlessly, keeping the floor on the other. - **A finger selects text with a LONG PRESS, and dux drives xterm's selection model itself rather than hoping the browser will.** Two facts make the obvious approach impossible, both MEASURED against the installed xterm 6.0.0: `xterm.css` puts `user-select: none` on `.xterm`, so the browser may never select in the terminal; and a browser synthesizes compatibility mouse events for a TAP but not a touch drag, so xterm's mouse-driven selection service never sees one (an earlier version left the work to a native selection that could not happen). - **A forwarded touch-scroll sends at most ONE wheel notch per touch-move; never a magnitude burst.** With mouse tracking on (an alt-screen TUI like Claude Code), a one-finger drag forwards wheel reports instead of scrolling locally. `onTouchMove` fires at ~60-120Hz, so forwarding the raw `dragScrollLines` magnitude emits a dense burst in one frame, where a real wheel sends one report per notch at human cadence; Claude Code's scrollback-pager repaint survives 1:1 but corrupts under the burst, duplicating lines, and the corruption PERSISTS (alt-screen has no client scrollback; no reconnect/replay heals it). The forward path caps to one notch per move via the pure `dragWheelReport` (`lib/viewport.ts`), `Math.sign` of the drag magnitude. The byte encoding is xterm's own because the report is a REPLAYED wheel event (next tenet); the bug was the burst, never the encoding, so do not "fix" it by touching the encoding. The LOCAL (normal-buffer) path keeps the full magnitude; do not restore the raw magnitude to the forward path.
- **A forwarded touch gesture is a REPLAYED DOM event, never a mouse report dux encodes itself.** A mouse report has two independent halves chosen by separate DEC private modes: a tracking PROTOCOL (`?9` X10, `?1000` VT200, `?1002` drag, `?1003` any-motion) and an ENCODING (`?1005` UTF-8, `?1006` SGR, `?1015` urxvt, `?1016` SGR pixels); `term.modes.mouseTrackingMode` publishes only the first. dux used to hand-build SGR reports gated on that field alone and compute the cell with `container.clientWidth / term.cols`; both halves were wrong (MEASURED: on a 390px phone the container is 374px where `.xterm-screen` is 361px, so 15 of 21 test points reported a different cell; and an app enabling tracking without `?1006` received SGR text it does not parse). Same technique as `lib/termlink.ts`, one level up (the link replay targets `.xterm-screen` with `bubbles: false` precisely so it CANNOT reach the mouse pipeline). Load-bearing: the RELEASE is dispatched at the DOCUMENT (xterm moves its `mouseup` listener there from inside its `mousedown` handler; X10, with no release, never arms it); nothing CLAMPS on dux's side (xterm clamps into the canvas and rejects out-of-grid, so a padding tap lands on the edge cell like a desktop click); `Terminal.onBinary` must be subscribed alongside `onData` (`CoreMouseService` routes a `DEFAULT` X10-byte report through `triggerBinaryEvent`; an `onData`-only pane dropped every such report, leaving a `?1000`-without-`?1006` TUI unclickable; measured in `tools/preview-env`), that payload encoded with `latin1Bytes`, never `TextEncoder` (X10 puts `col + 32` in one byte; UTF-8 would split it). A replay, not a better encoder, because xterm publishes NO read of the active encoding (`IModes` carries only `mouseTrackingMode`; the value lives on `CoreMouseService._activeEncoding`) and reaching into `term._core` is not on the table. - **The URL is the source of truth for position, and NOTHING in the web UI navigates relatively.** The hash names the whole position: the focused target plus a `/changes` suffix for the mobile changes screen. `mobileScreen` stays in LOCKSTEP with the focused target: `setState` repairs it in the same commit as any patch touching `selectedTarget`, and a patch stating the screen outright wins (how the changes screen opens). `syncUrl` writes both halves as one route; state to URL is the normal direction, URL to state happens only on popstate, boot, and the not-found retry. `routeScreen` is the inverse, telling `syncUrl` whether a move crosses a screen boundary: PUSH only when the destination is a different screen from the one the URL names, REPLACE otherwise, so switching agents or tabs never piles up entries while every screen change stays one Back away.   - The paste listener is registered on the terminal container in the CAPTURE phase, load-bearing: `attachCustomKeyEventHandler` returns false WITHOUT preventDefault for Ctrl+v precisely so the native paste still fires and xterm's handler reads the text, so image handling must run BEFORE xterm's handler on the hidden textarea inside that container (a key event carries no clipboard). It cancels the event only for an image. `defaultPrevented` staying false is NOT enough to pin that (the suite once passed with the listener deleted; a stray unconditional `stopPropagation` kills every text paste while leaving the flag false), so the stub `open()` appends a real textarea and a spy `paste` listener standing in for xterm's own, and the tests assert the spy FIRES for text and NOT for an image, also the only way the CAPTURE registration is exercised. The key handler must NOT swallow a paste chord for a non-owner (it used to, making the refusal unreachable on Linux/Windows); safe because a viewer's text paste ends in xterm's `handlePasteEvent`, whose `triggerDataEvent` is the pane's `onData`, which returns early for a non-owner, with the server's `may_write` denying it again. The compose textarea carries its own listener (it renders OUTSIDE the container); a path landing there joins the DRAFT, which the toast must SAY (`DropContext.delivery`). `ui.upload_write_gitignore` is a Preferences row; `ui.upload_directory` deliberately is not (a free-text row is a poor way to pick a path). Ownership and socket-open are rechecked immediately before EACH paste (a write to a closed socket drops silently); the compose sink additionally rechecks the BAR IS STILL THERE (it can outlive the box; if gone, report saved-but-not-added with the full path, deliberately not a fallback to the terminal sink, which would make a batch report two destinations). The read-the-window-from-a-ref pattern is GONE and must not come back: `lib/notify.ts` holds the window at module scope, so nothing is left to capture stale; raise through the raiser.
  - **A LONG TEXT PASTE IS THE SAME JOURNEY A THIRD TIME; the only new things are the DECISION and synthesising the file.** A wall of text spends the agent's context window; a path costs almost nothing. Past `ui.upload_pasted_text_chars` characters a text paste onto an AGENT becomes a `.txt` file through the same route, directory, form, length limit, collision naming and one toast, in the same pure `clipboardPasteAction`, which takes the clipboard's `text/plain` flavour as a PARAMETER read synchronously with `getData` (a `DataTransferItem` of kind `string` only yields async, after the paste happened). AGENT PANES ONLY, and STRUCTURALLY: `ClipboardPastePane` is a union whose `terminal` variant carries no threshold, so no later edit can invert it; a long paste into a shell is a command or heredoc and pastes verbatim at any length. The mobile compose bar is IN, a stated decision: the file is saved and its PATH joins the DRAFT (the ordinary `activeUploadSink` split, compose liveness check applying). The threshold counts CHARACTERS (code points), never bytes and never `.length` (bytes penalize Japanese three-fold, UTF-16 units two-fold); strictly greater, matching `pasteExceedsAttachmentLimit`. Counting is `countCodePoints(text, cap)`, a `charCodeAt` scan, NOT `[...text].length` (MEASURED on 20M chars: spread 218ms/180MB, iterator 127ms, this scan 37ms; with `cap = limit + 1` an ordinary paste stops at 0.1ms); the exact count for the toast is a second, uncapped pass once the paste is already becoming a file. `Ctrl+Shift+v` bypasses through the EXISTING `forceText` hatch, not a second latch. A non-owner is REFUSED with its own sentence (`NOT_OWNER_TEXT_PASTE_REASON`); an image still WINS when the paste carries both. The file is `new File([text], pastedTextName(now), ...)`, UTF-8 via the `Blob` constructor: no BOM added, no newline rewriting, nothing appended; MEASURED to preserve CRLF, lone CR, trailing whitespace, NUL, ESC, combining marks, RTL marks and a leading U+FEFF that arrived as content. Two exact caveats, both once claimed wrongly: a LONE SURROGATE becomes U+FFFD silently while still counting as one character (pinned as a known property), and the claim is about the JS string `getData("text/plain")` returned, not the OS clipboard's bytes; tests compare BYTES, never `await file.text()` (it STRIPS a leading BOM). `pastedTextName` shares `pastedImageName`'s stem. The toast MUST say what happened: `DropContext.pastedTextChars` adds a LEAD-IN naming the size before whichever rung the ladder chose, plus one shared RECOVERY sentence after; the lead-in follows the OUTCOME in TENSE ("tried to save" when nothing saved) and DESTINATION (it reads `ctx.delivery`). The RECOVERY sentence is on every rung and load-bearing on the bad ones: dux cancels the paste, so a failed save leaves the text neither typed nor saved; dux never writes to the clipboard, so the bytes are still there, and the sentence names the force-text chord and the Preferences row. A refusal carries a `subject` (`image`/`text`) so the two land on two toast ids. The default of 1000 is deliberately CONSERVATIVE (Codex's `LARGE_PASTE_CHAR_THRESHOLD` is 1000, Claude Code force-classifies over 800 chars; evidence of scale, not the reason), and ANY command can be a provider, so dux sits low; do not "correct" it upward because ordinary prose runs past it, that argument was made and declined. `0` disables it; floor and ceiling clamp with the warn-once-and-degrade pair (`normalized_upload_pasted_text_chars` pure, `upload_pasted_text_chars_load_warning` from `load_config`); the bootstrap projection normalizes AGAIN (`set_settings` and the raw config editor bypass `load_config`); the browser reads an ABSENT field as 0 (the `file_drop_max_bytes` rule). Unlike `upload_directory`, this one IS a Preferences row. Web-only, deliberately: a real terminal emulator already types a dropped path in for you.
- **Dropping a file on the EDITOR'S FILE TREE is the OTHER intent, and it is durable.** A pane drop means "look at this for me"; a tree drop means "add this file to my PROJECT", and the editor is the only surface where the user PICKS the destination by pointing at it. It lands as an ordinary VISIBLE file git can see, in the directory dropped on; never the uploads directory, never a `.gitignore`, never a path pasted into any terminal. The row decides the landing: a FOLDER row takes the files, a FILE row hands them to its PARENT (the same `targetDirForCreate` mapping New File… uses, reused), empty tree space is the worktree ROOT. The receiving row must HIGHLIGHT before the drop lands, asserted as the CLASSES the row paints (a `data-drop-target` marker no CSS read once let every `dropClass` call be deleted, leaving the tree visually inert with tests green). **A drop that MISSES every row must be swallowed** (`swallowMissedFileDrop`, on the overlay's `DialogContent` and the standalone shell's root): the browser's default action is to NAVIGATE to the file, and the tree's rows already `stopPropagation`, so the ancestor handler sees only misses. **dux takes files, not folders**: a folder is a NAMED refusal ("dux cannot take a folder, drop its files") sorted out of the `DataTransfer` by `classifyDroppedItems`, matched by NAME rather than index (`items` and `files` only line up when every item is a file); a drop delivering nothing identifiable gets its own message rather than silence. It reuses the ONE upload route (size cap, permit before buffering, never-rewritten name, pinned-handle create, symlink refusal, collision suffix), told apart by ONE query parameter, `dir`, distinguished by PRESENCE and not emptiness (the empty string is the worktree root, an ordinary drop target); presence also skips the route's input-ownership courtesy check (a tree drop pastes into nothing, and a browser really does carry a terminal-socket `conn`), a skip tested in both directions because deleting `query.dir.is_none() &&` otherwise breaks nothing. Server-side it is a third `FileDropDestination` variant whose `DropDir::open_tree_dir` walks components with `O_NOFOLLOW` like the uploads walk but CREATES NOTHING (STRICTER than create/rename/move, which canonicalize and permit an in-worktree symlinked directory; stricter is the safe direction, and both docs pages say so); a separate function, not a flag on `open_uploads`, because a boolean deciding whether a walk may create directories in the user's project gets passed the wrong way round. A terminal id must answer `None` there, never fall back to the terminal's own directory. Every refusal is a SENTENCE: a missing component is `TreeDirMissing` naming the folder, via `verified_path_of` rather than `reportable_path_of` (the absolute/UTF-8/no-control-character bar exists so a path can be TYPED INTO A PTY; this destination types nowhere; the identity half of the check is kept). **On a collision it SUFFIXES where the editor's move REFUSES**, both right for the same reason: a move names one exact destination, a drop names only a folder, so the next free name is the honest answer; neither overwrites, and the toast says which name was used. The client toast is `editorDropToast`, deliberately NOT `dropToastFor`, whose vocabulary (`sent`, `saved-not-sent`, "pasted the path") describes a delivery that does not happen here. Afterwards refresh like the MOVE path: `revalidateDirs` for the directory, `refreshSearchIndex` for the flat index.
- **In-browser file editing is web-only, and the TUI gets no counterpart.** The Monaco editor overlay (file tree, tabs, save, search, file create/rename/move/delete/info) and the config-file editor exist for editing ON THE GO; anyone at a terminal already has vim or helix. Do not build a TUI editor. The TUI's answer is `open-worktree`.
  - **A move is a MODAL, it is a RENAME on the wire, and an occupied destination is REFUSED rather than confirmed.** All three are decisions. Cut/copy/paste was declined (a file clipboard needs held-state, a visible indicator and paste-conflict rules; one dialog answers the question in one interaction). There is deliberately no `move` route: a move IS `rename` with a destination in another directory, reusing `dux_core::worktree_file::rename_entry` and every containment guard proven there; a second endpoint would be a second place for the guards to drift. An occupied destination is refused outright, no overwrite confirmation: there is no trash on the server, and the escape hatch (rename one, then move) costs one step; do not "improve" this into overwrite-with-confirmation without a real undo behind it. **The refusal has to be ATOMIC; a stat in front of `std::fs::rename` is not it.** `rename(2)` silently OVERWRITES (measured: file-onto-file and directory-onto-empty-directory both succeed), so `worktree_file::rename_no_replace` uses `rustix::fs::renameat_with` with `RenameFlags::NOREPLACE` (`RENAME_NOREPLACE` on Linux, `renameatx_np`'s `RENAME_EXCL` on macOS, dux's two targets). The fallback is narrow and stays named, never quietly the main path: only a filesystem answering `ENOSYS`/`EINVAL`/`ENOTSUP` (no `renameat2`; macOS before 10.12) runs the old racy pair. The SOURCE resolves with the no-follow resolver `delete_entry` uses (`entry_literal_path` plus `check_entry_parent_contained`): `rename(2)` moves the directory ENTRY, so moving a symlink moves the link, and a link whose target escapes the worktree is legitimate to move. The DESTINATION keeps the following resolver: a destination reached through a symlinked directory really would write outside the tree. The destination is chosen by BROWSING the same lazy `tree` endpoint the explorer uses (an empty directory stays reachable, a huge worktree costs nothing); the browser lists entries on `is_dir` alone, deliberately no second `expandable` check, because `git::list_dir` sets `is_dir` and `expandable` to the SAME value on every branch (an escaping symlinked directory comes back `is_dir: false`), so "a directory that cannot be walked into" does not exist on the wire.
  - **The info panel is the ONE editor dialog with a live truth to close itself on, the wire says which answer it got, and its freshness is exactly two fetches and no poll.** The other four (New, Rename, Move, Delete) key off the file tree, a client-owned lazy cache with nothing for `useVanishedTargetGuard` to watch, so they deliberately skip it. The route distinguishes the two failures: resolved-but-GONE answers **404** (`dux_core::worktree_file::EntryMissing`; the panel dismisses itself); REFUSED (traversal, `.git`, an escaping symlink, live or DANGLING) answers **400** and stays on screen with its reason. `FileApiError` carries the status for exactly this; keep the two answers apart. WHEN it learns any of that: no poll, no subscription; the fetch runs on exactly two events, the panel opening and the WINDOW REGAINING FOCUS (covering the real journey: delete in a terminal, come back). A file deleted by an agent while this tab stays focused is NOT noticed; that gap is accepted, stated here, in `web-editor.md`, and at the fetch. If you add a poll, rewrite all three.
    - **`GitStatusView` has a variant per genuinely different answer, and two of them exist because `git status` is SILENT rather than reassuring.** An ignored path and anything inside a nested repository or submodule are listed by no status call at all, so with only `Clean` to fall back on the panel called every file under `node_modules` "tracked and unmodified" (MEASURED), and the editor's tree has no ignore filter, so those paths are one right-click away. `Ignored` comes from `git::path_is_ignored`, `OtherRepository` from `git::repository_root` compared against the worktree, both pathspec-scoped and cheap. One place the discipline differs: `check-ignore` takes plain PATHNAMES and REJECTS the `:(literal)` magic `file_status` needs (MEASURED on git 2.55: "pathspec magic not supported by this command", exit 128), so it gets `--` and nothing else, correct because a pathname is already matched literally; `check-ignore` also consults the index, so a TRACKED file matching an ignore rule answers "not ignored", which is what we want. The panel's facts come from ONE no-follow stat (`symlink_metadata`, the link's own lstat, never the target's size/mode/mtime) plus that scoped git work, so a symlink is described as a symlink; the refusal of an escaping symlink is about the TARGET PATH STRING the panel prints verbatim. The web mirror keeps the vocabulary once: `fileInfo.ts`'s `codeLabel` takes its noun from the shared `fileStatusMeta` and only adds which SIDE the change is on.

### Agents and Providers

- **A provider is supported if and only if it supports PTY mode.** dux embeds the CLI's interactive session in a pseudo-terminal; that is the only thing a provider has to support.
- **Any CLI tool can be a provider.** Configure `command` in `config.toml` and dux spawns it. No adapters, no protocol layer. Adding a provider is a config-only change.
- **Claude, Codex, OpenCode, and Copilot are the defaults.**
- **No protocol layer.** No JSON-RPC, no custom message format, no adapter binaries. The CLI runs exactly as it would in a normal terminal.

### Agent Tabs

- **A tab is a provider session inside the agent's one shared worktree, not a new worktree.** One `AgentSession` (one branch, one sidebar row) hosts N provider tabs against the same checkout. **The strip carries provider tabs only**: companion terminals are never folded into it, and tabs are never separate sidebar agents. The strip renders at the top of the center/PTY pane and appears only with **two or more tabs**; a single tab looks exactly as today.
- **All tabs are generic; there is no Main/Support distinction.** No marker, no pin, no "Main"/"Support" labels anywhere user-facing. The one internal, load-bearing invariant is the **session-slot tab**, the tab with `tab_id == session_id`, which has no `agent_tabs` row (derived from the `agent_sessions` row). It keeps every session-keyed runtime lookup working and must never surface to the user as privileged.
- **Resume is decided dynamically by liveness, and it is per-provider.** A launching tab uses the provider's resume flag (e.g. `--continue`) **only when it is the sole tab of that provider coming up**: no other tab of the agent running the SAME provider is live or launching. Provider `continue` is directory-scoped AND per-provider for the resume-capable defaults (Claude, Codex, OpenCode): a claude tab and an opencode tab can both resume simultaneously; only two tabs of the same provider collide. Copilot is excluded from resume entirely (`resume_args: None` in `config.rs`): `should_resume_provider` returns `false` and `tab_resume_decision` always starts it fresh. The decision lives in exactly one place, `Engine::tab_resume_decision(session, tab_id, provider, requested)`: it ANDs the caller's request with `should_resume_provider(P)` (effective provider `P = tab_provider.unwrap_or(session.provider)`, must support resume and have started here) and a check that no OTHER tab of the session whose `tab_running_provider` equals `P` is in `providers` or has an in-flight `AgentLaunch`. `build_tab_launch_request` and every reopen path (web `launch_agent`, TUI `launch_focused_support_tab`) route through it, so the render badge, launch paths, and reconnect agree. There is no `resume_eligible_tab`; do not reintroduce a positional/first-tab notion of resume, and do not gate resume on `session.provider` when the tab runs a different provider.
- **Closing a tab ends that tab; closing the last live tab detaches the agent.** Closing any tab tears down its PTY. Closing an EXTRA tab also deletes its `agent_tabs` row, destructive and unrecoverable, so confirm it. Closing the session-slot tab has no row to delete; it goes through the single-tab `KillSessionPty` path, detaching the agent only when it was the last live tab. The distinct agent-level **"Detach agent"** action (`DetachAgent`, web `POST .../kill`) tears down EVERY tab and marks the agent Detached; separate from closing one tab. Deleting the agent tears down every tab's PTY. Extra tabs render in creation order and do not reorder; `sort_order` is an append-only stamp. **A clean exit closes the tab by itself**: when an extra tab's CLI exits 0, the row is deleted along with the prune, no confirm (no process to kill; the provider's conversation history lives in the worktree, so a fresh tab can resume it); a non-zero exit keeps the dormant tab as the crash-diagnosis/relaunch surface. The rule lives in `dux_core::engine::clean_exit_closes_tab_row`, honored by the TUI exit loop and the web's `prune_exited_ptys`; when the closed tab was on screen the pane minimizes, landing in the list when no live sibling remains.
- **New tabs default to the project provider and start fresh; provider is per-tab.** Adding a tab spawns the project `default_provider` immediately (fresh); retarget via `ctrl+p` (TUI) or the tab's `⋯` menu (web), effective on next launch. Per-agent cap: default 20, configurable via `agent_tabs_max`; the web "+" disables at the cap. The TUI deliberately has no "+" in the strip; tabs are added via the `new-agent-tab` palette command (or the NewTab keybinding), cap enforced in that flow.
- **Restart brings tabs back dormant, not running.** Each tab reopens as a pill with no process spawned, its content showing a **provider-agnostic** message (dux does not restore a tab's conversation across a restart; never name a specific provider command, they differ). **Focus alone never launches**; only an explicit action (Enter in the TUI, a button in the web) launches, with resume eligibility from `tab_resume_decision` like any other launch. There is no separate "always fresh" explicit-action path; the explicit action triggers the launch, it does not decide resume. On the web a dormant tab must render from a `has_live_process` flag WITHOUT opening the PTY socket, because subscribing force-launches the provider.
- **Tab state is derived runtime state: keep it in SQLite, never in config.** Extra tabs persist in an additive `agent_tabs` table (existing databases start with zero rows). The session-slot tab has no row. Do not write tab provider or order into portable project config.
- **Runtime provider state is keyed by tab id, with the session-slot tab id equal to the session id.** The `providers` map, `running_provider_pins`, resume-fallback state, and the PTY activity/streaming maps all key by tab id; `tab_id == session_id` keeps every session-keyed lookup working. **Sidebar liveness is any-tab**: the sidebar row and `SessionView.working`/`has_output` OR across ALL the agent's tabs. **Auto-reopen intent (`desired_running`) stays agent-level (session-slot-scoped)**, not OR-ed across tabs, so restart/auto-reopen semantics don't churn as extra tabs come and go. Only the center pane resolves the focused tab. Store `agent_tabs` in memory as `HashMap<tab_id, AgentTab>` (value carries `session_id`), O(1) ownership. A tab exiting while siblings are live shows a quiet, tab-scoped message ("Tab exited", or "exited cleanly and was closed"), never the workspace-wide "Agent exited" warning, which fires only when the LAST live tab exits (the pruned entry's `agent_detached`). If the session-slot tab exits while another tab is focused, stay on that tab.
- **Tabs honor each surface's existing UI tenets.** TUI: the strip is themed through `theme.rs` (reuse semantic fields; add a `dux.tab_*` token only where none fits); tab actions are Center-scope: switch keys (`Ctrl-Left`/`Ctrl-Right`, `Ctrl-1..9`, configurable) work whenever the pane is not fullscreen, INCLUDING while typing into the windowed pane (they are chords; the plain Left/Right defaults were dropped because those keys must type); no tab switching in fullscreen (minimize first); the strip is not rendered in fullscreen at all. `select_tab_4` ships with NO default key on purpose: under the legacy protocol Ctrl-4 and Ctrl-\ are the same byte (0x1c) and the macro bar keeps it, so tab 4 is reached via `Ctrl-Left`/`Ctrl-Right` or a rebind; the action still renders as a commented-out row in the config template for discoverability. TUI pills show their strip ordinal in the label (all positions) so `Ctrl-1..9` has a visible address; ordinals are strip positions, not stable ids, and renumber when a tab closes. Web pills stay un-numbered (deep links are the web's addresses): Chrome-style pills at the top of the terminal pane, deep-linkable (`#/agent/<sid>/tab/<tabId>` for extra tabs; the session-slot tab stays the bare `#/agent/<sid>`), reusing the shared `⋯`-menu, destructive-confirm, touch-target, and working-bob tenets above.

### Terminals

- **A terminal is owned by exactly one owner: an agent session, a project, or nothing at all.** Session-owned spawns in that agent's worktree; a project terminal at the project's repo root; a **standalone terminal** is owned by NOTHING and spawns in the user's home directory. Ownership never changes after spawn. `TerminalOwner::Standalone` is a real variant carrying no id, not an `Option` and not a sentinel; every ownership question is answered by an EXHAUSTIVE method on the type (`is_at_route`, `closed_by_session_delete`, `closed_by_project_removal`, `as_ref`), never a `matches!` at a call site, so a fourth kind is a compile error everywhere it must be answered for. On the web: `matchOwner`/`matchWireOwner` in `lib/terminalOwner.ts`, whose switches end in `assertNever`.
- **A standalone terminal opens in the home directory, from `home::home_dir()`, falling back to `/`.** Deliberately NOT the config-directory resolver (`Paths::config_root`, which consults `DUX_HOME`/`XDG_CONFIG_HOME` and answers where dux keeps its own files). The rule and its `~`-shortening twin live in `dux_core::home_path`, split into a function taking the resolved home plus a thin wrapper, so "home cannot be resolved" is testable without mutating the environment. An unresolvable home opens at `/` rather than refusing: the user asked for a shell and a shell runs anywhere. **What is resolved is a USABLE DIRECTORY, not merely a path**: a home that is a regular file, a dangling symlink, or unsearchable would fail the spawn. `dir_is_usable` answers all three with one `stat` on `path/.`; an unusable home takes the same `/` fallback. An EMPTY resolved home is rejected BEFORE that probe: the empty path is the one input where joining a component changes the subject (`"".join(".")` is `"."`); every other shape keeps its subject, measured (`joining_a_dot_only_changes_the_subject_for_the_empty_path`). It chooses a DIRECTORY and nothing more: never retry a failed spawn at `/`, because a missing shell or a bad `[terminal] command` is a configuration problem the user has to see.
- **A standalone terminal gets the global environment and no project overlay.** The two owned kinds merge `config.env` with their project's `env`; this one has only the global half.
- **A standalone terminal is addressable at UN-NESTED addresses** (`POST /api/v1/terminals`, `DELETE /api/v1/terminals/:tid`, `/ws/terminals/:tid/pty`, hash route `#/terminal/<id>`). Those addresses serve standalone terminals ONLY: an owned terminal is a 404 there, so the un-nested address is not a way around the nested routes' cross-owner rejections. Its palette command is `new-standalone-terminal` on both surfaces (TUI palette and web cog menu), and it is called a "standalone terminal" wherever named.
- **A standalone terminal's row names the DIRECTORY, not an owner.** The second line is the spawn directory with home collapsed to `~` (`~`, `~/code`), which the sidebar search also matches. It travels on the wire as `TerminalOwnerView::Standalone { cwd_label }` (the browser is not necessarily on the server's machine). It is the SPAWN directory, not a live probe: the string feeds the coarse change fingerprint, and a value moving on every `cd` would churn the sidebar and destabilize the search key.
- **Terminals are runtime-only.** No SQLite row, no config entry, no restore across restarts. Existence equals a running PTY.
- **Project and standalone terminals do not run the project's `startup_command`.** That command is a worktree provisioning step for new agents; a terminal of any owner is a plain shell running `[terminal] command`/`args` with the resolved environment.
- **Removing a project closes its project terminals** (graceful SIGTERM plus SIGHUP, because interactive shells ignore SIGTERM and the hangup is what ends them, then the reaper), exactly as deleting an agent closes that agent's terminals. Detaching an agent leaves its terminals running; projects have no detach.
- **NOTHING closes a standalone terminal automatically.** It ends when the user closes it or dux shuts down. A DECISION, not an oversight, written in a comment beside both `begin_close_session_terminals` and `begin_close_project_terminals` (and on the two `closed_by_*` methods) precisely so nobody later "fixes" the omission.
- **A terminal row is an agent row, rendered through the same shared row component on both surfaces.** Never a lesser single-line item. In the TUI it builds its `ListItem` through the shared `framed_row_item` (two content lines plus a trailing blank spacer) and paints selection through the shared `paint_framed_row_selection` (the half-cell tint frame, a `▄`/`▀` edge on the spacer rows, tint on the content rows only), with the same reserved top-margin row and `LEFT_PANE_GUTTER` padding. Never render a terminal row with the ratatui widget `highlight_style` (a full-cell flood); that idiom was deliberately removed. On the web it is the same two-row shape as the agent row. Change the agent row's framing/selection/spacing and the terminal row moves with it, because they share the code.
- **The row content is a two-line, two-column contract: two left elements ellipsize, two right elements survive.** Per line: `[fixed leading glyph] [left text (ellipsizes)] … [right text (survives)]`. Agent row: name/PR on line one, project/state (branch and tab count folded in) on line two. Terminal row: label/(nothing), owner/state (`agent@project` for a companion terminal, project name for a project terminal). The TUI realizes this through `fit_agent_meta_line` (marker + state word + tab count survive; project name + branch ellipsize) and `right_align_line`; the terminal row reuses those helpers, keeping the agent row byte-identical. Keep branch and tab count on the agent row: if they exist, they render.
- **A terminal has three states only: idle, running, typing. It never shows detached or needs-attention** (a live PTY is alive or gone). Priority mirrors the agent row (`agent_state_word` / web `stateWord`): typing outranks busy outranks idle. Wording deliberately differs for busy: a terminal shows **"Running"**, an agent "Working". Only the sidebar row shows these; the TUI kill overlay and web task manager are separate surfaces.
- **A terminal is busy (shown "Running") when it is streaming output OR a foreground app is running in it, even while quiet.** The shared `Engine::terminal_is_working` predicate (field/predicate keep the `working` name) feeds both `TerminalView.working` and the TUI row. `PtyClient::foreground_process_name` returns `None` at an idle prompt and `Some(app)` once a command runs, so a set `foreground_cmd` means an app owns the terminal and a running-but-quiet dev server/editor/watcher reads busy. Typing takes precedence. **A forwarded pointer report suppresses the streaming half only, deliberately**: streaming is an INFERENCE from repaint text and a repaint the user's own wheel provoked is no evidence, while the foreground app is a FACT read off the kernel. Suppress both and every terminal with a real process flickers to Idle on scroll.
- **Typing is a real keystroke within the input window, and a forwarded pointer report is neither typing nor evidence of work.** `pty::classify_pty_write` is the one classifier both surfaces call (through `Engine::note_pty_write`): `Typing` (keystroke or paste) stamps `pty_input`; `Ignored` (empty frame, focus report `CSI I`/`CSI O`, undecodable mouse report) stamps nothing; `Pointer` stamps `pty_pointer` and never `pty_input`. Bytes reach the PTY in every case; classification only decides the stamp. While `pty_pointer` is fresh, `Engine::is_agent_streaming` stops inferring "working" from output text and defers to the agent's own `OSC 9;4` report, falling back to not-working; honest cost: only Claude Code and Copilot emit `OSC 9;4`, so a genuinely busy Codex or OpenCode reads idle for the window. **Suppression length is per gesture**, decoded from the report's button field (`pty::decode_mouse_report`, `engine::pointer_suppression_window`): WHEEL arms `POINTER_REPAINT_WINDOW` (1250ms; notches keep coming), BUTTON press/release arms `POINTER_CLICK_REPAINT_WINDOW` (500ms; one repaint, and a click that starts work must let the cue appear promptly), MOTION arms nothing (any-motion apps emit one per cell crossed). Both surfaces are affected: the TUI forwards its own SGR reports too, and reading those as typing is the bug this replaced.
- **State colors are theme-derived, and Idle is the only unstyled state word.** Busy (agent "Working" / terminal "Running") is green (`Theme::session_working` in the TUI, `text-green-500` on the web), Typing is the theme's violet (`Theme::session_typing` / the `--dux-typing` token), Detached amber, Needs-you cyan; Idle uses the muted line color. Never hardcode a state color; add a semantic theme field wired through every theme when a new meaning is needed. The working green deliberately changed the agent row too, for web/TUI parity.
- **Line one (glyph + name/label) carries no live-state color; the "operating" cue is animation, not color.** The name/label keeps a stable IDENTITY color, neutral while live (`session_active`), dimmed when detached/exited, NEVER the typing/working color. Operating shows as the animated braille spinner glyph PLUS a name shimmer (TUI `shimmer.rs`, a wall-clock brightness wave; web `.agent-name-shimmer`); typing shows a caret glyph; attention keeps its accent blink. The live-state COLOR lives only on the line-two state word. The TUI run loop polls at ~30fps while `any_row_animating` and drops to the lazy 100ms cadence when quiet.
- **An idle terminal's sidebar name is a plain "Terminal"; the identifying "Terminal N" label survives everywhere identity matters.** In the sidebar row (TUI `terminal_row_lines`, web `TerminalFlatRow`) an idle terminal reads "Terminal"; a running one shows its foreground command. The `Terminal N` model label still drives the web tooltip, the breadcrumb, and the task manager's per-terminal stop buttons via `terminalTitle`.
- **Every sidebar element carries a position; both surfaces sort terminals by the active sort mode.** The same sort control that orders agents (TUI `Ctrl-p`, web sort dropdown) orders terminals, manual = drag order. Terminals get a runtime-only `sort_order` (stamped monotonically at spawn, reset on restart, never persisted) and a `ReorderTerminals` command behind `POST /api/v1/terminals/reorder`; the web reorders terminals within their own `SortableContext` (never crossing into the agents list). The sort comparators are duplicated per surface (Rust `terminal_items` / TS `sortFlatTerminals`) and must stay in lockstep.
- **Web only: the Terminals section is a collapsible divider with a chevron and no leading icon, matching the Inactive (Quiet tail) toggle, but defaulting OPEN** (a live terminal is worth surfacing; dormant Inactive agents default closed).

### Git and Data Safety

- **Worktrees are user data.** Never removed or mutated casually. Deletion requires explicit user confirmation.
- **Git operations are conservative.** Source checkout refresh uses `--ff-only`. Destructive operations require confirmation.
- **Commit messages are plain sentences.** No conventional commit prefixes (`feat:`, `fix:`, `chore:`). No structured trailers (`Constraint:`, `Confidence:`, `Scope-risk:`, `Tested:`) unless the user explicitly asks.
- **Prefer explicit failure over silent waiting.** If something fails, say so immediately with context.
- **A refname is a POSITIONAL, so every git call that takes one needs `--`.** A dash-leading branch/tag/commit-ish in a positional slot is read as an OPTION; git obeys it and exits 0, so the wrong thing happens and dux reports success. `git branch` refuses to CREATE such a name, but plumbing (`update-ref`) creates one outright and a non-leading component may begin with a dash (`foo/-bar`), so these names really reach dux. Measured on git 2.55: `git worktree add <path> --force` checks out HEAD; `git switch --detach` detaches; `git branch -m --force <new>` force-renames the CURRENT branch; `git push -u origin --all` pushes EVERY branch. Put the `--` in, and pin the reading with a test in the family already in `git.rs`.
  - **There are TWO exceptions, and in both `--` is NOT enough**: a porcelain command that consumes the separator itself and forwards the positional to an INNER git command with no separator. (`git push -u origin -- <name>` and `git branch -m -- <old> <new>` were verified genuinely protected; the plain rule holds everywhere else.)
    - **`git worktree add`.** Measured: it forwards the start point to an internal `git branch <name> <start-point>`, so a start point named `--force` or `--quiet` is obeyed even with `--` or `--end-of-options`. `create_worktree_from_start_point` therefore resolves the start point to an OBJECT ID first (`rev-parse --verify --end-of-options <sp>^{commit}`); 40 hex characters can never read as an option.
    - **`git pull`.** Measured with `GIT_TRACE=1` on git 2.55: `git pull --ff-only origin -- --force` runs `git fetch --update-head-ok origin --force`, separator gone; a branch named `--force`/`--prune`/`--all` is never fetched while pull exits 0 "Already up to date.", and a branch named `--depth=1` writes `.git/shallow` into the user's SOURCE CHECKOUT, converting it to a shallow clone. The object-id trick does not apply (the refspec names a ref on the REMOTE), so `pull_origin_branch` passes a FULLY QUALIFIED `refs/heads/<branch>` refspec, which cannot lead with a dash (measured: `git pull --ff-only origin -- refs/heads/--force` fetches and fast-forwards correctly).
    - When a separator does not visibly work, measure what the subcommand does with the argument. Every one of these gets a test in the `*_reads_an_option_looking_*` family in `git.rs`, no exceptions.
- **Every file dux keeps for itself is owner-only, and the config root's `0700` is what actually enforces it.** The per-file `0600` on `config.toml`, `sessions.sqlite3`, its SQLite sidecars and `dux.log` is defence in depth; the directory's mode is the real boundary (SQLite creates its sidecars with no mode dux can choose). The one place that decides any of this is `crates/dux-core/src/file_modes.rs`; do not chmod at a call site, and every file dux keeps must actually HAVE a mode (`config.toml` was once promised the every-start treatment by the template comment and `introduction.md` while nothing tightened it, so a hand-chmod'd `0644` stayed `0644`; `DuxPaths::ensure_dirs` now tightens it beside the root). Three rules hold there: tightening only ever CLEARS group and other bits, never the owner's, so it is idempotent and runs on every startup (required to reach existing installs); it is BEST EFFORT, a mode dux cannot set being a warning, never a reason to stop logging, stop opening the database, or refuse to start (getting that wrong once turned an un-chmoddable `logging.path` into no logging and no message anywhere); and it NEVER follows a symlink (the mode would belong to somebody else's file; a `config.toml` linked into a dotfiles repo is routine). dux does NOT tighten the user's own data: `worktrees/`, `dux.lock`, a user-created `themes/`. Preserving their mode is deliberate; tightening one must be argued for, not slipped in.
  - **"A `0400` config stays read-only" is a statement about the TIGHTENING PASS and nothing else; do not let it drift into a claim about writing.** `write_config_atomic` renames a fresh `0600` temp over the destination; rename needs write permission on the DIRECTORY, not the file, so a read-only config is replaced and comes back `0600`. Both surfaces say that outright. Preserving the destination's mode was considered and declined: it would carry a `0644` forward on every save and undo the tightening on the one file holding `[env]` tokens, and preserving `0400` would make dux look as though it honoured a file it overwrote. Pinned by `write_config_atomic_replaces_a_read_only_config_and_resets_its_mode`.
  - **Best-effort is a claim about an error path, so test the error path.** Making the tightening fatal in `create_private_dir_all` and `open_log_file` once left every `dux-core` test green: the apparent coverage took the SYMLINK branch, which returns `Ok(())` before any chmod. Two MEASURED shapes build the real case unprivileged: `create_dir_all` on `/proc/self/fdinfo` succeeds while the chmod is refused `EPERM` for every caller including root (procfs rejects `ATTR_MODE`, so it is root-safe), and `/dev/null` can be appended to while a non-root chmod on it is refused. Any new best-effort call site gets a test in that shape.

## Project Summary

`dux` is a Rust terminal UI for orchestrating AI coding sessions per git worktree.

The current app provides:

- A left pane for projects and agent sessions
- A center pane showing the agent's terminal output (embedded via PTY) or diff viewing
- A right pane for changed files and diffs
- Commented user config in the platform-specific dux config directory (`~/.dux/` on macOS, `~/.config/dux/` on Linux)
- Session persistence in `sessions.sqlite3` alongside the config
- Logging in `dux.log` alongside the config
- PTY-based agent startup: spawns CLI tools (`claude`, `codex`, `opencode`, `copilot`) directly in a pseudo-terminal

## Important Constraints

- The app spawns CLI tools directly via PTY (portable-pty) and renders their output using an embedded terminal emulator built on alacritty_terminal. There is no protocol layer (no ACP, no JSON-RPC).
- Long-running actions should not block the UI thread.
- All periodic or potentially-blocking work (git commands, file I/O, network) must run in background workers, never on the main UI thread. Even fast operations like `git symbolic-ref` should use workers in case the filesystem or git lock stalls.
- Async operations must keep the status line updated for the full operation lifecycle: a Busy message when the worker starts, then a clear success or failure message on completion. Do not start background work silently.
- User state lives under `~/.dux/` on macOS and `$XDG_CONFIG_HOME/dux/` (or `~/.config/dux/`) on Linux.
- **The web server (server mode) is single-tenant / trusted-access by design.** No login of any kind. The server binds `127.0.0.1` by default and optionally a Tailscale address; access control is delegated to loopback scope, Tailscale ACLs, or an upstream proxy. A Host-header allowlist and same-origin check guard against DNS-rebinding and cross-site requests. Every client shares one workspace: it can attach to and drive any agent or terminal PTY, browse the server's filesystem (project picker), and see every session's status and changed files. Intentional for a per-developer or trusted-team tool. Do not add features that assume mutually-distrusting web users without first designing a real per-user isolation model (session ownership enforced on subscribe/write, a sandboxed file browser, per-user status scoping).
- Worktrees are user data and should not be removed or mutated casually.
- Git operations should be explicit and conservative, especially around the source checkout.
- **Target platforms are macOS and Linux only.** Windows users run dux through WSL2, which is Linux. Do not add `#[cfg(windows)]` branches, `cfg!(windows)` checks, or Windows-specific code paths. Assume Unix throughout.

## App Module Structure

The `crates/dux-tui/src/app/` directory splits the TUI into focused submodules. Each file contains an `impl App` block for a specific concern:

- **`mod.rs`**: `App` struct, types, enums, bootstrap, run loop, and state helpers. Read this first to understand the data model.
- **`input.rs`**: All keyboard/mouse event handling (`handle_key`, `handle_left_key`, etc.).
- **`render.rs`**: All rendering methods (`render`, `render_header`, `render_left`, etc.) and UI helper functions.
- **`sessions.rs`**: Project and session CRUD (create agent, delete, reconnect, refresh, project browser).
- **`workers.rs`**: Background thread management (`drain_events`, `spawn_*`, `run_create_agent_job`).

When making changes, edit only the relevant submodule. A new `App` method goes in the submodule matching its concern; a new type or enum goes in `mod.rs`.

## Recommendations For Future Changes

- Keep the status line centralized. New async operations report progress through the shared status API, not ad hoc strings.
- The core keyed status controller (`dux_core::statusline::KeyedStatusController`) is the single source of truth for engine status across the TUI and the web. The **TUI renders it as a single status line** (most-recent-wins, documented-lossy for concurrent statuses). The **web renders it as toasts** (sonner), one per open keyed status, and **every web toast auto-dismisses, whatever its tone, unless marked `sticky`** (see the web toast tenet). **Correlation is by per-operation key**: a `Busy` and its final (success/error/`StatusCleared`) carry the same key so the surfaces replace/dismiss the right entry. Every `Busy` must be followed by a final; a keyed `Busy` left open expires to a Warning after the busy timeout. Do NOT add a third surface; do NOT emit an unkeyed `Busy` for a multi-step web operation (it strands the anonymous slot on a spinner until the leak guard retires it).
- **The controller has TWO retention policies, chosen at construction.** `StatusRetention::Retain` is the TUI's: Busy persists until a final replaces it, Info auto-clears after `ui.status_clear_seconds` (default 6; 0 disables), Warning/Error persist until the next status, what a most-recent-wins status line needs. `StatusRetention::Emit` is the web's, encoding that **a Busy is live STATE while a final is an EVENT**: a browser connecting mid-operation must be told what is running; one connecting long after has legitimately missed the outcome. The bug the split fixed: finals were retained forever and `server.rs` replays the snapshot to EVERY `/ws/events` connection, so an hour-old error re-raised as a fresh toast on every page load. **A final is not discarded outright, because of the reconnect**: a socket dropping between the Busy and its final would leave the outcome broadcast to nobody, the client's 60s leak guard silently retiring the spinner while an orphaned worktree sits on disk. So Emit retains a final for `FINAL_REPLAY_WINDOW` (30s) and `tick` then drops it. A FIXED CONSTANT, deliberately not `ui.status_clear_seconds`: replayability and on-screen time are different questions, and tying them would let a user's `0` ("never auto-clear") silently restore infinite retention. 30s is derived: the socket backs off 500/1000/2000ms over `MAX_RECONNECT_ATTEMPTS` of 3, so the last attempt starts ~3.5s after a drop. Accepted: a brand-new tab within 30s of a failure also sees it; a 30-second-old error is current. The expiry is SILENT (`tick` reports a count, not keys): a `status_cleared` at 30s would dismiss the toast everywhere, including every sticky one. Two knock-on effects: `ui.status_clear_seconds` has no server-side effect in web mode, and the engine no longer sends `status_cleared` for an expired Info on the web path. New status call sites follow the pending→final convention; never leave a Busy hanging.
- Status line messages must be verbose and actionable. Not "Done." or "Pushed."; explain what happened and, when relevant, what the user can do next: "Changes committed successfully. Press ^U to push to remote."
- Code must be production ready and modular for future Open Source contributors. No shortcuts.
- Route new modal UI through `PromptState` so `Esc` keeps working uniformly.
- Prefer command-palette actions over adding many more global hotkeys. **Per surface: in the TUI that means the `Ctrl-p` palette. The web has no palette; the equivalent home is the cog app menu (`appMenu.ts`), which deliberately has NO keybinding of its own.** Do not add a global web hotkey to reach a menu action; add the action to the menu.
- Keybinding labels shown to the user use proper casing (`Ctrl-g`, not `ctrl-g` or `CTRL-G`). The `^X` notation (e.g. `^P`) is acceptable in footer hint bars.
- Keybinding parsing from config is case-insensitive for modifiers and control keys (crokey lowercases the input). Letter keys are lowercased too, so `P` and `p` are the same binding; uppercase P must be written `shift-p`.
- Never hardcode keybinding labels in user-facing strings (config comments, status messages, UI text). Always look up the actual binding via `RuntimeBindings::label_for()` so labels stay accurate after rebinding. The only exceptions are pure text-input contexts and palette-only command names.
- Keep agent creation and other blocking git/provider work in background workers.
- The PTY approach is CLI-agnostic: any terminal command can be a provider. Keep it generic.

## Recommendations For Debugging

- First check the `dux.log` file in the dux config directory (`~/.dux/` on macOS, `~/.config/dux/` on Linux).
- Confirm whether the provider command in `config.toml` is installed and on PATH.
- If agent creation fails, determine whether it stopped in:
  - worktree creation
  - PTY spawn (command not found)
  - PTY process early exit
- If the UI appears frozen, verify the operation is on a worker path rather than the main event loop.

## Git Command Safety

When shelling out to git, **always ensure the command output is immune to user-specific git configuration**. Settings like `color.diff`, `diff.noprefix`, `status.branch`, `status.renames`, `core.quotePath` can alter output in ways that break parsing.

- **Prefer plumbing commands** (`cat-file`, `rev-parse`, `for-each-ref`) over porcelain for machine-readable output.
- **Use `--porcelain`** for `git status`. Never `--short` (affected by `status.branch`, `status.relativePaths`, etc.).
- **Prefer `--porcelain=v1 -z` when parsing status paths.** NUL-delimited records handle spaces, quotes, Unicode, and embedded newlines safely.
- **Use `--numstat`** for line-level diff statistics (tab-separated, config-immune).
- **Prefer `--numstat -z` when parsing file paths from diff stats.** Parse rename/copy records from NUL-delimited output.
- **Override config with `-c`** when no porcelain/plumbing alternative exists (e.g., `git -c color.diff=false diff`).
- **Imperative commands** that aren't parsed (`worktree add`, `branch -D`, `pull`) are fine as-is.
- **For imperative git commands, rely on exit status rather than parsing stdout.** Treat stdout/stderr as user-facing diagnostics unless Git documents the format as machine-stable.
- **Do not parse human-facing commands like `git branch --show-current` when a plumbing-style alternative exists** (`symbolic-ref --quiet --short HEAD`, `rev-parse`).
- **Avoid shelling out to `git diff` for display**: the project computes diffs in-process with the `similar` crate and highlights with `syntect`. Use `git::file_at_head()` for the base version and read the working copy from disk.

## Recommendations For Editing

- Follow the existing `crates/dux-tui/src/app/` submodule pattern. If a new feature area grows beyond ~200 lines, extract it into its own submodule with `use super::*;` and an `impl App` block.
- Keep changes scoped to one submodule at a time; avoid cross-cutting edits across multiple app submodules in one PR when possible.
- Use `theme.rs` constants for all colors and styles; never raw `Color::*` values in rendering code.
- Reuse existing semantic color names in `Theme` when they fit. Define a new semantic color only when no existing token fits, updating every supported theme/default mapping in the same change.
- The canonical config renderer produces a fully commented config on first creation. Subsequent saves preserve user edits via `toml_edit`. Users can run `dux config diff` to see what changed or `dux config regenerate` for the latest canonical template.
- **`dux config diff` is DERIVED from the config structure; adding a setting requires nothing of you.** `collect_config_changes` in `crates/dux-tui/src/cli.rs` projects both the parsed file and `Config::default()` to `serde_json::Value` and walks them structurally (replacing a hand-maintained list that had already drifted). `serde_json` rather than `toml` is load-bearing: TOML has no null and its serializer omits `None` fields, which would hide every default-`None` setting. Before touching it: it compares the PARSED FILE against `Config::default()` and deliberately calls neither `load_config` nor `ensure_defaults`, reporting what the user wrote, not what dux normalizes it into. Each subtree gets a POLICY, RECURSE or SUMMARIZE; `env` and `projects` are summarized so a token or local path can never reach the output (no third "ignore" policy on purpose). Emitted dotted paths are sorted explicitly (provider and macro names live in an insertion-ordered `IndexMap`), built from structural segments and quoted when a user-controlled key is not a bare TOML key, never reparsed with string-prefix checks. The exhaustiveness test mutates every leaf of the serialized default config and asserts a path is emitted for each; do not weaken it into a walk that merely visits leaves.
- **`dux config diff --raw` prints the whole config, `[env]` values included.** The plain summary is safe to paste into a bug report and `--raw` is not; say so wherever either is documented.
- When a setting can have a sensible default at first boot (the user's home directory, platform-specific paths), resolve and store the concrete value in `config.toml` right away; never leave a placeholder.
- Preserve safe failure behavior around project refresh and failed agent startup.
- **Never use byte-based `.len()` or `[..n]` slicing to truncate user-visible strings.** Terminal output, file paths, and UI text can contain multi-byte UTF-8. Use `.chars().count()` for length and `.chars().take(n).collect()` (or `char_indices().nth()`) for truncation; byte-based slicing panics inside a multi-byte character.

## Verification

Use:

```bash
cargo fmt
cargo clippy --all-targets --all-features -- -D warnings
cargo test
```

`cargo clippy --all-targets --all-features -- -D warnings` is a CI gate: the `Clippy` check on every PR runs this exact command and fails on any warning. Run it locally before committing; a new stable Rust release can enable new lints, and when that happens fix the code rather than suppressing the lint unless there is a specific, documented reason.

For interactive smoke testing, ask the user to run `cargo run` as a final sanity check rather than running it automatically.

**Seeing the web UI: use the preview container at `tools/preview-env/`, never a directly-run dux.** It builds the binary on the host, mounts it into an isolated Docker container (own config/sessions in named volumes, loopback-only port), ships a `fake` streaming provider, and screenshots via `./up.sh` + `./shot.sh` (see its README; for click-through journeys, write a throwaway `puppeteer-core` script from `shot.js`'s boilerplate or drive the REST API, and delete the script after). **Never run `dux server` or the TUI directly on the host to inspect UI work, and never kill dux processes on the host**: a directly-run instance shares the developer's real `~/.config/dux` with their own live dux, possibly the very instance this session runs inside; a stray instance corrupts shared state and a killed process can destroy the user's active session.

**The web UI is compiled into the binary, and a failed frontend build is a HARD build failure.** `crates/dux-web/build.rs` runs `npm run build` and panics if it fails, so `cargo build` fails. It deliberately writes no placeholder page and does not fall back to a previously built `dist/`; both existed only to let a failure continue quietly, and a release once shipped binaries serving `web assets not built` with every check green. The escape hatch for Rust-only work is `DUX_DISABLE_UI_BUILD` (any non-empty value), which SKIPS the build rather than tolerating a failure. With it set and no existing `dist/`: the binary embeds a notice page, `dux server` adds a banner warning row plus a `dux.log` WARN, and the tests in `crates/dux-web/tests/static_serving.rs` that need a real build print a `SKIPPED` reason and return. Because a skipped test is itself a hiding place, `pr.yml` and `release.yml` fail fast when `DUX_DISABLE_UI_BUILD` is set, and `release.yml` additionally starts the packaged archive (`.github/scripts/smoke_archive.sh`) before uploading. The real-build assertion is "the served page references a content-hashed bundle AND that bundle downloads"; a doctype and a root element are not evidence of a build. Contributor docs live in `CONTRIBUTING.md`.
